# 実測結果サマリ

このファイルは [`experiments.md`](experiments.md)（韓国語・約5,400行）から **実際に測定した数値だけ** を
抜き出した日本語版です。各実験の手順・スクリプト・失敗記録・考察は元の文書にあります。

測定は 2003年の名著2冊（Dan Tow《SQL Tuning》／ Cary Millsap《Optimizing Oracle Performance》）の
論点を、現代の PostgreSQL・MySQL・ClickHouse で**実際に動かして確かめる**という形で進めました。
書かれていることを確認するだけでなく、**合わなかった箇所・自分の記述が誤っていた箇所**も残しています。

> 本リポジトリの測定値は TPC のベンチマークデータを利用した独自計測であり、
> TPC の公式監査を受けた結果ではありません（[NOTICE](../NOTICE) 参照）。

## PART 1 — クエリチューニング（Dan Tow《SQL Tuning》）

### T-1 | 統計とインデックスは何倍効くか

TPC-H SF=0.5、PostgreSQL 16、`shared_buffers=1GB`、`work_mem=64MB`。

| 地点 | 状態 | 中央値 | 結合方式 | 推定行数 vs 実際 |
|---|---|---|---|---|
| A | 統計 ✗ インデックス ✗ | 1,296 ms | Merge + Parallel Hash | 113,139,667 vs 15,164（**7,461倍**） |
| B | 統計 ✓ インデックス ✗ | 375 ms | Parallel Hash Join | 推定が正常化 |
| C | 統計 ✓ インデックス ✓ | 215 ms | Nested Loop + Index Scan | 51,018 vs 3,791（13倍） |

統計がないと推定行数が **7,461倍** ずれ、プランそのものが変わります。
`ANALYZE` だけで 1,296 → 375 ms（3.5倍）。インデックスはそこからさらに 1.7倍でした。

### T-2 | フルスキャンとインデックスの転換点はどこか

TPC-H SF=0.5（`lineitem` 300万行）、`random_page_cost=1.1`。

| 範囲 | 取得行数 | 選択率 | スキャン方式 | 時間 |
|---|---|---|---|---|
| 1日 | 1,281 | 0.043% | **Index Scan** | 3.4 ms |
| 1か月 | 39,213 | 1.307% | Bitmap Heap Scan | 50.2 ms |
| 1年 | 453,459 | 15.113% | Bitmap Heap Scan | 289.2 ms |
| 18か月 | 679,323 | 22.640% | Bitmap Heap Scan | 327.3 ms |
| 20か月 | 756,799 | 25.223% | **Parallel Seq Scan** | 302.1 ms |
| 3年 | 1,363,921 | 45.457% | Parallel Seq Scan | 422.4 ms |

書籍の「20% / 0.5% 法則」に対し、この環境での切り替わりは **選択率 25% 付近**でした。
重要なのは、**オプティマイザが方式を変えた地点と、実際に速くなる地点が一致しない**ことです
（20か月で Seq Scan に変わり、時間も 327 → 302 ms と実際に改善）。

また SF=10 では、インデックスを追加したあとに**遅くなったクエリが2本**ありました（元文書 §T-2）。

### T-3 | 結合方式 — 同じデータ・別の機器で結論が逆になる

TPC-H SF=0.5。機器A / 機器B は CPU・メモリ構成が異なります。

| 強制条件 | 使われた結合 | buffers | 機器A | 機器B |
|---|---|---|---|---|
| 自動選択 | Nested Loop ×2 | 500,750 | **216 ms** | 234 ms |
| NL 禁止 | Hash Join ×2 | 77,016 | 429 ms | **144 ms** |

**同じクエリ・同じデータで勝者が逆転します。** buffers は Hash 側が 6.5分の1 なのに、
機器A では Hash のほうが遅い。「論理読み取りが少ないほうが速い」は無条件には成り立ちません。

インデックスの有無で Nested Loop の危険度も変わります。

| | 自動選択 | NL 強制 | 倍率 |
|---|---|---|---|
| `lineitem ⋈ part`、インデックス**あり** | 26.1 ms | **21.3 ms**（NL が勝つ） | 0.82倍 |
| `lineitem ⋈ part`、インデックス**なし** | 139.1 ms | **1,025.3 ms** | **7.37倍** |

### T-6 | スタースキーマでの駆動表選択

TPC-DS、`store_sales` 200万行、PostgreSQL 16.13、4回の最小値。

| `i_manager_id` | item 行数 | 選択率 | 進入点 | 時間 |
|---|---|---|---|---|
| `= 8` | 196 | 1.0% | **Parallel Seq Scan on item** | **28.6 ms** |
| `1~10` | 1,937 | 9.7% | Seq Scan on date_dim | 47.6 ms |
| `1~50` | 9,952 | 49.8% | Seq Scan on date_dim | 85.0 ms |
| `1~100` | 20,000 | 100% | Seq Scan on date_dim | 127.4 ms |

フィルタが絞り込むほど、オプティマイザは**進入点そのものを別の表に移します**。
Nested Loop を禁じると、絞り込みが強い場合ほど損害が大きくなりました（1% で **5.41倍**、100% では 1.95倍）。

### T-7 | 複雑なクエリの3つの罠

`store_sales` 200万行、PostgreSQL 16.13。

**① `NOT IN` と NULL**

| | 結果 |
|---|---|
| NULL 0件、`NOT IN` | 73 行 |
| NULL **1件**、`NOT IN` | **0 行** ← 200万件中わずか1件が答えを全て消した |
| NULL 1件、`NOT EXISTS` | 73 行（影響なし） |

速度でも `NOT IN` 377.4 ms に対し `NOT EXISTS` 47.4 ms（**8倍**）。

**② `work_mem` の崖**

| `work_mem`（200万行） | サブプラン | 時間 |
|---|---|---|
| ≥ 32MB | `hashed SubPlan` | 約1秒 |
| ≤ 30MB | `SubPlan`（再実行に転落） | **180秒超** |

2MB の差でプラン種別が変わり、**180倍以上**の差になります。設定値の線形な調整では捉えられない挙動です。

**③ `UNION` と `UNION ALL`**

| 分岐 | | 行数 | 時間 |
|---|---|---|---|
| 重なりあり | `UNION` | 44,750 | 208.8 ms |
| | `UNION ALL` | 332,530 | 145.2 ms |
| **互いに素** | `UNION` | 332,530 | 307.6 ms |
| | `UNION ALL` | 332,530 | **148.2 ms** |

分岐が互いに素なら結果は同一で、`UNION` の重複排除は **2.1倍の純粋な無駄**でした。

### T-8 | 結合キー＋フィルタの複合インデックス

TPC-DS、`store_sales` 200万行、4ラウンド交差測定。

| 条件 | probe buffers | min | median |
|---|---|---|---|
| ① NL、複合インデックスなし | 20,179 | 25.72 ms | 27.73 ms |
| ② NL + 複合 `(ss_item_sk, ss_sold_date_sk)` | 4,290 | 10.90 ms | 11.90 ms |
| ③ NL + カバリング `… INCLUDE (ss_ext_sales_price)` | **1,543** | **2.63 ms** | **2.88 ms** |
| ④ NL 禁止（全て Hash） | — | 115.05 ms | 126.79 ms |

カバリングインデックスで **9.8倍**（25.72 → 2.63 ms）、probe buffers は **13分の1**。
なお追加したインデックスは 43 MB で、既存 PK（60 MB）より小さく済んでいます。

### T-9 | 「箱の外」の解 — 事前集計と非正規化、そしてその代償

TPC-H SF=0.5。§T-8 が到達した下限をさらに超える手段を測りました。

| 方式 | 結合数 | buffers | min | median |
|---|---|---|---|---|
| ① 元のクエリ（インデックスのみ） | 3 | 500,750 | 400.3 ms | 418.1 ms |
| ③ §T-8 の最良（複合インデックス2本） | 3 | 349,914 | 310.3 ms | 324.7 ms |
| ④ 非正規化（フィルタ引き上げ） | **0** | **6,169** | **51.0 ms** | **53.4 ms** |
| ⑤ 事前集計マテビュー | 0 | **12** | **0.1 ms** | **0.1 ms** |

400 ms → **0.1 ms（4,000倍）**。ただしこれは**無料ではありません**。

| 項目 | ④ 非正規化 | ⑤ 事前集計 MV |
|---|---|---|
| 保存容量 | 289 MB | 512 kB |
| 更新コスト | 28.5 ms → **404.8 ms（14倍）** | `REFRESH` 343 ms |
| 伝播ファンアウト | 顧客1件の変更 → **40行**更新 | 全体再計算 |
| 適用範囲 | このフィルタ**組合せ**なら再利用可 | **このクエリ・このパラメータ専用** |

TPC-DS 側ではファンアウトがさらに非対称でした。担当者1名の再配置で、正規化モデルは
`item` 196行の更新に対し、非正規化モデルは **19,523行（ファンアウト100倍）**。

MV の汎用性と `REFRESH` コストも測っています。

| MV 設計 | 行数 | サイズ | REFRESH |
|---|---|---|---|
| 汎用（フィルタ列を `GROUP BY` に残す） | 967,874 | 108 MB | 5,240 ms |
| パラメータを定義に埋め込む（この質問専用） | **158** | **32 kB** | **70 ms** |

さらに同期トリガの実コスト、`FOR SHARE` のロック範囲、隔離レベルを上げた場合、
変更キュー＋非同期伝播への代替案、ワーカーの起こし方（ポーリング / `NOTIFY` / 固定窓 / 適応窓）まで
測定しています（元文書 §T-9）。**`NOTIFY` がポーリングより悪くなる境界**も特定しました。

### クライアント往復のコスト

| 方式 | 3回測定 |
|---|---|
| サーバ内部ループ 1,000回 | 5.7 / 5.5 / 5.8 ms |
| `IN` リスト1回 | 3.5 / 2.7 / 2.8 ms |
| **クライアント往復** 1,000回（TCP） | 255 / 288 / 240 ms |
| 同じものを1回 | 66 / 70 / 71 ms |

サーバ内部では 1.6倍の差が、クライアント往復を挟むと **3.8倍**になります。
Millsap の言う「往復の除去」が、2003年より通信が速い現在でも効く理由です。

## PART 2 — 応答時間と待ち行列（Cary Millsap《Optimizing Oracle Performance》）

### M-4 | 待ち行列理論の「膝（knee）」はどこか

PostgreSQL 16.13、**4 CPU コア**、`scale=10`（accounts 100万）、各20秒。

| clients | TPS | avg | p95 | p99 | W = R − S |
|---|---|---|---|---|---|
| 1 | 1,327 | 0.75 ms | 1.09 | 1.47 | —（基準 S=0.75） |
| **4** | **4,642** | 0.86 | 1.39 | 2.01 | 0.11 ms（13%） |
| 8 | 4,367 | 1.81 | 3.66 | 5.64 | 1.06 ms（59%） |
| 16 | 4,520 | 3.45 | 7.42 | 11.61 | 2.70 ms（78%） |
| 64 | 3,103 | 18.02 | 59.08 | 105.35 | **17.27 ms（96%）** |

4 を超えると TPS は伸びず、**応答時間の 96% が待ち時間**になります。

**そして、ここで自分の記述が誤っていました。** この表だけを見て「膝 = コア数」と書きましたが、
ワークロードと機器を変えて測り直すと **コア数の1倍から16倍まで散らばりました。**

| ワークロード | エンジン / 機器 | コア | 膝 | コア比 |
|---|---|---|---|---|
| `pgbench` tpcb-like | PostgreSQL 16.13 | 4 | **4** | ×1 |
| `sysbench` `oltp_read_write` | MySQL 8.0.46 | 4 | **8〜16** | ×2〜4 |
| `pgbench` tpcb-like | PostgreSQL | 32 | **128** | **×4** |
| `sysbench` `oltp_read_write` | MySQL 8.4.11 | 32 | **512** | **×16** |

32コアの PostgreSQL では、判定式（`TPS倍 < 1.3` かつ `遅延倍 > 1.5`）が倍数の空白で機能しなかったため、
**クライアント1増あたりの限界 TPS** という別の尺度を併用して膝を特定しました。

| 区間 | クライアント当たり限界 TPS |
|---|---|
| 32→64 | 127.4 |
| 64→128 | 59.6 |
| **128→160** | **20.9** |
| 160→184 | 20.7 |

128 を超えた瞬間に 3倍近く落ちて以降ほぼ一定 → **膝は 128**。

### M-6 | コミットコスト（`log file sync` 相当）

8 clients / 30秒、各設定2回。

| `synchronous_commit` | TPS | avg | p99 |
|---|---|---|---|
| `on`（既定） | 2,521 / 2,597 | 3.15 / 3.05 ms | 9.52 / 9.44 ms |
| `off` | **5,320 / 6,003** | 1.49 / 1.32 ms | 5.95 / 4.88 ms |

TPS **2.1〜2.3倍**。この差分が「コミットごとの fsync 待ち」の値段です（耐久性と引き換え）。

### M-7 | チェックポイント圧力 — 平均では見えない

16 clients / 60秒、`scale=10`。

| `max_wal_size` | TPS | p99 | **max** | 強制チェックポイント増 |
|---|---|---|---|---|
| 1GB（既定） | 3,438 | 15.51 ms | **69.4 ms** | +1 |
| 256MB | 3,023 | 17.07 ms | **3,745.9 ms** | **+6** |

TPS は 12%、p99 は 10% の悪化にしか見えませんが、**最大応答時間は 54倍（69 ms → 3.7秒）**。
平均と p99 だけを見ていると見逃す種類の劣化です。

## PART 3 — 書籍の外の主題

### X-1 | マルチテナント分離 — 3戦略はどこで分かれるか

`store_sales` 200万行、12テナント、PostgreSQL 16、4 CPU、4回の最小値。

**① 単一テナントの読み取り（性能差はほぼない）**

| 戦略 | buffers | min |
|---|---|---|
| A 共有 + 複合インデックス | 643 | 2.60 ms |
| A + RLS | 643 | 2.83 ms |
| B パーティション | 542 | 2.75 ms |
| C スキーマ分離 | 542 | 1.82 ms |

**② 条件を書き忘れたとき（ここで分かれる）**

| 戦略 | 条件なし `count(*)` | 判定 |
|---|---|---|
| A 共有テーブル | 2,000,000 | **漏洩** |
| A + RLS | 166,658 | 隔離 |
| B パーティション | 2,000,000 | **漏洩** |
| C スキーマ分離 | 166,658 | 隔離 |

パーティションは性能の道具であって**隔離の保証ではありません**。`WHERE` を1回忘れれば全テナントが見えます。

**③ 全テナント横断の集計／④ スキーマ変更のコスト**

| 戦略 | 横断集計 min | クエリ長 | DDL 回数 | DDL 時間 |
|---|---|---|---|---|
| A 共有 | 40.7 ms | 133字 | 1 | 1,031 ms |
| B パーティション | 24.5 ms | 133字 | 1（12へ自動伝播） | **635 ms** |
| C スキーマ分離 | **13.1 ms** | **1,601字**（`UNION ALL` ×12） | **12** | 1,219 ms |

**⑤ 騒がしい隣人（noisy neighbor）**

| 戦略 | 単独 | 隣人同時 | 低下 |
|---|---|---|---|
| A 共有 | 1,013 tps | 749 tps | **1.35倍** |
| B パーティション | 1,006 tps | 842 tps | 1.20倍 |
| C スキーマ分離 | 1,027 tps | 1,129 tps | 0.91倍 |

読み取り性能はどれもほぼ同じで、分かれるのは **隔離保証・横断集計・運用コスト・相互干渉**でした。
MySQL / InnoDB 版、TPC-DS × MySQL 版も測り、エンジンを変えても同じ戦略が同じ値を持つかを確認しています。

### X-2 / X-3 | 無停止スキーマ変更（1,000万行・背景書き込み負荷あり）

背景負荷 2,300〜3,700行/秒の下で、`INT → BIGINT` の型変更を測定。
この変更はテーブルの作り直しを伴うため、ネイティブ `ALTER` では書き込みが止まります。

| 方式 | 全体所要 | 書き込み停止 | 停止 / 全体 |
|---|---|---|---|
| MySQL `ALTER ... MODIFY`（ネイティブ COPY） | 17.5秒 | 15.2秒 | 87% |
| PostgreSQL `ALTER ... TYPE`（ネイティブ） | 7.8秒 | 7.6秒 | 98%（`ACCESS EXCLUSIVE` のため読み取りも停止） |
| MySQL gh-ost | — | **約1.1〜1.4秒** | 切り替えの瞬間のみ |
| PostgreSQL 手書き expand-contract | — | **18〜29 ms** | 切り替えの瞬間のみ |

比較のため、再作成を伴わない変更も測っています。

| | 所要 | 書き込み最大空白 |
|---|---|---|
| MySQL `ADD COLUMN ... ALGORITHM=INSTANT` | 70 ms | 2 ms |
| PostgreSQL `ADD COLUMN ... DEFAULT 'x'` | 35 ms | 6 ms |

**チャンクサイズの効果**（gh-ost、1,000万行）

| チャンク | 所要 | cutover ブロック | バックフィル 行/秒 |
|---|---|---|---|
| 100 | 1,260.3秒 | 1,099 ms | 7,935 |
| 1,000 | 255.1秒 | 1,431 ms | 39,205 |
| 10,000 | **120.0秒** | 1,121 ms | **83,316** |

**レプリカ遅延によるスロットルが実際に効くか**も、遅延を人為的に作って確認しました。

| | throttle 対象 | 所要 | 完了 | 実スロットル |
|---|---|---|---|---|
| 対照群 | replica1（遅延なし） | 270.1秒 | 完了 | 10行 |
| 処置群 | replica2（遅延75秒） | 450.1秒（タイムアウト） | **未完了** | 449行 |

### 自分が出した測定値の誤りを発見し、訂正しました

gh-ost の cutover を当初「6〜12ms」と記録していましたが、背景負荷をかけるローダーが
複数の statement をまとめてサーバへ送る構造だったため、**実際には1秒近く止まっていた区間が
ログ上から消えていました**。1 statement ごとに結果を読んでから次を送る同期的なローダーに
書き直し、1,000万行で測り直した結果が上の値です（**約100〜200倍の差**）。
この測定バグは PostgreSQL 側の結果にも影響していたため、関連する記述もあわせて訂正しました。

→ 訂正の経緯は [コミット 5e33b1e](https://github.com/ruke79/sql-tuning-lab/commit/5e33b1e) に残しています。

### PostgreSQL の cutover が常に約1,034ms だった真因

バッチサイズを変えても cutover が常に約 1,034 ms に張り付いていました。
gh-ost の戦略（`lock_timeout` + リトライ）を移植したところ **29倍悪化**。
背景負荷の接続数という仮説も実験で否定しました。
`pg_locks` / `pg_stat_activity` を cutover の瞬間にサンプリングして見つけた真因は
**autovacuum** で、ロックを譲るかどうかの判定周期が `deadlock_timeout`（既定1秒）に
縛られていたためでした。バックフィル中だけ停止すると **23.5倍改善**。

既知の解法を持ち込む前に、何が待たせているかを実際に見る必要がある、と学んだ件です。
なお cutover の残差（44〜87 ms）の原因も、ロック待ちではなく
**毎回新しい接続を張るコスト**であると特定し、接続再利用で 18〜29 ms に下げています。

### X-5 | オンラインインデックス作成（⚠️ 構造検証のみ）

| | 所要 | 書き込み最大空白 | 空白/全体 |
|---|---|---|---|

## 命題51件の実行検証（verify-lab）

「説明できると言っている技術的命題を、実際に動かして再現できるか」を判定する検証ラボです。
Spring 7・JPA 7・並行処理 5・JVM 7・DB 25 の計51件を PostgreSQL 16.13
（プライマリ＋ストリーミングレプリカ）の実環境で実行し、**51件すべて CONFIRMED**
（REFUTED・INCONCLUSIVE・ERROR はゼロ）。

- CDC は `wal_level` を `logical` に上げなければ判定できませんでした。ただし logical は
  UPDATE あたり WAL が約80バイト増えるため、書き込みコストの測定基準は `replica` に戻しています
- レプリケーション遅延は同一ホストでは数ミリ秒で追いつくため、`recovery_min_apply_delay=2s` で
  観測窓を人為的に開けて初めて再現できました
- Kafka 3.9.1（KRaft 単一ノード）の実ブローカーでも MSA 命題7件を検証し全件 CONFIRMED。
  所要は Kafka が1件あたり 6.9秒、Spring が 12ミリ秒で、**500倍以上**の差があります
  — 実物で検証することの代償も測っています

結果は run 単位でテーブルに記録し、Grafana のダッシュボード17パネルで可視化しています。

## この文書の読み方について

数値はすべて自分の環境で実際に測ったものです。一方で、次の点は測定の限界として明記しておきます。

- **機器依存**: §T-3 / §T-5 のように、同じデータでも機器を変えると勝者が逆転します。
  絶対値ではなく「どの条件で何が起きるか」を読むための数値です
- **スケール**: 多くは SF=0.5（300万行）／`store_sales` 200万行の縮小スケールです。
  §X-2 / §X-3 のみ 1,000万行、§X-5 は 512行の構造確認にとどまります
- **未了**: §X-5 の 1,000万行実測は未了です
- **TPC 公式結果ではありません**: 独自計測であり監査を受けていません（[NOTICE](../NOTICE)）

手順・スクリプト・失敗記録・考察の全文は [`experiments.md`](experiments.md) にあります。
