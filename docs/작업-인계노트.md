## 2. 검증 방식

이 프로젝트의 모든 수치는 **실제 PostgreSQL 16을 띄워 측정**했다(SF=0.5, lineitem 300만 행).
문서의 SQL 블록 31개는 전부 파싱 검증했고, gradle 명령 참조는 소스와 대조했다.

한계: **ClickHouse는 실행 검증하지 못했다**(환경 제약). 명령 형태는 compose 설정 및
기존 스크립트와 대조만 했다.

## 3. 해결한 문제 (시간순)

| 문제 | 원인 | 조치 |
|---|---|---|
| `column "r_regionkey" is of type integer but expression is of type character varying` | `setString()`이 파라미터를 varchar로 확정 → PG가 캐스팅 거부 | PG는 `Types.OTHER`(Oid 미지정)로 바인딩 |
| `store_sales_pkey ... is duplicated` | 생성기가 한 영수증에 같은 상품 중복 생성 | 영수증별 상품 중복 제거 |
| `multiple definition of 'nItemIndex'` (dsdgen) | GCC 10+ 기본값 `-fno-common` | 컨테이너에 `-fcommon` 주입 gcc 래퍼 |
| 실습이 변수 2개를 동시에 변경 | `index` 명령이 인덱스+ANALYZE를 함께 수행 | `analyze` / `vacuum` 명령 신설, §T-1을 4지점 실험으로 재설계 |
| 문서에 `SELECT ...` 플레이스홀더 5곳 | 실행 불가 | 전부 완전한 SQL로 교체 |
| 스크립트가 멈춤 | 인덱스 없이 NL 강제 → 반복 풀스캔 | `statement_timeout` 가드 + 인덱스 누락 사전 경고 |
| 40줄 스택 트레이스 | 테이블 미생성 상태로 실행 | `SchemaCheck` — 준비 상태 점검 후 할 일 안내 |
| ClickHouse 접속법 부재 | 문서에 PG/MySQL만 있었음 | §0-1 세 DB 접속, §0-2 ClickHouse 용어 대응표 |

## 4. 실측으로 확인된 결과 (이 프로젝트의 핵심 자산)

### T-1 — 통계가 인덱스보다 중요했다

| 지점 | 상태 | 중앙값 | 조인 방식 |
|---|---|---|---|
| A | 통계✗ 인덱스✗ | 1,296 ms | Merge Join |
| D | A + `jit=off` | 734 ms | 〃 |
| B | 통계✓ 인덱스✗ | 375 ms | Parallel Hash Join |
| C | 통계✓ 인덱스✓ | 215 ms | Nested Loop + Index |

전체 개선 중 **통계 921ms(85%), 인덱스 160ms(15%)**.
A의 추정 오차는 7,461배(113,139,667 vs 15,164)였고, 부풀려진 비용이 JIT 임계값을 넘겨
A 시간의 43%(562ms)를 컴파일에 소모했다. **나쁜 통계 → 나쁜 계획 → 불필요한 JIT** 연쇄.

### T-2 — 전환점과 클러스터링

- 풀스캔 전환점 **22.6~25.2%** (책의 20% 기준과 근접)
- `l_shipdate` correlation ≈ 0 → plain Index Scan은 0.043%뿐, 0.1~22%는 **Bitmap Heap Scan**이 지배
- **진짜 교차점은 15~22%인데 옵티마이저는 22~25%에서 전환** → 그 구간에서 13% 손해
- 선택도 7.55%에 이미 페이지의 74.5%를 읽음(초선형)

**CLUSTER 실험 (제로섬)**

| | CLUSTER 전 | 후 |
|---|---|---|
| l_shipdate correlation | -0.005 | **1.000** |
| l_orderkey correlation | **1.000** | 0.004 |
| shipdate 범위 쿼리 | 226.6 ms | **73.1 ms** (3.1배 개선) |
| orderkey 조인(q03) | 225.8 ms | **273.6 ms** (1.21배 악화) |

물리 순서는 하나뿐 → 클러스터링은 공짜가 아니라 **접근 경로 선택**이다.

### T-3 / T-5 — 승자가 장비에 따라 갈린다

같은 데이터(고정 시드로 행수 동일), 같은 PG 버전인데 결론이 반대다.

| q03 | buffers | 장비 A | 장비 B |
|---|---|---|---|
| Nested Loop (옵티마이저 선택) | 500,750 | **216 ms** | 234 ms |
| Hash Join | 77,016 | 429 ms | **144 ms** |

장비 B에서는 **옵티마이저가 틀렸다**(1.6배 손해). q05도 1.35배 손해.
조인 순서(§T-5)도 마찬가지 — "나쁜 순서"라 이름 붙인 lineitem 드라이빙이 장비 B에선 1.21배 빨랐다.

**q09는 LIO의 한계를 보여준다**: NL 92,249 buffers 36.4ms vs Hash 86,593 buffers 166.3ms.
버퍼는 거의 같은데 시간은 4.6배 — `buffers`는 해시 테이블 구축 CPU를 세지 않기 때문.

### T-4 — 인덱스 무력화의 실제 모습

계획에 인덱스 이름이 보여도 소용없다. **`Index Cond`냐 `Filter`냐**가 기준이다.

| | 조건 위치 | buffers | 시간 |
|---|---|---|---|
| 범위 비교 | **Index Cond** | 102 | 14.2 ms |
| `extract(year ...)` | **Filter** | 640 | 83 ms (워커 4개) |

같은 인덱스·같은 결과 행수인데 6배 느리다. 추정도 23배 빗나간다(표현식엔 통계가 없음).
`c_custkey + 0`, `::text` 형변환도 동일하게 인덱스를 죽이며 추정이 1 → 375로 망가진다.

**VACUUM 여부가 계획을 바꾼다**: 적재 직후 Parallel Seq Scan(13,656 buffers, 121ms)
→ VACUUM 후 Parallel Index Only Scan(640 buffers, 83ms).

### T-8 — 결합 인덱스로 조인 방식 판정이 뒤집혔다

§T-5에서 지목한 지점(lineitem probe 한 노드가 전체 LIO의 60%)을 실제로 공략했다.
`l_shipdate`가 `Filter` → `Index Cond`로 올라가고 `Rows Removed by Filter`가 사라진다.

| 조건 | probe buffers | 총 buffers | min | median |
|---|---|---|---|---|
| ① NL, 결합 인덱스 없음 | 301,369 | 500,750 | 407.2 ms | 433.3 ms |
| ② NL + 결합 인덱스 | **228,320** | 427,701 | **313.0 ms** | **330.6 ms** |
| ③ NL + 커버링 인덱스(INCLUDE) | 224,993 | 424,389 | 292.8 ms | 333.7 ms |
| ④ Hash | — | 77,016 | 321.9 ms | 360.6 ms |

**①에서 Hash에 졌던 NL이 ②에서 역전한다(313 vs 322).** §T-3·§T-5에서 "이 장비는 Hash가 낫다"고
판정났던 q03의 결론이 인덱스 하나로 뒤집혔다 — 조인 방식의 우열은 고정된 성질이 아니라
**쓸 수 있는 접근 경로의 함수**다.

**절감분은 전부 힙 접근에서 나오고 거기서 멈춘다.** 줄어든 73,049 buffers는 전부 probe 노드 몫인데,
③으로 힙 접근을 0(`Heap Fetches: 0`)으로 만들어도 3,327밖에 더 안 준다.
남은 224,993은 **74,024번의 B-tree 하강 자체**(74,024 × 약 3 buffers ≈ 222,000에 수렴)이고 이것이 NL의 하한이다.
인덱스는 90MB → 135MB로 1.5배 커지므로 **②에서 멈추는 것이 옳다.**

### T-8 이어서 — orders probe: 만들어도 옵티마이저가 안 쓴다

②를 적용하면 병목이 옮겨간다. lineitem 이 228,320 으로 줄면서 **orders probe 가 197,553 으로
전체의 46%** 가 된다. 노드 모양이 §T-8 도입부와 똑같다(`Index Cond`=조인키, `Filter`=날짜,
`Rows Removed by Filter: 5`). probe 당 약 13 buffers(3 하강 + 10 힙)로 **힙 낭비율이 50%** 다.

같은 처방 `CREATE INDEX ON orders (o_custkey, o_orderdate)` 를 적용했더니 —
**옵티마이저가 무시하고 계속 좁은 `idx_orders_custkey` 를 골랐다.**

| 인덱스 | 크기 | 추정 비용 |
|---|---|---|
| `(o_custkey)` | 6,816 kB | `0.42..1.70` ← 선택됨 |
| `(o_custkey, o_orderdate)` | 23 MB | `0.42..1.73` |

차이가 1.8% 뿐이다. `o_orderdate < '1995-03-15'` 선택도가 **48.7%** 로 약한 데다,
`random_page_cost=1.1` 에서는 힙 접근이 거의 공짜로 계상돼 **절약분이 비용 모델에 안 잡힌다.**
`random_page_cost` 를 올려도 소용없다 — 1.5 이상에서는 결합 인덱스로 가는 게 아니라
**NL 을 포기하고 Hash Join 으로 계획이 통째로 바뀐다.**

**좁은 인덱스를 지워야 쓰인다** (`(A)` 는 `(A,B)` 의 선행 부분집합이라 기능적으로 중복).

| 단계 | orders probe | lineitem probe | 총 buffers | min | median |
|---|---|---|---|---|---|
| ① 원본 | 197,553 | 301,369 | 500,750 | 400.3 ms | 418.1 ms |
| ② + lineitem 결합 | 197,553 | 228,320 | 427,701 | 287.8 ms | 332.1 ms |
| ③ + orders 결합(좁은 것 제거) | **119,766** | 228,320 | **349,914** | **267.5 ms** | **291.4 ms** |

①→③ 총 buffers 30.1% 감소, median 30.3% 단축. 별도 교차 측정(n=36)에서도
좁은 인덱스 대비 결합 인덱스가 min 251.0/median 290.8 vs 285.4/315.5 로 일관되게 빨랐다.

**여기서 얻은 두 가지**

1. **인덱스를 만드는 것과 옵티마이저가 쓰는 것은 별개다.** `(A)` 와 `(A,B)` 가 공존하면
   PostgreSQL 은 더 작다는 이유로 좁은 쪽을 계속 고른다. 넓은 것을 만들었으면
   **좁은 것을 반드시 지워야** 한다. 안 지우면 디스크만 더 쓰고 계획은 그대로다.
2. **이번엔 비용 모델이 절약분을 과소평가했다.** §T-3에서는 `buffers` 만 보면 틀린다고 했는데
   (Hash 가 buffers 적지만 느림), 여기선 정반대로 76,000회의 힙 접근 절약을 0.03 으로 계상했다.
   **`buffers` 도 추정 비용도 단독으로는 못 믿고, 실측만이 판정한다.**

### T-9 — 인덱스가 못 넘는 벽을 모델 변경으로 넘는다

§T-8 이 lineitem probe 228,320 에서 멈춘 지점(74,024회 B-tree 하강이 하한)에서 이어진다.

**문제 정량화.** q03 의 필터는 3개 테이블에 흩어져 있다(선택도 0.2024 / 0.4866 / 0.5384).
독립 가정으로 곱하면 149,646 행이 나와야 하는데 **실제는 15,164 행** — `o_orderdate` 와
`l_shipdate` 가 상관되어(주문 후 배송) 결합 선택도가 10배 강하다(Tow 2장 *filter redundancy*).
최종적으로 300만 행 중 **0.505%** 만 필요한데, 필터가 흩어져 그 조합에 도달하려면
이미 큰 테이블을 다 헤집은 뒤여야 한다는 것이 문제의 본질이다.

**측정값** (10라운드 교차, 세 방식 결과 해시가 동일함을 먼저 검증)

| 방식 | 조인 | buffers | min | median |
|---|---|---|---|---|
| ① 원본 | 3 | 500,750 | 400.3 ms | 418.1 ms |
| ③ §T-8 최선 | 3 | 349,914 | 310.3 ms | 324.7 ms |
| ④ 반정규화(필터 끌어올림) | **0** | **6,169** | **51.0 ms** | **53.4 ms** |
| ⑤ 사전 집계 MV | 0 | **12** | **0.1 ms** | **0.1 ms** |

③→④ 만으로 buffers 57배, 시간 6배. 세 필터가 하나의 `Index Cond` 로 합쳐지고 조인이 사라진다.

**대가도 함께 쟀다 (이게 없으면 반쪽짜리 결론이다)**

| 항목 | ④ 반정규화 | ⑤ MV |
|---|---|---|
| 저장 | 289MB (원본에 컬럼 3개만 추가 시 63MB) | 512 kB |
| 갱신 | 고객 1건 변경 시 **40행** 전파, 28.5 → **404.8 ms (14배)** | `REFRESH` 343 ms |
| 적용 범위 | 필터 **조합**이면 재사용 | **이 쿼리·이 파라미터 전용** |

⑤가 0.1ms 인 건 답을 미리 적어둔 것이라 그렇다. MV 정의에 `o_orderdate < '1995-03-15'` 가
박혀 있어 **날짜나 세그먼트가 바뀌면 못 쓴다** — 조회 조건이 자유로운 화면에는 성립하지 않는다.

**여기서 얻은 것**: §T-8이 "접근 경로를 최적화하라"였다면 §T-9는
**"접근 경로로 못 가는 지점이 있고 거기서는 문제의 형태를 바꿔야 한다"** 이다.
단 순서를 지켜야 한다 — 인덱스로 되는 것을 반정규화로 풀면 **쓰기 14배를 내고 몇 ms 를 사는**
나쁜 거래다. Tow 가 반정규화를 책 맨 마지막에 "다른 방법이 없을 때만"으로 못박은 이유.

**반복 쿼리 통합**: 서버 내부 루프 1,000회(5.7ms) vs `IN` 1회(2.8ms) 는 2배 차이지만,
실제 애플리케이션 형태인 **클라이언트 왕복** 1,000회는 255ms vs 66ms 로
**왕복 1회당 약 0.18ms × 999회 ≈ 180ms** 가 순수 오버헤드다(원격이면 5배 → §M-9).

### M-8 — 책의 "LIO 7,000 → 7" 재현

인덱스 없음 15,427 buffers → 인덱스 있음 **10 buffers** (1,540배 감소).

## 5. 문서에서 정정한 잘못된 서술

측정 과정에서 **내가 처음에 쓴 내용 중 6건이 사실과 달랐고 모두 정정**했다.
기록으로 남기는 이유는, 같은 함정을 다시 밟지 않기 위해서다.

1. **"q09에서 NL 강제 시 참혹해진다"** → 실제로는 NL이 4.6배 빨랐다.
   NL이 무너지는 조건은 필터 폭이 아니라 **안쪽 조인키 인덱스의 부재**(있으면 216ms, 없으면 60초 초과).
2. **`join_collapse_limit=1`로 콤마 조인 순서 강제** → 효과 없음. 명시적 `JOIN ... ON` 구문이라야 적용된다.
3. **"statistics_target을 올리면 오차가 준다"** → 균일 분포에서는 전혀 줄지 않는다
   (target 1~1000에서 추정 8,319/8,696/10,204/8,280, 실제 9,015). 치우친 데이터에서만 의미 있다.
4. **"`extract()`를 쓰면 Parallel Seq Scan이 된다"** → VACUUM된 테이블에서는 Index Only Scan + Filter.
   출력을 3줄만 잘라 보고 단정한 실수였다.
5. **"customer 드라이빙(휴리스틱)이 항상 빠르다"** → 장비에 따라 반대.
6. **T-8에서 "커버링 인덱스가 결합 인덱스보다 확실히 낫다"** → 조건별로 나눠 batch 측정했을 때
   나온 착시였다(커버링 284ms vs Hash 310ms). **같은 라운드 안에서 교차 측정하니 사실상 동률**
   (②313 / ③293 min, median은 331 / 334로 역전). 시간대 드리프트가 조건 간 차이보다 컸다.
   → §T-0에 "비교할 조건은 교차(interleave)해서 재라"를 원칙으로 추가할 것.

**교훈**: 2003년 책의 규칙은 출발점이지 결론이 아니다.
Tow가 3단계 중 세 번째("어떤 계획이 최선인지 판단")를 가장 중요하다고 한 이유이며,
그래서 §T-0(측정 위생)이 문서 맨 앞에 있다.

## 6. 측정 위생 (§T-0) — 가장 중요한 절

1. **한 번에 한 변수만.** `index`는 인덱스+ANALYZE를 함께 하므로 `analyze`로 분리한다.
2. **단발 EXPLAIN ANALYZE를 성능 지표로 쓰지 않는다.** 세션 최초 JIT은 유독 비싸다.
3. **JIT이 결과를 지배하는지 확인한다.** `JIT: Total`을 `Execution Time`과 비교.
4. **캐시 상태를 의식한다.** `--warmup` 옵션과 `Buffers: read` 확인.
5. **VACUUM 여부가 계획을 바꾼다.** `relallvisible` 확인.
6. **비교할 조건들은 교차(interleave)해서 잰다.** 조건 A를 10회, 그다음 조건 B를 10회 재는
   batch 방식은 그 사이의 시간대 드리프트를 조건 차이로 착각하게 만든다.
   한 라운드 안에서 A→B→(A→B)… 로 번갈아 재고, 라운드를 반복한다.

실제로 이 원칙을 어겨 오판한 사례가 세션 중 세 번 있었다 —
인덱스 생성 직후 단발 측정에서 C가 B보다 느리게 나왔다가(캐시 미충전) 반복 측정에서 뒤집혔고,
`extract()` 계획을 3줄만 보고 잘못 단정했으며,
**T-8에서 batch 측정으로 커버링 인덱스가 이긴 것처럼 보였다가 교차 측정에서 동률로 밝혀졌다**(원칙 6).
