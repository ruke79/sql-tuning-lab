## 2. 검증 방식

이 프로젝트의 모든 수치는 **실제 PostgreSQL 16을 띄워 측정**했다(SF=0.5, lineitem 300만 행).
문서의 SQL 블록 31개는 전부 파싱 검증했고, gradle 명령 참조는 소스와 대조했다.

한계: **ClickHouse는 실행 검증하지 못했다**(환경 제약). 명령 형태는 compose 설정 및
기존 스크립트와 대조만 했다.

## 3. 해결한 문제 (시간순)

| 문제 | 원인 | 조치 |
|---|---|---|
| `column "r_regionkey" is of type integer but expression is of type character varying` | `setString()`이 파라미터를 varchar로 확정 → PG가 캐스팅 거부 | PG는 `Types.OTHER`(Oid 미지정)로 바인딩 |
| `store_sales_pkey ... is duplicated` | 생성기가 한 영수증에 같은 상품 중복 생성 | 영수증별 상품 중복 제거 |
| `multiple definition of 'nItemIndex'` (dsdgen) | GCC 10+ 기본값 `-fno-common` | 컨테이너에 `-fcommon` 주입 gcc 래퍼 |
| 실습이 변수 2개를 동시에 변경 | `index` 명령이 인덱스+ANALYZE를 함께 수행 | `analyze` / `vacuum` 명령 신설, §T-1을 4지점 실험으로 재설계 |
| 문서에 `SELECT ...` 플레이스홀더 5곳 | 실행 불가 | 전부 완전한 SQL로 교체 |
| 스크립트가 멈춤 | 인덱스 없이 NL 강제 → 반복 풀스캔 | `statement_timeout` 가드 + 인덱스 누락 사전 경고 |
| 40줄 스택 트레이스 | 테이블 미생성 상태로 실행 | `SchemaCheck` — 준비 상태 점검 후 할 일 안내 |
| ClickHouse 접속법 부재 | 문서에 PG/MySQL만 있었음 | §0-1 세 DB 접속, §0-2 ClickHouse 용어 대응표 |

## 4. 실측으로 확인된 결과 (이 프로젝트의 핵심 자산)

### T-1 — 통계가 인덱스보다 중요했다

| 지점 | 상태 | 중앙값 | 조인 방식 |
|---|---|---|---|
| A | 통계✗ 인덱스✗ | 1,296 ms | Merge Join |
| D | A + `jit=off` | 734 ms | 〃 |
| B | 통계✓ 인덱스✗ | 375 ms | Parallel Hash Join |
| C | 통계✓ 인덱스✓ | 215 ms | Nested Loop + Index |

전체 개선 중 **통계 921ms(85%), 인덱스 160ms(15%)**.
A의 추정 오차는 7,461배(113,139,667 vs 15,164)였고, 부풀려진 비용이 JIT 임계값을 넘겨
A 시간의 43%(562ms)를 컴파일에 소모했다. **나쁜 통계 → 나쁜 계획 → 불필요한 JIT** 연쇄.

### T-2 — 전환점과 클러스터링

- 풀스캔 전환점 **22.6~25.2%** (책의 20% 기준과 근접)
- `l_shipdate` correlation ≈ 0 → plain Index Scan은 0.043%뿐, 0.1~22%는 **Bitmap Heap Scan**이 지배
- **진짜 교차점은 15~22%인데 옵티마이저는 22~25%에서 전환** → 그 구간에서 13% 손해
- 선택도 7.55%에 이미 페이지의 74.5%를 읽음(초선형)

**CLUSTER 실험 (제로섬)**

| | CLUSTER 전 | 후 |
|---|---|---|
| l_shipdate correlation | -0.005 | **1.000** |
| l_orderkey correlation | **1.000** | 0.004 |
| shipdate 범위 쿼리 | 226.6 ms | **73.1 ms** (3.1배 개선) |
| orderkey 조인(q03) | 225.8 ms | **273.6 ms** (1.21배 악화) |

물리 순서는 하나뿐 → 클러스터링은 공짜가 아니라 **접근 경로 선택**이다.

### T-3 / T-5 — 승자가 장비에 따라 갈린다

같은 데이터(고정 시드로 행수 동일), 같은 PG 버전인데 결론이 반대다.

| q03 | buffers | 장비 A | 장비 B |
|---|---|---|---|
| Nested Loop (옵티마이저 선택) | 500,750 | **216 ms** | 234 ms |
| Hash Join | 77,016 | 429 ms | **144 ms** |

장비 B에서는 **옵티마이저가 틀렸다**(1.6배 손해). q05도 1.35배 손해.
조인 순서(§T-5)도 마찬가지 — "나쁜 순서"라 이름 붙인 lineitem 드라이빙이 장비 B에선 1.21배 빨랐다.

**q09는 LIO의 한계를 보여준다**: NL 92,249 buffers 36.4ms vs Hash 86,593 buffers 166.3ms.
버퍼는 거의 같은데 시간은 4.6배 — `buffers`는 해시 테이블 구축 CPU를 세지 않기 때문.

### T-4 — 인덱스 무력화의 실제 모습

계획에 인덱스 이름이 보여도 소용없다. **`Index Cond`냐 `Filter`냐**가 기준이다.

| | 조건 위치 | buffers | 시간 |
|---|---|---|---|
| 범위 비교 | **Index Cond** | 102 | 14.2 ms |
| `extract(year ...)` | **Filter** | 640 | 83 ms (워커 4개) |

같은 인덱스·같은 결과 행수인데 6배 느리다. 추정도 23배 빗나간다(표현식엔 통계가 없음).
`c_custkey + 0`, `::text` 형변환도 동일하게 인덱스를 죽이며 추정이 1 → 375로 망가진다.

**VACUUM 여부가 계획을 바꾼다**: 적재 직후 Parallel Seq Scan(13,656 buffers, 121ms)
→ VACUUM 후 Parallel Index Only Scan(640 buffers, 83ms).

### T-8 — 결합 인덱스로 조인 방식 판정이 뒤집혔다

§T-5에서 지목한 지점(lineitem probe 한 노드가 전체 LIO의 60%)을 실제로 공략했다.
`l_shipdate`가 `Filter` → `Index Cond`로 올라가고 `Rows Removed by Filter`가 사라진다.

| 조건 | probe buffers | 총 buffers | min | median |
|---|---|---|---|---|
| ① NL, 결합 인덱스 없음 | 301,369 | 500,750 | 407.2 ms | 433.3 ms |
| ② NL + 결합 인덱스 | **228,320** | 427,701 | **313.0 ms** | **330.6 ms** |
| ③ NL + 커버링 인덱스(INCLUDE) | 224,993 | 424,389 | 292.8 ms | 333.7 ms |
| ④ Hash | — | 77,016 | 321.9 ms | 360.6 ms |

**①에서 Hash에 졌던 NL이 ②에서 역전한다(313 vs 322).** §T-3·§T-5에서 "이 장비는 Hash가 낫다"고
판정났던 q03의 결론이 인덱스 하나로 뒤집혔다 — 조인 방식의 우열은 고정된 성질이 아니라
**쓸 수 있는 접근 경로의 함수**다.

**절감분은 전부 힙 접근에서 나오고 거기서 멈춘다.** 줄어든 73,049 buffers는 전부 probe 노드 몫인데,
③으로 힙 접근을 0(`Heap Fetches: 0`)으로 만들어도 3,327밖에 더 안 준다.
남은 224,993은 **74,024번의 B-tree 하강 자체**(74,024 × 약 3 buffers ≈ 222,000에 수렴)이고 이것이 NL의 하한이다.
인덱스는 90MB → 135MB로 1.5배 커지므로 **②에서 멈추는 것이 옳다.**

### T-8 이어서 — orders probe: 만들어도 옵티마이저가 안 쓴다

②를 적용하면 병목이 옮겨간다. lineitem 이 228,320 으로 줄면서 **orders probe 가 197,553 으로
전체의 46%** 가 된다. 노드 모양이 §T-8 도입부와 똑같다(`Index Cond`=조인키, `Filter`=날짜,
`Rows Removed by Filter: 5`). probe 당 약 13 buffers(3 하강 + 10 힙)로 **힙 낭비율이 50%** 다.

같은 처방 `CREATE INDEX ON orders (o_custkey, o_orderdate)` 를 적용했더니 —
**옵티마이저가 무시하고 계속 좁은 `idx_orders_custkey` 를 골랐다.**

| 인덱스 | 크기 | 추정 비용 |
|---|---|---|
| `(o_custkey)` | 6,816 kB | `0.42..1.70` ← 선택됨 |
| `(o_custkey, o_orderdate)` | 23 MB | `0.42..1.73` |

차이가 1.8% 뿐이다. `o_orderdate < '1995-03-15'` 선택도가 **48.7%** 로 약한 데다,
`random_page_cost=1.1` 에서는 힙 접근이 거의 공짜로 계상돼 **절약분이 비용 모델에 안 잡힌다.**
`random_page_cost` 를 올려도 소용없다 — 1.5 이상에서는 결합 인덱스로 가는 게 아니라
**NL 을 포기하고 Hash Join 으로 계획이 통째로 바뀐다.**

**좁은 인덱스를 지워야 쓰인다** (`(A)` 는 `(A,B)` 의 선행 부분집합이라 기능적으로 중복).

| 단계 | orders probe | lineitem probe | 총 buffers | min | median |
|---|---|---|---|---|---|
| ① 원본 | 197,553 | 301,369 | 500,750 | 400.3 ms | 418.1 ms |
| ② + lineitem 결합 | 197,553 | 228,320 | 427,701 | 287.8 ms | 332.1 ms |
| ③ + orders 결합(좁은 것 제거) | **119,766** | 228,320 | **349,914** | **267.5 ms** | **291.4 ms** |

①→③ 총 buffers 30.1% 감소, median 30.3% 단축. 별도 교차 측정(n=36)에서도
좁은 인덱스 대비 결합 인덱스가 min 251.0/median 290.8 vs 285.4/315.5 로 일관되게 빨랐다.

**여기서 얻은 두 가지**

1. **인덱스를 만드는 것과 옵티마이저가 쓰는 것은 별개다.** `(A)` 와 `(A,B)` 가 공존하면
   PostgreSQL 은 더 작다는 이유로 좁은 쪽을 계속 고른다. 넓은 것을 만들었으면
   **좁은 것을 반드시 지워야** 한다. 안 지우면 디스크만 더 쓰고 계획은 그대로다.
2. **이번엔 비용 모델이 절약분을 과소평가했다.** §T-3에서는 `buffers` 만 보면 틀린다고 했는데
   (Hash 가 buffers 적지만 느림), 여기선 정반대로 76,000회의 힙 접근 절약을 0.03 으로 계상했다.
   **`buffers` 도 추정 비용도 단독으로는 못 믿고, 실측만이 판정한다.**

### T-9 — 인덱스가 못 넘는 벽을 모델 변경으로 넘는다

§T-8 이 lineitem probe 228,320 에서 멈춘 지점(74,024회 B-tree 하강이 하한)에서 이어진다.

**문제 정량화.** q03 의 필터는 3개 테이블에 흩어져 있다(선택도 0.2024 / 0.4866 / 0.5384).
독립 가정으로 곱하면 149,646 행이 나와야 하는데 **실제는 15,164 행** — `o_orderdate` 와
`l_shipdate` 가 상관되어(주문 후 배송) 결합 선택도가 10배 강하다(Tow 2장 *filter redundancy*).
최종적으로 300만 행 중 **0.505%** 만 필요한데, 필터가 흩어져 그 조합에 도달하려면
이미 큰 테이블을 다 헤집은 뒤여야 한다는 것이 문제의 본질이다.

**측정값** (10라운드 교차, 세 방식 결과 해시가 동일함을 먼저 검증)

| 방식 | 조인 | buffers | min | median |
|---|---|---|---|---|
| ① 원본 | 3 | 500,750 | 400.3 ms | 418.1 ms |
| ③ §T-8 최선 | 3 | 349,914 | 310.3 ms | 324.7 ms |
| ④ 반정규화(필터 끌어올림) | **0** | **6,169** | **51.0 ms** | **53.4 ms** |
| ⑤ 사전 집계 MV | 0 | **12** | **0.1 ms** | **0.1 ms** |

③→④ 만으로 buffers 57배, 시간 6배. 세 필터가 하나의 `Index Cond` 로 합쳐지고 조인이 사라진다.

**대가도 함께 쟀다 (이게 없으면 반쪽짜리 결론이다)**

| 항목 | ④ 반정규화 | ⑤ MV |
|---|---|---|
| 저장 | 289MB (원본에 컬럼 3개만 추가 시 63MB) | 512 kB |
| 갱신 | 고객 1건 변경 시 **40행** 전파, 28.5 → **404.8 ms (14배)** | `REFRESH` 343 ms |
| 적용 범위 | 필터 **조합**이면 재사용 | **이 쿼리·이 파라미터 전용** |

⑤가 0.1ms 인 건 답을 미리 적어둔 것이라 그렇다. MV 정의에 `o_orderdate < '1995-03-15'` 가
박혀 있어 **날짜나 세그먼트가 바뀌면 못 쓴다** — 조회 조건이 자유로운 화면에는 성립하지 않는다.

**여기서 얻은 것**: §T-8이 "접근 경로를 최적화하라"였다면 §T-9는
**"접근 경로로 못 가는 지점이 있고 거기서는 문제의 형태를 바꿔야 한다"** 이다.
단 순서를 지켜야 한다 — 인덱스로 되는 것을 반정규화로 풀면 **쓰기 14배를 내고 몇 ms 를 사는**
나쁜 거래다. Tow 가 반정규화를 책 맨 마지막에 "다른 방법이 없을 때만"으로 못박은 이유.

**반복 쿼리 통합**: 서버 내부 루프 1,000회(5.7ms) vs `IN` 1회(2.8ms) 는 2배 차이지만,
실제 애플리케이션 형태인 **클라이언트 왕복** 1,000회는 255ms vs 66ms 로
**왕복 1회당 약 0.18ms × 999회 ≈ 180ms** 가 순수 오버헤드다(원격이면 5배 → §M-9).

### T-9 이어서 — 트리거 동기화의 실제 오버헤드

위 ④의 전파 비용은 수동 UPDATE 로 잰 것이었다. Tow 의 전제("엄밀한 트리거로 자동 동기화하면
기능적으로 안전하다")를 실제 구현해서 확인했다.

**먼저 ④의 설계 결함을 고쳤다.** `lineitem_denorm` 에 `l_linenumber` 가 없어 행을 특정할 수
없었다 — 조회 전용이면 무관하지만 **동기화가 불가능하다.** 반정규화 테이블에는 원본 키를
반드시 함께 가져와야 한다.

**오버헤드** (단일 세션 `\timing`, 6라운드 교차, 최소값)

| 작업 | 팬아웃 | 트리거 OFF | 트리거 ON | 배수 |
|---|---|---|---|---|
| `customer` 1행 UPDATE | 38행 | 0.153 ms | 0.223 ms | **1.5배** |
| `orders` 1행 UPDATE | 4행 | 0.291 ms | 0.806 ms | **2.8배** |
| `lineitem` 1행 UPDATE | 1행 | 0.348 ms | 1.098 ms | **3.2배** |
| `lineitem` DELETE (1주문) | 4행 | 0.140 ms | 0.315 ms | 2.2배 |
| `lineitem` INSERT 약 1,200행 | 1,200행 | 14.267 ms | 34.775 ms | 2.4배 |

> 배수는 실행마다 흔들린다(3라운드 재실행 시 `orders` 3.7배 / `lineitem` UPDATE 4.0배).
> **재현되는 것은 절대 배수가 아니라 순서**다 — customer < DELETE < orders < lineitem UPDATE.

**핵심 발견 — 비용은 팬아웃이 아니라 "위를 되짚어야 하는가"가 결정한다.**
38행을 고치는 `customer` UPDATE 가 **가장 싸고(1.5배)**, 1행만 고치는 `lineitem` UPDATE 가
**가장 비싸다(3.2배)**. 전자는 트리거 1회 발화 + 집합 UPDATE 1회로 끝나는데,
후자는 상속 컬럼을 채우려고 **매번 orders·customer 를 거슬러 올라가 다시 조회**하기 때문이다.
→ 반정규화의 쓰기 비용을 추정할 때 팬아웃만 보면 틀린다.

**드리프트 검사**: 커밋 워크로드(등급 50건, 주문일 200건, 배송일, DELETE 21주문, INSERT 51주문)
이후 원본과 대조 — 3,000,583행 일치, **누락 0 / 유령행 0**.
단, **이것은 단일 세션 결과다.** 아래 동시성 항목에서 이 결론이 뒤집힌다.

### T-9 동시성 — 단일 세션 결론이 뒤집혔다

`pgbench` 8 클라이언트 / 20초, 좁은 키 범위에 집중시켜 경합을 최대화했다.

| 조건 | tps | 평균 지연 | 데드락 | 무작위 워크로드 후 드리프트 |
|---|---|---|---|---|
| A. 트리거 OFF | 5,702 | 2.03 ms | 0 | — |
| B. 트리거 ON (소박한 구현) | 3,562 | 3.02 ms | 0 | 0 |
| C. 트리거 ON + `FOR SHARE` | 3,593 | 2.87 ms | 0 | 0 |

동시 쓰기 처리량은 **약 1.4~1.5배 비용**, 데드락은 없었다.

**그런데 B의 "드리프트 0" 은 안전하다는 증명이 아니었다.** 워크로드가 `cust`/`ord` 를 독립적으로
뽑아서 "T2가 고른 주문이 하필 T1이 지금 고치는 고객의 것"인 경우가 안 생겼을 뿐이다.
겨냥해서 만들면 **드리프트가 재현된다**:

```
A: BEGIN; UPDATE customer ... WHERE c_custkey=1;   (미커밋, 트리거가 기존 행들 갱신)
B:        INSERT INTO lineitem (고객 1의 주문에 새 행);   (트리거가 옛 값을 읽음)
A: COMMIT;                                          → denorm 에 옛 등급이 박힘
```

A의 갱신은 아직 없던 행을 지나쳤고, B는 아직 안 보이는 새 값을 읽었다. 둘 다 자기
트랜잭션 안에서는 옳았는데 결과가 어긋난다 — `READ COMMITTED` 의 전형적 함정.

**수정**: lineitem 트리거가 상위 행을 `FOR SHARE OF o, c` 로 **잠그고 읽게** 한다.
같은 겨냥 실험에서 드리프트가 사라졌고, 처리량 손해도 측정 편차 범위였다.
(단 B/C는 `FOR SHARE` 외에 구현도 달라져서, 둘의 tps 차를 `FOR SHARE` 효과로만 읽으면 안 된다.)

**핵심 교훈**: 파생 데이터의 정합성은 **단일 세션 테스트로 보증되지 않고, 무작위 부하
테스트로도 드러나지 않는다.** "이 두 트랜잭션이 겹치면 어떻게 되는가"를 손으로 따져야 한다.
→ 반정규화 비용 항목에 **설계 난이도**가 하나 더 붙는다.

### T-9 동시성 이어서 — orders / customer 경로도 같은 병을 앓았다

위에서 고친 건 `sync_li` 하나뿐이었다. "잠그지 않고 상위를 읽는" 지점을 전부 세니 셋이었고,
겹침 후보를 손으로 열거해 검증했다(같은 행을 만져 행 락이 직렬화할 H4·H5는 실험 제외).

| # | 시나리오 | 결과 |
|---|---|---|
| **H1** | 고객 등급변경 ∥ 주문을 **그 고객으로 이동** | **드리프트** (`MACHINERY` vs `H1NEW`) |
| **H2** | 고객 등급변경 ∥ 주문을 **그 고객에서 빼냄** | 안전 |
| **H2'** | 위와 **순서만 뒤집음** | **드리프트** (`H2REV` vs `MACHINERY`) |
| **H3** | 주문 날짜변경 ∥ 그 주문에 lineitem INSERT | **드리프트** (`1998-06-06` vs `2001-09-09`, 수동 3/3) |

> **H3 는 스크립트에서 재현이 안 된다.** 두 psql 세션으로 수동 실행하면 3/3 재현되지만
> `t9-concurrency.sh` 안에서는 `drift=f` 로 나온다 — B 가 A 의 UPDATE 보다 먼저 들어가면
> A 의 전파가 B 의 새 행까지 덮어 드리프트가 사라지는데, 스크립트 신호로는 그 창을
> 안정적으로 못 맞춘다. 자동 검증은 H1·H2' 로 하고 H3 수동 절차는 스크립트 주석에 남겼다.
> **재현이 어렵다는 것이 안전하다는 뜻이 아니라는 점**이 이 해저드의 위험성이다.

**H2 vs H2' 가 이 실습의 핵심이다.** 같은 두 트랜잭션인데 **순서만 뒤집으니 한쪽만 깨진다.**

- H2(안전): A가 denorm 행을 먼저 잡고 락을 쥐어서 B가 **막힌다** → 뒤에 쓴 B가 옳은 값을 쓴다
- H2'(위험): B가 먼저 락을 쥐고 A가 **나중에** 덮어쓰는데, A가 쓰는 값은 이미 떠난 주문의 것
- H1(위험): 아예 **경합이 없다.** A의 subquery 가 "아직 내 고객 것이 아닌" 주문을 대상에서
  빼버리므로 직렬화해 줄 락이 생기지 않는다

> **판별법**: 두 트랜잭션이 **같은 denorm 행에서 경합하면** DB가 직렬화해 주지만,
> **한쪽이 그 행을 "내 대상이 아니다"라고 건너뛰면** 아무도 직렬화해 주지 않는다.
> → 트리거 검토 시 **"이 갱신이 놓치는 행은 무엇인가"** 를 물어야 한다.

**수정**: `sync_ord` 는 customer 를 `FOR SHARE` 로, `sync_cust` 는 대상 주문 목록을
`FOR SHARE` 로 잠그고 읽게 했다. 세 시나리오 모두 드리프트 소멸.

**대가** (8 clients / 20초)

| 구현 | tps | 지연 | 데드락 | 드리프트 |
|---|---|---|---|---|
| 트리거 OFF | 5,702 | 2.03 ms | 0 | — |
| 소박한 구현 | 3,562 | 3.02 ms | 0 | 0 (겨냥하면 발생) |
| `sync_li` 만 수정 | 3,593 | 2.87 ms | 0 | 0 (H1·H2' 잔존) |
| **3경로 전부 수정** | **3,297** | **3.65 ms** | **0** | **0** |

정합성을 끝까지 지키면 **약 1.8배 비용**(5,702 → 3,297)이고, `sync_li` 만 고친 상태보다
21% 더 느리다 — 나머지 두 경로의 락이 공짜가 아니다. 데드락은 어느 구성에서도 없었다.

### T-9 동시성 마무리 — `FOR SHARE` 락 범위는 워크로드가 결정한다

`sync_cust` 가 고객의 주문 전체를 잠그는 것이 대형 계정에서 문제가 되는지 확인했다.
TPC-H 자연 분포는 고객당 평균 10 / 최대 25건이라 편중이 없어, 주문을 한 고객에 몰아 만들었다.

**① 단일 세션에서도 공짜는 아니다.** 잠그는 행이 1,000건을 넘으면 **1.42~1.45배**가 붙는다
(5,000행에서 153.6 → 222.9ms, **+69ms**). 처음엔 "0.96~1.17배, 사실상 공짜"로 적었는데
재측정에서 뒤집혔다(정정 목록 12번). 다만 이 +69ms 는 아래 ②의 +2,677ms 에 비하면 작다 —
**지배적인 건 락 획득 비용이 아니라 락을 기다리는 쪽**이라는 방향은 그대로다.

**② 비용의 대부분은 경합에서 나온다.** 고객1이 5,000건을 가진 상태에서 그중 한 주문을
다른 세션이 건드리면 **58ms → 2,735ms (약 47배)**. 등급과 무관한 트랜잭션이 통째로 막힌다.

**③ 대기 길이는 고객 크기에 비례하지 않는다.** 100/1,000/5,000 어디서나 약 2.5초 —
대기는 앞선 트랜잭션이 열려 있는 시간으로 정해진다. **크기가 키우는 건 "막히는 범위"** 다.

**④ 그래서 처리량 손해는 적중률을 따라간다** (워크로드 키 범위 1~5,000 고정, 소유 비율만 변경)

| 고객1 주문수 | 적중률 | naive tps | `FOR SHARE` tps | 손해 |
|---|---|---|---|---|
| 50 | 1% | 7,691 | 8,093 | 0.95배 (편차) |
| 500 | 10% | 391 | 390 | 1.00배 |
| 5,000 | 100% | 67.8 | 27.5 | **2.47배** |

균일 워크로드에서 1.27배였던 손해가 대형 고객 편중에서 **2.47배**가 된다.
그런데 배수보다 중요한 건 **naive 열의 절대값**이다 — 7,691 → 391 → 67.8.
**락을 아예 안 써도 1%→10% 구간에서 이미 20배가 무너진다.** 편중의 주범은 락이 아니라
팬아웃 자체이고, `FOR SHARE` 는 이미 무너진 것을 2.5배 더 무너뜨릴 뿐이다.

**결론**: 정합성 락의 비용은 "무엇을 잠그느냐"가 아니라 **"누가 그걸 건드리느냐"** 다.
같은 `FOR SHARE` 가 어떤 서비스에선 공짜이고 어떤 서비스에선 처리량을 반 토막 낸다.
판단 기준은 락 범위의 크기가 아니라 **그 범위가 실제 쓰기 트래픽과 겹치는 비율**이고,
이건 스키마가 아니라 워크로드를 봐야 안다.
→ 대형 계정에 쓰기가 몰리는 시스템이라면 행 락 대신 **변경 큐 + 비동기 전파 + 정합성 배치**를
검토하거나, 애초에 그 컬럼을 반정규화하지 않는 쪽을 봐야 한다.

**그래서 최종 손익**: 조회 324.7 → 53.4ms(6배)를 얻고, **모든 쓰기에 1.5~3.2배**를
조회가 있든 없든 **영구히** 지불한다. 읽기 편중 + 잦은 조회 + §T-8로 안 되는 경우,
셋을 모두 만족할 때만 성립하는 거래다.

### T-9 대안 전략 — 변경 큐 + 비동기 전파는 무엇을 사고 무엇을 파는가

앞 절의 결론이 가리킨 대안을 실제로 구현해 동기 트리거와 같은 조건에서 비교했다
(`scripts/tpch/t9-change-queue.sh`, 8 clients / 15초 / 4 CPU).

**큐 설계에서 정합성을 만드는 것은 두 가지 성질이다.**
1. 큐에 **값이 아니라 키만** 넣는다. 워커가 적용 시점에 진실을 다시 읽는다
   → 멱등하고 순서에 무관하다. 같은 키를 열 번 처리해도 결과가 같다.
2. 원본 변경과 큐 INSERT 가 **같은 트랜잭션에서 커밋**된다
   → 워커가 큐 항목을 볼 수 있다는 것은 그 변경도 이미 볼 수 있다는 뜻이다.
   그래서 워커는 낡은 값을 읽을 수 없다. **경쟁이 지연으로 바뀐다.**

**① 쓰기 경로 지연** (고객 등급 1건 변경, 5회 최소값)

| 고객1 주문수 | denorm 행 | 동기 naive | 동기 `FOR SHARE` | 큐 | 큐/naive |
|---|---|---|---|---|---|
| 10 | 68 | 4.4ms | 4.4ms | 2.4ms | 0.55배 |
| 100 | 450 | 6.9ms | 7.8ms | 2.5ms | 0.36배 |
| 1,000 | 3,992 | 32.7ms | 43.7ms | 2.3ms | 0.07배 |
| 5,000 | 20,113 | 147.7ms | 222.3ms | 2.3ms | **0.02배** |

동기 트리거는 팬아웃에 비례해 커지고, 큐는 행 1개 INSERT 라 **크기와 무관하게 2.3ms 상수**다.
단 이 시점에 파생 테이블은 아직 안 고쳐졌다 — 일이 사라진 게 아니라 미뤄졌을 뿐이다.

**② 피해 반경** (5,000주문 고객의 등급 변경 트랜잭션이 열려 있는 동안, 무관한 `UPDATE orders`)

| 동기 naive | 동기 `FOR SHARE` | 큐 |
|---|---|---|
| 2,712ms | 2,863ms | **735ms** |

여기서 알게 된 것: **`FOR SHARE` 를 안 써도 대형 고객에서는 어차피 막힌다.**
naive 도 `lineitem_denorm` 2만 행을 갱신하며 행 락을 잡고, 그게 `sync_ord` 경로와 겹치기 때문이다.
락 회피는 `FOR SHARE` 를 빼서 되는 게 아니라 **경로 자체를 옮겨야** 된다.
큐도 0은 아니다(735ms) — 큐 테이블과 공용 자원의 경합이 남는다. 그래도 한 자릿수 배 차이다.

**③ 처리량 — 자연 분포에서는 큐가 안 이긴다**

| 구성 | ③-a 자연 분포 tps | 대비 | ③-b 편중 tps | 대비 |
|---|---|---|---|---|
| A. 트리거 없음(정합성 포기) | 4,932 | 1.00배 | 6,073 | 1.00배 |
| B. 동기 naive | 3,521 | 1.40배 | 48.8 | **124배** |
| C. 동기 `FOR SHARE` | 3,225 | 1.53배 | 24.4 | **249배** |
| D. 큐 (워커 OFF) | 4,660 | 1.06배 | 6,268 | 0.97배 |
| E. 큐 (워커 ON) | 3,308 | 1.49배 | **4,051** | 1.50배 |

이 표가 이 실습의 핵심이다.
- **자연 분포에서 E(3,308)와 C(3,225)는 사실상 같다.** 큐는 처리량을 사주지 않는다.
  같은 일을 하는 데 드는 총 비용은 같기 때문이다. 큐가 사주는 건 **쓰기 지연(①)과 피해 반경(②)**이다.
- **편중이 생기면 갈린다.** 동기는 124~249배로 무너지고 큐는 1.50배를 유지한다
  (E는 C 대비 **166배**). 무너지는 이유는 락 자체가 아니라 **모든 트랜잭션이
  20만 행짜리 전파 트랜잭션 뒤에 줄을 서기** 때문이고, 큐는 그 줄서기를 없앤다.
- **D(워커 OFF)는 시스템 처리량이 아니다.** 애플리케이션 체감 지연만 보여준다.
  드리프트가 남아 있는 건 "틀렸다"가 아니라 "아직 안 됐다"이다. 비교해야 할 값은 E다.

> ⚠️ 앞 절(락 범위)의 "편중 시 2.21배"와 여기 "249배"는 모순이 아니라 **구성이 다르다**.
> 락 범위 실험은 `sync_cust` **한 경로만** 설치했고, 여기는 3경로를 모두 설치했다.
> `sync_ord` 가 `customer` 행을 `FOR SHARE` 로 읽으므로, 주문 갱신 전부가 등급 변경 뒤에 줄을 선다.
> **경로를 하나 더 붙이는 것만으로 손해가 2배에서 249배가 됐다** — 반정규화 유지 비용은
> 경로 수에 선형이 아니라 경로 간 상호작용에 지배된다.

**④ 미뤄진 일은 어디로 갔나** (편중 워크로드, 워커 ON)

| 배치 수 | 큐 항목 | 실작업 키 | 합침 절감 | 평균 지연 | 최대 지연 |
|---|---|---|---|---|---|
| 99 | 97,347 | 90,748 | 6.8% | **4,424ms** | **6,652ms** |

부하 종료 시점 큐 잔량 37,253건 → 소진까지 5,184ms. 최종 드리프트 0.
**지연창이 4~7초**라는 것이 큐가 판 대가다. 합침 절감이 6.8%로 낮은 건 항목 수 기준이기 때문이고
(ord/line 키는 대부분 서로 다르다), 실제 절감은 cust 경로에 몰려 있다 —
한 배치의 cust 항목 수십 건이 배열 원소 1개로 접혀 2만 행짜리 UPDATE 를 한 번만 돌게 만든다.

**⑤ 정합성** — `t9-concurrency.sh` 가 잡아낸 H1 경쟁을 큐에서 재현했다.
전파 전 드리프트 40,226 → `denorm_drain` 2회 후 **0**. 위의 성질 2 때문에 워커는
낡은 값을 읽을 수 없고, 동기 naive 의 **정합성 문제가 큐에서는 가시성 문제**가 된다.

**⑥ 워커가 죽으면 드리프트는 무한정 남는다.** 큐 유실을 시뮬레이션하니 44,070건이 영구히 어긋났다.
전량 대사(reconciliation)로 복구되며 **300만 행 풀스캔 3,262ms**. 큐를 쓴다는 것은
이 배치를 상시 운영한다는 뜻이다 — 큐는 대사 배치를 **대체하지 않고 요구한다.**

**결론 10**: 큐는 비용을 없애지 않는다. **임계 경로 밖으로 옮기고 배치로 합칠 뿐이다.**
- 산 것: 쓰기 지연의 상수화, 피해 반경 축소, 편중 하에서의 처리량 유지
- 판 것: 4~7초의 지연창, 큐/워커라는 운영 대상, 상시 대사 배치,
  그리고 **"읽는 쪽이 낡은 값을 견딜 수 있는가"라는 새 요구사항**
- 팬아웃 자체가 감당 불가면 큐도 못 구한다. 처리량 대신 **지연이 무한정 늘 뿐이다.**

→ 실무 판단 기준은 "정합성이 중요한가"가 아니라 **"읽는 쪽의 지연 예산이 얼마인가"** 다.
지연 예산이 0이면 `FOR SHARE`(그리고 편중을 감당할 것), 초 단위를 견디면 큐,
어느 쪽도 감당 못 하면 **그 컬럼을 반정규화하지 않는 것**이 답이다.

### T-9 큐 튜닝 — 지연창은 손잡이로 줄이는 값이 아니라 "구간"이다

앞 절의 4.4초는 **설정 하나(워커 1 / 배치 1,000)의 결과**였다. 워커 수와 배치 크기를 축으로
훑었다(`scripts/tpch/t9-queue-tuning.sh`, 8 clients / 12초 / 4 CPU).
**조건은 라운드 교차로 재고 중앙값과 범위를 함께 낸다** — 이 실습에서는 산포가 커서
중앙값만 보면 판단이 안 선다.

**① 배치 크기** (편중, 워커 1개, `-R 800`, 5라운드)

| 배치 | 지연 중앙값 | 지연 범위 | 최대 지연 | 잔량 |
|---|---|---|---|---|
| 100 | 1,581ms | 166~8,746 | 2,218ms | 2,991 |
| 500 | 1,278ms | 239~3,466 | 2,190ms | 2,942 |
| 2,000 | **121ms** | **53~249** | 1,112ms | 261 |

중요한 건 중앙값 차이(13배)보다 **범위**다. 작은 배치의 166~8,746ms 는 "느리다"가 아니라
**따라잡기가 불안정하다**는 뜻이다 — 따라잡으면 수백 ms, 한 번 밀리면 적체가 스스로를 키워
수천 ms 로 간다. 쌍봉 분포다. 배치 2,000 은 중앙값이 낮을 뿐 아니라 범위가 좁다.

**② 워커 수** (편중, 배치 2,000, `-R 800`, 5라운드)

| 워커 | 지연 중앙값 | 지연 범위 | 잔량 |
|---|---|---|---|
| 1 | 309ms | 89~774 | 1,931 |
| 2 | 267ms | 184~371 | 1,186 |
| 4 | 447ms | 232~995 | 3,346 |

1개와 2개는 범위가 겹쳐 **구분되지 않고**, 4개는 오히려 나쁘다. 같은 고객1의 denorm 행을
두고 서로 기다리는 데다, 4 CPU 를 8개 클라이언트와 나눠 갖는다.

**③ 자연 분포 대조** (배치 2,000, `-R 800`) — 워커 1개 81ms(73~176) / 2개 182ms / 4개 601ms.
잔량은 0 으로 수렴하고 합침배수도 1.2 라 접을 것이 없다.
여기서 두 가지가 드러났다.
- **워커를 늘리면 여기서도 지연이 는다**(81 → 182 → 601). 핫키가 없으니 행 경합이 아니라
  순수한 CPU 경합이다. 즉 "워커를 늘리면 빨라진다"는 **어느 분포에서도 성립하지 않았다.**
- **편중 자체가 자릿수를 바꾸지는 않는다.** 워커 1개 기준 자연 81ms vs 편중 121~309ms 로
  같은 자릿수다. 자릿수를 바꾸는 건 편중이 아니라 **따라잡지 못하게 되는 것**이다.

**④ 배치는 상한인가 목표인가** (자연 분포, `-R 200`) — 배치 100: 59ms / 배치 2,000: 57ms.
사실상 같다. 워커가 배치가 차기를 기다리지 않고 `LIMIT batch` 로 있는 만큼 가져가기 때문이다.
**즉 batch 는 상한이지 목표가 아니고, 크게 잡아 손해가 없다.**
(배치가 찰 때까지 기다리는 설계였다면 여기서 큰 배치가 훨씬 불리하게 나왔을 것이다.)

**⑤ 포화 부하** (편중, 워커 1개, 무제한)

| 배치 | 부하 tps | 평균 지연 | 배치 횟수 | 배치당 항목 | **총 처리항목** | 적체 |
|---|---|---|---|---|---|---|
| 100 | 4,456 | 6,189ms | 62 | 1,308 | 81,096 | 55,542 |
| 500 | 4,301 | 4,895ms | 122 | 620 | 75,640 | 44,718 |
| 2,000 | 4,224 | 3,122ms | 68 | 1,142 | 77,656 | 35,813 |

배치를 20배 키워도 **총 처리항목이 거의 같다**(7.6~8.1만). 배치당 항목이 늘면 배치 횟수가
그만큼 준다. **포화에서 배치 크기는 용량을 사주지 않는다.**

**결론 11**: 지연창은 손잡이를 돌려 연속적으로 줄이는 값이 아니라 **구간**이다.
- 따라잡는 구간 → 수십~수백 ms, 범위도 좁다
- 밀리기 시작한 구간 → 중앙값 수천 ms, 꼬리는 그 몇 배
- 포화 → 지연이 수렴하지 않는다. 그건 지연창이 아니라 **적체**다

배치 크기가 하는 일은 지연을 줄이는 게 아니라 **그 경계를 옮기는 것**이고, 워커 수는
어느 분포에서도 도움이 되지 않았다. 그래서 운영 판단은 "지연 몇 ms 를 목표로 튜닝"이 아니라
**"지금 따라잡고 있는가(잔량이 0 으로 돌아오는가)"** 를 지표로 삼아야 한다.
그 지표가 무너지면 손잡이가 아니라 **모델**을 봐야 한다 — 팬아웃을 줄이거나 핫 계정을 쪼개거나.

> ⚠️ **비교는 같은 스윕 안에서만 유효하다.** ①의 (워커1·배치2000)은 121ms, ②의 같은 조건은
> 309ms 로 2.5배 차이가 났다. 라운드 교차는 스윕 내부의 시간대 드리프트만 지운다.
> 스윕끼리의 절대값을 비교하면 안 된다.

### T-9 워커를 어떻게 깨울 것인가 — 폴링 / NOTIFY / 고정 창 / 적응형 창

앞 절에서 저부하(`-R 200`) 지연이 배치 100/2000 둘 다 57~59ms 로 **배치와 무관하게 바닥이
잡혀 있었다.** 용의자는 워커의 20ms 고정 sleep 이었고, 여기서 검증했다
(`scripts/tpch/t9-notify-vs-poll.sh` + `t9_worker.py`).

**공정성 설계 두 가지.** ⓐ plpgsql 로는 알림을 기다릴 수 없어(`pg_sleep` 은 NOTIFY 로 안 깨진다)
워커를 파이썬 클라이언트로 내보내되 **네 방식이 같은 코드·같은 `denorm_drain()`** 을 쓰게 했다.
각각 다른 언어로 짜면 깨우는 방식이 아니라 언어와 왕복 비용을 비교하게 된다.
ⓑ ①② 는 **전부 NOTIFY 를 발행하는 트리거**로 돌렸다(폴링 워커는 무시할 뿐).
쓰기 경로를 동일하게 만들어야 지연 차이만 남는다. NOTIFY 의 쓰기 비용은 ③에서 따로 쟀다.

세 번째·네 번째 방식까지 **같은 스윕에** 넣어 4파전으로 쟀다
(스윕이 다르면 절대값을 비교할 수 없으므로 반드시 같은 스윕이어야 한다).
- **고정 창(디바운스)**: 알림으로 깨우되 창 동안 더 모았다가 한 번에 처리
- **적응형 창**: 창 대신 **drain 사이 최소 간격**을 보장한다. 기다릴 시간을 그때그때
  *계산*하므로, 직전 drain 이후 이미 간격만큼 지났으면 한 톨도 안 기다린다.
  파라미터의 의미가 "얼마나 기다릴까"가 아니라 **"초당 몇 번까지 DB 를 찌를까"** 다.

**① 저부하** (`-R 50`, 자연 분포, 배치 2,000, 3라운드 교차)

| 깨우는 방식 | 지연 중앙값 | 최대 지연 | 왕복 | 빈 폴링 | 배치당 항목 |
|---|---|---|---|---|---|
| 폴링 20ms | 12ms | 195ms | 933 | 556 | 4.4 |
| **NOTIFY** | **2ms** | 7ms | 1,222 | 608 | 2.9 |
| 고정창 5ms | 6ms | 14ms | 920 | 460 | 3.6 |
| 고정창 20ms | 15ms | 43ms | 640 | 325 | 5.2 |
| **적응형 5ms** | **3ms** | 11ms | **871** | 354 | 3.1 |
| 적응형 20ms | 12ms | 33ms | 498 | 118 | 4.4 |

지연 바닥은 폴링 간격의 절반이다 — 앞 절에서 배치를 20배 바꿔도 꿈쩍 않던 값이
sleep 을 바꾸자 그대로 따라 움직였다. **고정 창은 여기서 손해다**(창 안에 모일 것이 없어
창이 그냥 기다림이 된다).

**적응형이 그 손해를 없앤다. 같은 파라미터에서 고정 창을 두 축 모두 이긴다** —
5ms: 지연 6→3ms · 왕복 920→871 / 20ms: 지연 15→12ms · 왕복 640→498.

**② 중부하** (`-R 800`) — 여기서 판이 뒤집힌다.

| 깨우는 방식 | 지연 중앙값 | 최대 지연 | 왕복 | 빈 폴링 | 배치당 항목 |
|---|---|---|---|---|---|
| 폴링 20ms | 9ms | 46ms | 2,066 | 378 | 13.2 |
| NOTIFY | 2ms | 30ms | **7,078** | 1,905 | 4.4 |
| 고정창 5ms | 3ms | 37ms | 4,213 | 737 | 6.4 |
| 고정창 20ms | 9ms | 25ms | 1,988 | 365 | 13.9 |
| **적응형 5ms** | 6ms | 34ms | **1,380** | **4** | 16.2 |
| 적응형 20ms | 15ms | 67ms | 438 | **2** | 51.7 |

**NOTIFY 의 왕복이 7,078 로 압도적으로 많다.** 트랜잭션마다 알림이 하나씩 나가므로
알림 기반이 사실상 **트랜잭션 속도의 바쁜 폴링으로 퇴화**했다
(배치당 4.4항목 — 잘게 쪼개 일한다). "알림 기반은 조용하다"는 통념과 반대다.

고정 창이 그 지점을 고치고(5ms: 지연 +1ms 에 왕복 7,078→4,213),
**적응형은 한 발 더 간다 — 빈 폴링이 4 와 2 로 사실상 0 이다**(고정 창은 737/365).
페이싱 덕에 깨어날 때는 이미 일이 쌓여 있어 **헛왕복 자체가 사라진다.**
배치당 항목이 4.4 → 16.2 → 51.7 로 커지는 것이 그 기전이다.

곡선으로 보면 **적응형 5ms(6ms/1,380)가 고정창 20ms(9ms/1,988)와 폴링 20ms(9ms/2,066)를
두 축 모두에서 이긴다.** 같은 파라미터끼리는 적응형이 더 공격적으로 모을 뿐이다
(5ms 기준 지연 3→6ms, 왕복 4,213→1,380).

**③ NOTIFY 는 공짜가 아니다** (포화 부하, 워커 없이 쓰기 경로만)

| | tps | 범위 |
|---|---|---|
| 큐 INSERT 만 | 3,963 | 3,908~4,067 |
| 큐 INSERT + NOTIFY | 2,526 | 2,518~2,587 |
| **쓰기 경로 비용** | **1.57배** | |

payload 를 비워 한 트랜잭션의 동일 알림이 하나로 합쳐지게 했는데도 이 값이다.

**결론 12**: 두 손잡이는 경쟁 관계가 아니라 **서로 다른 구간의 손잡이**다.
- 따라잡는 구간(건강) → **깨우는 간격**이 지연을 지배. 배치·워커는 거의 무관
- 적체 구간(불건강) → **처리 용량**이 지배 (앞 절 ⑤)

그래서 NOTIFY 는 처리량 대책이 아니라 **응답성 대책**이고, 심지어 처리량을 1.57배 깎는다.
적체가 문제인 상황에 붙이면 **오히려 악화된다.**

**결론 13**: 깨우는 방식의 파라미터는 **고정값으로 두면 반드시 한쪽 구간에서 틀린다.**

| | 한산(`-R 50`) | 바쁨(`-R 800`) |
|---|---|---|
| NOTIFY 단독 | 최선(2ms) | 왕복 폭증(7,078) |
| 고정 창 | 손해(모을 것이 없는데 기다린다) | 이득 |
| **적응형 창** | **고정 창을 두 축 모두 지배** | **빈 폴링 0 수렴** |

고정 창은 부하 구간마다 답이 갈리므로 **한 값으로 두 구간을 다 감당하지 못한다.**
적응형은 대기 시간을 *계산*해 그 딜레마를 없앤다.
다만 적응형도 공짜가 아니다 — 부하가 높으면 **페이싱이 곧 지연**이 되므로
(5ms → 6ms, 20ms → 15ms) 값은 **허용 지연**을 보고 정해야 한다.

### T-9 큐 깊이 기반 제어 — 가설 기각을 기록한다

앞 절이 남긴 가설: "적응형은 시간만 보므로 일이 쌓여 있어도 기다린다 — 큐 깊이를 보면
그걸 피할 수 있지 않은가." `denorm_drain` 이 남은 깊이를 함께 돌려주게 하고(추가 왕복 없음),
깊이 ≥ 임계치(500)면 페이싱을 건너뛰는 `qdepth` 모드를 붙여 같은 스윕에서 쟀다.

**결과: 잰 어떤 구간에서도 이득이 없었다.** (5파 재실행, 3라운드 교차)

| 구간 | 적응형 5ms | 큐깊이 5ms | 판정 |
|---|---|---|---|
| 한산 `-R 50` | 4ms / 왕복 883 | 4ms / 왕복 878 | **동일** — 신호 발화 없음 |
| 바쁨 `-R 800` | 5ms / 왕복 1,420 / 배치당 15.9 | 6ms / 왕복 1,295 / 배치당 17.7 | **동일**(편차 범위) — 발화 없음 |
| 버스트 소진 (2만 건 적체 → 기동) | 1,508~1,818ms | 1,900~1,927ms | 이득 없음 — 절약분이 묻힌다 |

- **정상 구간에서 신호가 발화하지 않는 이유**: 페이싱 간격(5~20ms) 동안 쌓이는 항목이
  `-R 800` 에서도 ~4건이라 임계치 500 에 한참 못 미친다. 워커가 따라잡는 한 깊이는 늘 얕다.
- **버스트에서도 이득이 없는 이유**: 이론상 절약은 페이싱 × 배치 수(20ms × 9 ≈ 180ms)인데
  배치 작업 시간(1.5~1.9초)에 묻힌다. 오히려 근소하게 느렸다(3/3 재현, 편차와 겹침).
- **신호를 낮춰 잡으면?** '페이싱이 곧 지연'을 깊이로 피하려면 임계치를 페이싱당
  도착량(~4건)까지 내려야 하는데, 그건 **NOTIFY 로 돌아가는 것**이다.

**결론 14**: **합침은 기다림 그 자체다 — 기다림을 건너뛰면 합침도 같이 사라진다.**
왕복을 줄이는 것(모아서 크게)과 지연을 줄이는 것(즉시 처리)은 같은 손잡이의 양끝이라
신호를 하나 더 단다고 둘 다 가질 수는 없다. 페이싱 값은 신호가 아니라
**읽는 쪽의 허용 지연**으로 정하는 것이 맞다.
파생 미완 항목이던 "큐 길이 기반 제어"는 이것으로 닫는다 — 기각도 결과다.

> ⚠️ **적체 구간에서의 비교는 재현하지 못했다.** 편중 워크로드로 적체를 만들려 했으나
> 워커가 배치를 한 번도 적용하지 못한 채 큐가 비는 상태가 나와 해석이 불가능했다(원인 미규명).
> 빈 데이터로 "차이가 사라진다"를 주장하지 않기 위해 해당 절을 스크립트에서 **삭제**했다.

### T-2 / T-3 / T-5 를 tpcds 로 — 스크립트가 아예 없던 것을 채웠다

`scripts/tpcds` 에는 실험 스크립트가 하나도 없어 T-2~T-5 를 tpcds 로 돌릴 수 없었다.
세 개를 만들고 실측했다.

**T-2 — 스타 스키마에는 "날짜 컬럼"이 없다.** tpch 는 `l_shipdate` 에 직접 걸지만
tpcds 는 대리키 `ss_sold_date_sk` 뿐이라 `date_dim` 을 거쳐야 한다. 두 형태를 다 쟀더니
**전환점이 3~4배 차이** 났다 — 팩트 직접은 20~30%, 차원 경유는 5~10%.
차원을 거치면 옵티마이저가 팩트 쪽 선택도를 조인 전에 몰라 보수적으로 잡기 때문이다.

**강제 실행으로 진짜 전환점을 찾으니 옵티마이저가 최대 2.03배 틀렸다** —
진짜 전환점은 5~10% 인데 30% 가 되어서야 Seq 로 바꾼다(19.98% 지점: 137.8 vs 67.9ms).
tpch 판의 같은 어긋남(13% 손해)보다 폭이 훨씬 크다.
반면 **차원 경유에서는 옵티마이저가 정확했다.**

**T-3 — 스타 스키마는 NL 쪽으로 크게 기운다.** 순수 Hash 강제 시 q03 은 28배(2.0 → 56.2ms),
q19 는 3.6배 느리다. 버퍼가 2,144 vs 40,510 으로 한 자릿수 배 차이다.
그리고 **여기서는 옵티마이저가 옳았다**(자율선택이 모든 강제 조합보다 빠르거나 같다) —
tpch 에서 1.3~1.6배 손해 보던 것과 대비된다. 같은 옵티마이저가 T-2(스캔)에서는 2.03배
틀리고 T-3(조인)에서는 맞았다는 것이 이번 실습의 핵심이다.

**T-5 — 필터 비율 휴리스틱이 맞았다.** item 0.10% / date_dim 8.21% / store_sales 100% 에서
Tow 의 예측대로 item 드라이빙이 최선(1.70ms)이고, date_dim 부터 몰면 **38배** 손해(65.67ms).
버퍼가 원인을 말해준다 — (a)·(c) 는 hit=2,144 로 끝나는데 (b) 는 **read=37,438** 이다.

부수로 함정 하나 확인: `join_collapse_limit=1` 은 조인 **순서**만 고정하고 inner/outer 는
옵티마이저가 정하므로 **"FROM 첫 테이블 = 드라이빙 테이블"이 아니다**.
실제로 (a)와 (c)는 FROM 첫 테이블이 다른데 계획이 동일하다 — **PostgreSQL 이 (c)의 나쁜
순서를 알아서 되돌렸다.** (b)는 못 되돌린다. `date_dim → store_sales` 를 먼저 붙이라고
못박으면 중간 결과가 이미 거대해져 되돌릴 여지가 없기 때문이다.

**처음에는 이 절에 결과 표만 있고 실행 SQL 이 없었다**(지적 받음). 재현 불가능한 절이라
1단계(필터 비율 집계)와 2단계(세 가지 순서의 명시적 JOIN) SQL 을 모두 실었고,
**문서에서 SQL 을 추출해 그대로 실행**해 표의 숫자가 재현되는지 확인한 뒤 표를 그 실행값으로
맞췄다. 문서에 적힌 쿼리와 표의 숫자가 다른 실행에서 나온 상태를 남기지 않기 위해서다.

**설계 결정**: `join-method-compare.sh` 는 복제하지 않고 `MODULE` 변수로 일반화한 뒤
tpcds 쪽에 3줄 래퍼를 뒀다(기본값 tpch 라 기존 사용법·회귀 없음 확인). 로직을 복사하면
한쪽만 고쳐지는 일이 반드시 생긴다. T-2 스크립트는 대상 컬럼·의미가 달라 별도로 작성했다.

### T-4 를 tpcds 로 — 정정 3번을 다듬게 됐다

`scripts/tpcds/t4-index-defeat.sh` 신설(tpch 는 문서 내 SQL 뿐이었다). 5개 실험.

- ① 함수로 감싸기: Index Cond 4.06ms vs Filter 37.54ms — **9.2배**
- ② 형변환 무력화(Seq 2.96/3.48ms) → 표현식 인덱스로 복구(0.063ms)
- ③ VACUUM: Bitmap 15.79ms(relallvisible 0) → Index Only 4.31ms(8,850/8,896) — 3.7배
- ⑤ 스타 스키마 고유: 대리키에 형변환을 걸면 NL 0.767ms → Hash **128.455ms = 167배**

**④에서 §5 정정 3번을 다듬어야 할 결과가 나왔다.** `ss_coupon_amt` 는 최빈값이 90.04% 인
진짜 편중 컬럼이라 "치우친 데이터에서 target 이 효과를 낸다"를 실증할 셈이었는데, 반대였다 —
**최빈값은 target=1 에서도 오차 1.00배**다. MCV 목록은 target=1 이어도 한 칸은 담으므로
90% 짜리 값은 공짜로 잡힌다. 반대로 희소값(21행/200만)은 target=1000 에서도 2.62배 오차가
남는다 — 어느 target 에서도 MCV 에 못 들어가기 때문이다(MCV/히스토그램 열로 확인).
⇒ target 이 하는 일은 "편중 잡기"가 아니라 **MCV 목록을 늘려 중간 빈도 값을 담는 것**이고,
진짜 변수는 "조회하는 값이 MCV 에 있는가"다.

**자기 함정 하나**: ⑤를 단발 측정해 "형변환 쪽이 더 빠르다"는 정반대 결론을 적을 뻔했다
(§T-0 ② 위반, 콜드 캐시). 4회 최소값으로 바꾸니 방향이 뒤집혔다. 스크립트 전체에
`best_ms()` 를 적용했다. 그리고 ④의 추정치를 집계 노드(항상 rows=1)에서 뽑고 있어
"target 을 바꿔도 추정 1"이라는 무의미한 표가 나왔던 것도 함께 고쳤다.

### T-6~T-9 를 tpcds 로 — tpch 결론이 세 군데서 갈렸다

`scripts/tpcds/` 에 `t6-query-diagram.sh` / `t7-complex-sql.sh` / `t8-combined-index.sh` /
`t9-preaggregation.sh` 4종 신설. T-6·T-7 은 tpch 판에도 스크립트가 없던 절이다.

**T-6 — 다이어그램의 예측이 그대로 맞았다.** `i_manager_id` 필터만 1%→100% 로 약화시키며
"가장 깊은 스캔 노드"를 뽑으면 진입점이 **item(1%) → date_dim(4.8% 이후)** 으로 옮겨간다.
시간은 28.6 → 127.4ms. 전환이 1%~4.8% 사이로 **생각보다 이르다.**
그리고 조인 방식은 한 번에 뒤집히지 않고 `NL×3 → NL×4 → NL×1` 로 **차원 하나씩 항복한다.**

- 자기 함정 A: "약한 필터에서는 어차피 Hash 니 NL 금지해도 차이 없겠지"를 먼저 써 뒀다가
  뒤집혔다 — 무필터에서도 1.95x 손해. 이유는 내가 만든 표 안에 이미 있었다(100% 구간에도
  `NL×1` 이 남는다: date_dim 60행 → store_sales 인덱스 진입). **NL 은 사라지지 않고 개수만 준다.**
- 자기 함정 B: 단발 측정에서 최강 필터가 **3,054ms** 로 제일 느리게 나왔다(무필터 148ms).
  `I/O Timings: shared read=5,698ms` — 콜드 캐시였다. 그대로 믿었으면 정반대 결론이었다.

**T-7 — UNION 절의 통상적 설명을 한 단계 정정했다.** ① ON→WHERE 이동은 결과가
1,006,740 → 1,006,571 로 169행 줄고 계획 노드가 `Hash Right Join` → `Hash Join` 이 된다
(사라진 169 = 매출 없는 고객 73 + 이익 ≤0 만 있는 고객 96, 내역까지 확인).
② `NOT IN`(hashed SubPlan) 377ms vs `NOT EXISTS`(NL Anti Join) 47ms = **8.0x**, 그리고
NULL 을 **한 건** 넣으면 `NOT IN` 의 답이 73 → **0** 이 된다(`NOT EXISTS` 는 불변).
③ `UNION → UNION ALL` 은 **무조건 하는 치환이 아니다.** 분기가 겹치면 행수가 달라진다
(44,750 vs 332,530). 서로소인 경우에만 답이 같고, 그때 중복 제거는 순수 낭비 **2.08x**.

**T-8 — tpch 판의 "커버링은 대개 과하다"가 뒤집혔다.** probe buffers 20,179 → 4,290 →
**1,543**, 시간 27.7 → 11.9 → **2.9ms**. ③이 ②를 다시 4.1x 이기는 이유는 `Heap Fetches: 0`
이다 — 팩트 행이 넓을수록(23컬럼) 힙 한 페이지의 유효 행이 적어 커버링 이득이 커진다.
**부수 발견**: 선행 컬럼이 같은 좁은 인덱스가 여기서는 PK 라 지울 수 없는데도 옵티마이저가
결합 인덱스를 골랐다. 결합 인덱스(43MB)가 PK(60MB)보다 **작기** 때문이다
(2번째 컬럼이 bigint 8B → integer 4B). ⇒ 규칙은 "좁은 쪽이 이긴다"가 아니라
**"작은 쪽이 이긴다"** 이고, tpch 에서 좁은 쪽이 이긴 것은 그게 마침 작았기 때문이다.

**T-9 — "접힌 것은 유지도 싸다"가 틀렸다.** ① 21,393 buffers/36ms → ② 반정규화 325/1.8ms
→ ③ MV 161/0.96ms. 대가 쪽에서 두 가지가 나왔다:

- **팬아웃**: 상품 1건 담당자 변경이 `ss_denorm` 86행으로, 담당자 1명 재배정(item 196행)이
  **19,523행**으로 번진다(100배). 차원이 작고 팩트가 큰 스타 스키마의 구조적 성질이다.
- **자기 함정**: "③은 접혀 있으니 유지도 쌀 것"을 먼저 적었다가 뒤집혔다. 점 변경 하나의
  반영 비용이 반정규화 140ms vs MV REFRESH **5,260ms = 38배**. PG 의 REFRESH 는 증분이
  아니다(`CONCURRENTLY` 도 전량 재계산 후 교체). **접힘은 저장량의 성질이지 갱신 비용의
  성질이 아니다.** ⇒ 읽기만 보면 ③, 쓰기까지 보면 ②.
- **범용성의 가격을 수치화**: tpch 판 MV 는 파라미터가 박혀 못 쓰는 게 한계였으므로 이번엔
  필터 컬럼을 `GROUP BY` 에 남겨 범용으로 만들었는데 — 범용 967,874행/108MB/REFRESH 5,240ms
  vs 파라미터 박은 것 158행/32kB/70ms. **3,400배 크기, 75배 REFRESH** 가 범용성의 값이다.
  접힘이 2.1분의 1뿐인 이유는 `i_brand_id` 11,483종 × 연월 60개라 그룹 수가 팩트에 육박해서다.
  ⇒ 범용 MV 를 만들기 전에 **group by 조합의 카디널리티부터 세야 한다.**

**이식하지 않은 것과 그 이유**: T-9 의 유지 전략 6종(`t9-trigger-sync` / `t9-concurrency` /
`t9-lock-range` / `t9-change-queue` / `t9-queue-tuning` / `t9-notify-vs-poll`)은 tpcds 로
복제하지 않았다. 이들이 재는 락 범위·큐 멱등성·워커 기동 방식은 스키마 모양과 무관하고,
스키마가 바꾸는 것은 팬아웃 크기뿐인데 그것은 `t9-preaggregation.sh` 의 "대가 ②"에서 잰다.
복제하면 유지 대상만 늘고 새로 알게 되는 것이 없다(§0-4 대응표에 근거를 적어 뒀다).

### §T-6 확장 — 옵티마이저가 병렬을 고르는 / 못 고르는 지점 (`scripts/tpch/t6-parallel-decision.sh`)

**사용자가 SF=10(lineitem 5,999만, 인덱스 없음, ANALYZE 후) 실행 로그를 보내며 "q13이 병렬이
안 된 것 같은데 확인해 달라"고 한 데서 시작됐다.** 맞았고, 확인하는 과정에서 같은 성질의 문제가
셋 더 나와 한 스크립트로 묶었다. 셋 다 **행을 더 읽어서가 아니라 프로세스를 어떻게 나눌지
판정하는 데서** 느려진 경우다 — 행 수·인덱스로는 안 보인다.

사용자 환경 요약(SF=10): q01 6,985 / q03 2,178 / q05 4,652 / q06 1,077 / q09 6,634 /
q13 11,489 / **q18 44,955** ms.

- **① q13 은 완전히 직렬** — `Gather` 가 하나도 없다. SF=0.5 에서 같은 모양이 재현된다.
  손잡이를 하나씩 켜서 분리했다: `parallel_setup_cost=0` 도 `min_parallel_table_scan_size=0` 도
  안 뒤집히고 **`parallel_tuple_cost` 단독으로** 뒤집힌다. 병렬 경로는 존재한다(PG16 의
  `Parallel Hash Right Join`) — 거절한 건 비용이다. `GROUP BY c_custkey` 는 부분 집계가
  줄여 주지 못해 워커마다 전체 그룹을 Gather 로 올리고(75,000×3=225,000행 → 비용 22,500),
  그게 직렬 계획 전체(33,506)와 맞먹는다. 실측은 직렬 506.4 vs 병렬 243.8ms — **2.08배,
  플래너가 틀렸다.** 그리고 그룹 수는 규모에 비례하므로 **데이터를 더 넣어도 저절로 안 풀린다.**
- **② 워커 수는 제일 큰 테이블이 아니라 구동 스캔이 정한다** — q05 는 lineitem 을 만지면서
  `Workers Planned: 1`. 짐작하지 않고 계획의 병렬 스캔 대상마다 `parallel_workers=4` 를 박아
  **어느 테이블이 전체 병렬도를 움직이는지 실제로 확인**하게 했다. 로컬은 customer(14MB),
  사용자 SF=10 은 supplier(17MB)로 둘 다 워커 1개 — 크기 규칙(`8MB→1, 24MB→2, 72MB→3`)과 일치.
  박으면 워커 4 / 138.5→91.3ms(1.52배). 해시 조인의 병렬도는 **구동 경로에서 상속**된다.
- **③ q18 의 하위 집계가 프로세스마다 재실행된다** — `Seq Scan on lineitem lineitem_1 … loops=4`
  (사용자 쪽은 loops=5). `GROUP BY l_orderkey` 는 감소율이 **4.0:1** 뿐이라 부분 집계 이득이
  없고, 그래서 이 노드가 병렬 구역 안의 **비병렬 해시 쪽**에 놓여 통째로 재실행된다.
  사용자 계획에서 `Batches: 85 / Disk Usage 2,356,056kB` 가 워커마다 찍히고 temp write 가
  **30.5GB** 였던 것이 이것이다. 45초의 정체.
- **④ work_mem 은 이번엔 답이 아니다** — 그룹당 바이트를 **쟀다**(750,000그룹에 294,929kB
  = **403바이트**). 키 8바이트로 어림하면 50배 틀린다. 6천만 행이면 프로세스당 5.63GB,
  ×5 = **22.5GB**. §T-7 의 t7-complex-sql.sh 에서 4GB 가 몇 시간을 몇 분으로 바꾼 것과는
  **성격이 다른 병**이다 — 거기는 한 노드가 한 번 넘쳤고, 여기는 같은 일을 N번 한다.
- **⑤ 처방과, 이득이 두 갈래라는 것** — 하위 집계를 임시 테이블로 한 번만 계산하면 본 쿼리가
  **0.4ms** 가 된다. (가) 중복이 사라지고, (나) **계획이 바뀐다** — 37행이라는 걸 알게 된
  옵티마이저가 lineitem 풀스캔 대신 `Nested Loop` + `Index Scan` 으로 간다. (나)는 §T-1 의
  "통계가 인덱스보다 중요했다"와 같은 자리다. 그리고 **①과 ③이 여기서 만난다** — 떼어 낸
  하위 집계도 고카디널리티 `GROUP BY` 라 그대로 두면 직렬로 돈다.

**이 실습에서 조심한 것 / 고친 것:**
1. **⑤의 "본 쿼리 0.4ms" 를 그대로 적지 않았다.** 수치만 보면 측정 실패로 보이므로 계획을
   같이 찍게 해서 `Nested Loop`+`Index Scan` 임을 보이도록 고쳤다. 안 그랬으면 (나)를
   통째로 놓치고 "중복 제거 효과"로만 잘못 적었을 것이다.
2. **준비 단계를 ④의 `max_parallel_workers_per_gather=0` 인 채로 재고 있었다.** ④는 메모리를
   재려고 직렬을 강제한 것인데 그 설정을 ⑤의 시간 측정에 끌고 왔다. 실제 설정으로 분리했고,
   임시 테이블 `ANALYZE` 도 넣었다(통계 없는 임시 테이블은 플래너가 기본값으로 때려 맞춘다).
3. 임시 테이블 행수를 `EXPLAIN` 출력의 첫 `rows=` 로 읽어 **"1행"** 이라고 찍고 있었다
   (실제 37행). 집계 노드의 rows 를 읽은 것 — 평문 `SELECT count(*)` 로 바꿨다.
4. `current_setting('min_parallel_table_scan_size')::bigint` 가 `'8MB'` 를 못 캐스팅해
   표에 `ERROR` 가 찍혔다. `pg_size_bytes()` 로 고침.
5. **이 컨테이너는 로케일이 UTF-8 이 아니라 `${#s}` 도 `printf %-Ns` 도 바이트를 센다.**
   한글 라벨 표가 2칸씩 어긋났다. 바이트만으로 표시 폭을 구하는 `dispw/padr/padl` 을 넣었다
   (폭 = 바이트수 − 이어지는바이트수/2).
6. ②가 `ALTER TABLE … SET (parallel_workers)` 로 테이블 옵션을 건드리므로 **끝에 잔재 검사**를
   넣었다. 남으면 다른 실습의 병렬도가 조용히 바뀌어 원인 모를 수치 차이가 된다(정정 8번의 교훈).

**규모의 한계를 명시했다** — SF=0.5 는 방향만 보이는 규모다(⑤의 합계 이득이 1.07배뿐이다).
그 이유 자체가 교훈이라 문서에 적었다: **중복은 넘치기 전까지 병렬에 가려진다.** N개가 동시에
하니 벽시계로는 1배처럼 보이고, 넘치는 순간 N개가 디스크 대역폭을 나눠 쓰며 계단처럼 뛴다.
그래서 스크립트는 각 절이 판정에 쓴 지표(Gather 통과 행 수 / 구동 테이블 크기 / `loops` /
그룹당 바이트)를 같이 찍어, 수치가 작아도 자기 환경을 판정할 수 있게 했다.

> 사용자 로그에서 같이 읽은 것(스크립트 밖): q01 7.0초 vs q06 1.08초는 **스캔이 같고 집계가
> 지배하는** 사례(필터 뒤 5,900만 vs 114만 행). q03 의 `dirtied=78428 written=78289` 는
> 적재 후 VACUUM 을 안 한 상태의 **힌트 비트 쓰기** — 첫 실행을 버리는 이유(§T-0)가 그대로
> 나왔다. JIT 가 쿼리마다 370~930ms 붙지만 EXPLAIN 의 JIT 시간은 워커 합산일 수 있어
> 비율을 단정하지 않았다(SF=0.5 는 JIT 임계 아래라 여기서 재현 불가 — `SET jit=off` 로
> 사용자 환경에서 확인할 것).

### 환경 복구 — `scripts/restore-lab.sh`

이 랩은 Docker 없이 **호스트에 직접 설치된 PostgreSQL 16** 위에서 돌아간다. 세션이 바뀌며
컨테이너가 재생성되면 클러스터가 down 이거나, 롤·DB·데이터가 통째로 사라져 있다.
세션마다 같은 복구를 손으로 반복하다가 스크립트로 묶었다.

```bash
./scripts/restore-lab.sh --check   # 점검만
./scripts/restore-lab.sh           # 빠진 것만 복구 (데이터가 있으면 안 건드린다)
```

클러스터 기동 → 롤 `tuner` → DB → **측정 조건**(`shared_buffers=1GB` / `work_mem=64MB` /
`max_parallel_workers_per_gather=4`) → 비어 있는 DB 만 재적재 → 실습 잔여물 경고.

**설정 항목을 넣은 이유가 가장 중요하다.** 다른 넷은 에러를 내며 멈추지만, 서버 설정이
기본값(`shared_buffers=128MB`, `work_mem=4MB`)으로 돌아간 것은 **아무 에러 없이 숫자만 조용히
틀린다.** 실제로 이번 복구에서 그 상태였고, 모르고 쟀으면 문서의 실측표와 배수가 어긋난
결과를 새 측정값으로 적을 뻔했다. §T-0 의 "측정 전제를 만드는 단계가 그 전제를 깨뜨리지
않는지 본다"와 같은 계열이다.

부수로 확인한 것: `--dir=./data/tpch` 는 저장소 루트가 아니라 **모듈 디렉터리** 기준으로
풀린다(실제 경로 `tpch/data/tpch`). generate·load 가 같은 상대 경로를 써서 동작에는 문제가
없지만, COPY 스크립트를 직접 부를 때는 그 경로를 줘야 한다.

#### `--mysql` 이 없는데 있는 것처럼 안내하고 있었다 — 세 겹의 실수

사용자가 `mt-tenant-isolation-mysql.sh` 를 돌렸다가 이렇게 받았다:

```
MySQL 의 tpch.lineitem 이 없습니다. ./scripts/restore-lab.sh --mysql 을 먼저 실행하세요.
→ ./scripts/restore-lab.sh --mysql
   → 클러스터를 기동한다
      ./scripts/restore-lab.sh: line 60: pg_ctlcluster: command not found
```

**MySQL 을 고치러 갔는데 PostgreSQL 에러가 돌아왔다.** 세 가지가 겹쳤다:

1. **`--mysql` 은 구현된 적이 없다.** 스크립트 안내문에만 있었다 — 내가 쓴 처방이
   실행되는 코드가 아니었다. 이 랩의 원칙("실행해 보지 않은 절차를 적지 않는다")을
   **처방문에서** 어긴 경우고, 절 본문만 보고 있었지 안내 문구는 안 보고 있었다.
2. **모르는 인자를 조용히 삼켰다.** `MODE="${1:-}"` 이라 `--mysql` 은 `--check` 도
   `--force-tpch` 도 아니어서 그냥 버려지고, 기본 경로(PostgreSQL 복구)로 들어갔다.
   사용자는 자기가 시킨 것과 **다른 일**이 실패하는 걸 본다. 인자 검증이 없으면
   오타 하나가 전혀 다른 곳에서 터진다.
3. **호스트 설치만 가정했다.** 스크립트 머리말에 "이 랩은 Docker 없이 호스트에 직접
   설치된 PostgreSQL 위에서 돌아간다"고 적혀 있었는데, 그건 **이 컨테이너 환경**의
   이야기지 사용자 머신의 이야기가 아니었다. 사용자는 `docker/docker-compose.yml` 로
   돌린다. 그래서 `pg_ctlcluster` 가 없다.

고친 것:

- **인자 검증** — 모르는 인자는 사용법을 찍고 exit 2. 조용히 무시하지 않는다.
- **`--mysql` 을 실제로 구현** — `scripts/restore-lab-mysql.inc`. 서버 기동(호스트/Docker
  둘 다) → 계정 권한 → `tpch`/`tpcds`/`sysbench_lab` 의 데이터와 **인덱스** →
  측정 조건 → `mt_n*`·`li_ac` 같은 잔여물.
- **기동 방법 판별** — `pg_ctlcluster` 가 있으면 그걸로, 없고 `tuninglab-postgres` 가
  있으면 `docker start`, 컨테이너도 없으면 `docker compose up -d postgres`.
  재기동도 같은 식(`pg_restart`). MySQL 쪽도 같다.

**그리고 그 `--mysql` 이 바로 진짜 결함을 하나 찾았다:**

```
! tpcds.store_sales 이 2000000 행인데 인덱스가 1개다 — index 를 안 돌렸다
→ index 실행 → tpcds.store_sales 인덱스 6개
```

MySQL 의 tpcds 는 `load --db=mysql` 만 돌고 `index --db=mysql` 이 안 돌아 있었다.
PRIMARY 하나뿐인 상태로 `mt-tenant-isolation-mysql.sh` 를 쟀으면 에러 없이 숫자만
틀렸을 것이다 — 정정 8번(PostgreSQL 판)과 **같은 함정이 MySQL 쪽에 그대로 있었다.**
그래서 두 MySQL 스크립트의 선행 조건 안내에 `index --db=mysql` 을 명시적으로 넣었다.

측정 조건은 **보고만 하고 바꾸지 않는다.** PostgreSQL 은 `ALTER SYSTEM` 으로 되돌리지만
MySQL 은 설정 출처가 환경마다 다르다(Docker 면 `docker/mysql/my.cnf`, 호스트면
`/etc/mysql/...`). `SET GLOBAL` 로 덮으면 파일과 실제 값이 어긋난 채 남아, 다음 사람이
my.cnf 를 읽고 틀린 조건을 가정한다. 그게 기본값으로 도는 것보다 나쁘다.

#### 고쳤더니 다음 벽이 나왔다 — 같은 실수를 두 번 더

사용자가 고친 `--mysql` 을 돌리자 이번엔 여기서 멈췄다:

```
! 호스트에 mysql 클라이언트가 없다 — 컨테이너 안에서 쓰려면: ...
→ docker exec -it tuninglab-mysql mysql -u tuner -ptuner tpch
   ERROR 1049 (42000): Unknown database 'tpch'
→ ./gradlew :tpch:bootRun --args="schema --db=mysql"
   HikariPool$PoolInitializationException: Failed to initialize pool: Unknown database 'tpch'
```

**앞의 세 겹과 같은 종류의 실수가 세 개 더 있었다.**

1. **클라이언트가 호스트에 있다고 가정했다.** PostgreSQL 쪽 스크립트들은 이미
   `psql` 이 없으면 `docker exec` 로 넘어간다. MySQL 쪽 넷은 그 분기가 없어서,
   **서버는 멀쩡한데 점검을 못 하고 멈췄다.** 내가 방금 쓴 `--mysql` 도 없다고
   `return 1` 했다 — 옆 파일에 있는 패턴을 안 보고 쓴 것이다.
   → `mycli_as USER PASS ...` 로 통일했다. ③의 `mt_app` 처럼 **다른 계정으로 붙는
     호출**이 있어서 계정을 인자로 받는 형태여야 했다.
2. **DB 가 있다고 가정했다.** `schema --db=mysql` 의 JDBC URL 이 `.../tpch` 라
   **DB 가 먼저 있어야** 스키마가 만들어진다. `docker/mysql/init/01-create-databases.sql`
   이 만들어 주기는 하는데, 그건 **볼륨이 비어 있는 첫 기동에만 돈다.** 볼륨을 먼저
   만들어 둔 환경에서는 영영 안 생긴다. 그 에러(`Unknown database`)는 원인이 안 보인다.
3. **init 의 권한이 좁았다.** `GRANT ALL ON tpch.*|tpcds.*|sysbench_lab.*` 뿐인데
   `mt-*-mysql.sh` 는 `mt_n0..24` 라는 **새 DB** 25개와 계정 `mt_app` 을 만든다.
   DB 를 채워 놔도 준비 단계에서 죽는다. init 파일과 `--mysql` 양쪽을 고쳤다
   (`--mysql` 은 root 로 넓히고, 무엇을 실행했는지 그대로 찍는다).

**재현해서 확인했다.** MySQL 의 `tpch` 를 통째로 지우고 `--mysql` 을 돌렸다:

```
! DB tpch 없음 — 이 상태로 gradlew 를 돌리면 Unknown database 'tpch' 로 죽는다   (--check)
→ DB tpch 를 만든다 → schema → load(3,000,491행, 191s) → index → ✓ 인덱스 4개
```

> **왕복비를 찍게 했다.** `docker exec` 는 프로세스를 하나 더 띄우므로 벽시계 값에
> 들어가는 연결 비용이 호스트 클라이언트보다 크다. 크기는 환경마다 다르고
> 이 컨테이너에는 docker 데몬이 없어 **내가 잴 수 없다** — 그래서 스크립트가
> 시작할 때 빈 쿼리 왕복을 직접 재서 헤더에 찍는다.
> `클라이언트 docker — 빈 쿼리 왕복 NNms. 아래 벽시계 값 전부에 이만큼이 들어 있다.`
> 짐작한 숫자를 주석에 적는 대신(예전 주석은 "연결비 25~30ms" 라고 못박아 뒀다)
> **재는 코드를 넣는 쪽**이 맞다. 이 값에 묻히는 차이는 `srv_ms`(EXPLAIN ANALYZE)로 본다.

교훈 하나로 묶으면: **"내 환경에서 되니까"가 세 번 연속으로 틀렸다.** 호스트 설치 ·
호스트 클라이언트 · 이미 만들어진 DB — 셋 다 이 컨테이너의 우연한 상태였지
랩의 전제가 아니었다. 스크립트를 고칠 때 옆에 있는 PostgreSQL 판이 이미 그 분기를
갖고 있었다는 게 특히 뼈아프다.

#### 권한은 파싱하지 말고 **해 본다**

사용자 환경에서 `--mysql` 이 이렇게 찍었다:

```
! 계정 tuner 에 없는 권한: CREATE, DROP, CREATE USER, CREATE ROUTINE
→ DB tpch 를 만든다        ← 바로 다음 줄에서 CREATE 가 된다
```

**앞뒤가 안 맞는 출력이다.** 원인은 `SHOW GRANTS` 를 문자열로 뒤진 것 —
`GRANT ALL PRIVILEGES ON \`tpch\`.* TO ...` 에는 "CREATE" 라는 글자가 없어서
'없음'으로 잡혔는데, 실제로는 그 DB 단위 권한으로 `CREATE DATABASE tpch` 가 된다.
반대로 `ALL` 인데 못 하는 것도 있다(`SET GLOBAL` 은 동적 권한이라 별도).

→ **스크립트가 할 일을 그대로 해 보는 것**으로 바꿨다. `mt_probe_$$` DB 와 계정을
  만들었다 지운다. 결론이 맞기만 한 게 아니라 **출력이 자기모순을 일으키지 않는다.**
  판정과 근거가 같은 동작에서 나오기 때문이다.

root 비밀번호도 같은 계열이었다. compose 파일의 값을 그냥 썼는데, 컨테이너는
**만들어질 때 박힌 값**을 갖는다. 이제 `docker inspect` 로 컨테이너 환경에서
읽어 오고, 그래도 안 되면 사용자가 직접 확인할 명령을 찍는다.

#### SF=10 이 MySQL 에 들어오면서 드러난 것 둘

사용자의 MySQL tpch 가 **5,999만 행**(SF=10)으로 적재됐다 — 데이터 파일이 이미
SF=10 이었고 `--mysql` 이 그대로 넣었다(41분). 그 상태로 `mt-tenant-isolation-mysql.sh`
를 돌리면 복사본 3개 + DB 25개라 **준비만 1시간대, 디스크 40GB** 다. 그래서:

**(가) 규모 가드.** 1,000만 행을 넘으면 추정치(분·GB)를 찍고 멈춘다.
`SAMPLE=3000000`(문서 실측 조건과 같은 크기) 또는 `FORCE=1` 로 고르게 한다.

**(나) 그 SAMPLE 을 만들다가 더 큰 것을 밟았다.** 처음엔 `LIMIT $SAMPLE` 로 짰는데,
MySQL 이 고른 조인 순서가 customer 를 앞에서부터 자르는 바람에 표본에
**nation 0·1·2 세 개만** 들어왔다. 측정 대상인 테넌트 3 은 **0행**이었다.
그런데 스크립트는 멈추지 않고 ②에 **"3.6배"** 를 찍었다 — 아무것도 안 재고 나온 배수다.

두 겹으로 고쳤다:
- 표본을 `l_orderkey % N = 0` 으로 솎는다 → 테넌트 분포가 보존된다.
- 적재 뒤 **쓸 수 있는 상태인지 검사**한다: 행수 > 0, 테넌트 수 == 25,
  대상 테넌트 행수 > 0. 원래 검사가 `count == NLI` 뿐이라 표본에서는 무력했다.
  **"적재가 됐는가"가 아니라 "재려는 것이 그 안에 있는가"를 물어야 했다.**

**(다) 박아 둔 해석이 측정과 어긋났다.** ①의 해설이 `echo` 로 고정돼 있어서,
표본으로 돌려 A 와 A′ 가 뒤집혀도 "N 이 A 를 이긴다"를 그대로 찍었다.
이제 측정값에서 갈라 쓴다 — 왕복비 바닥에 깔렸으면 **판정 불가**라고 말하고,
역전이 실제로 나왔을 때만 그 서술을 하며, 방향이 반대면 그대로 적는다.
그리고 이 절의 핵심 주장인 ②는 벽시계 대신 **서버 시간(EXPLAIN ANALYZE)** 으로
옮겼다 — 왕복비가 안 섞이므로 규모와 무관하게 같은 것을 잰다.

확인:

| | A (서버) | A′ (서버) | 배수 |
|---|---|---|---|
| 1/11 표본 (27만 행) | 20.5 ms | 3.82 ms | **5.4x** |
| 전체 (300만 행, 벽시계) | 459 ms | 88 ms | 5.2x |

표본에서도 같은 값이 나온다 — **표본을 제대로 뜨면** 그렇다는 것이 (나)의 요점이다.

#### 사용자 환경(8.4.11 / Docker / SF=10 표본) 실행 — 하나 더 걸렸다

고친 스크립트로 사용자가 돌린 결과를 §X-1 MySQL 절의 "재현" 항목에 기록했다.
②가 7.8배, ⑥(나)의 A′/A 가 1.23 — 버전·규모·접속 경로가 전부 달라도 **방향은 같다.**
왕복비 계기도 자기검증을 했다(벽시계 − 서버 = 65·52ms ≈ 헤더의 55ms).

**그런데 ①의 N 이 122,632ms 로 찍혔다.** A 는 236ms. 500배라 "비정규화가 압도한다"로
읽히는데 그게 아니다 — **표본은 복사본에만 적용된다.** N 은 원본 세 테이블을 그대로
조인하는 전략이라 손대지 않으므로, N 만 5,999만 행을 읽고 나머지는 300만 행을 읽었다.
④가 N 에만 59,997,159행을 돌려준 것이 증거다(나머지는 2,998,730행).

**같은 표 안에 모집단이 둘인데 표가 그걸 말해 주지 않았다.** SAMPLE 을 넣으면서 "복사본을
줄인다"만 생각하고 "줄지 않는 것이 무엇인가"를 안 물었다. LIMIT 표본 사고와 같은 계열이다 —
그때는 *무엇이 표본에 안 들어왔는가*(테넌트 3), 이번엔 *무엇이 표본을 안 탔는가*(N).
**표본을 도입할 때는 '표본 밖에 남은 것'을 먼저 세는 습관이 필요하다.**

→ 표본 실행이면 N 행에 `※` 를 붙이고 해석에서 N 을 뺀다. 같이 보려면 SAMPLE 없이 돌리라고
  명시한다.

준비 시간 추정도 틀렸다. `NROW` 로만 계산해 SF=10 + SAMPLE=300만을 3.6분으로 찍었는데
실제로는 17분이었다. 복사본을 만드는 `INSERT..SELECT` 는 **표본을 떠도 원본 전체를 훑으므로**
스캔 몫은 `NLI` 에, 쓰기 몫만 `NROW` 에 비례한다. 출력이 그걸 그대로 보여 준다 —
A·A′·B 는 288~357초인데 **C 는 72초다.** C 만 이미 만들어진 `li_a` 에서 복사하기 때문이다.
실측 두 점(3M/3M = 215초, 60M/3M = 1,014초)으로 계수를 맞췄다.

#### 그 계수로 SF=10 전체를 "70분"이라고 찍었는데 3시간이 지나도 준비가 안 끝났다

사용자가 `FORCE=1` 로 SF=10 전체를 돌렸다. 3시간 넘게 `── 준비 ──` 에 머물렀다.

**선형 외삽이 버퍼 풀 경계에서 무효가 된다.** `li_a` 는 `CREATE TABLE` 에 보조 인덱스
두 개(`k_ten`, `k_cust`)가 달려 있어 **INSERT 도중에 같이 만들어진다.** SF=0.5 에서는
그 인덱스가 262MB 라 1GB 버퍼 풀 안에 들어가 랜덤 삽입이 전부 메모리에서 끝났다.
SF=10 이면 5GB 가 넘으므로 행마다 디스크로 나간다 — **계단이지 기울기가 아니다.**

**이 랩이 §T-2·§T-3 에서 문서화한 바로 그 교차점을, 그걸 적은 스크립트가 밟았다.**
계수를 두 점으로 맞추면서 그 두 점이 **같은 캐시 영역 안에 있다는 것**을 안 봤다.
외삽하려면 최소한 경계 반대편에 점이 하나 있어야 했다.

→ 고친 것: 복사본의 보조 인덱스 추정치(`NROW/3M × 262MB`)를 `@@innodb_buffer_pool_size`
  와 견주어, 넘으면 **시간을 추정하지 않는다.** "몇 시간 단위를 각오해야 한다"고 말하고,
  선형식 값은 "그 식은 여기서 무효다"라는 꼬리표를 달아 참고로만 보여 준다.
  진행을 볼 방법도 같이 찍는다 — `information_schema.INNODB_TABLESPACES` 의 `FILE_SIZE`
  가 차는 속도다(`ROWS_EXAMINED` 는 실행 중에 0 으로 나와 못 쓴다. 확인했다).

SF=10 기준 출력: 디스크 37GB, 보조 인덱스 4,978MB vs 버퍼 풀 1,024MB, `li_a` 목표 11GB.

> **얻을 것과 치를 것.** `FORCE=1` 로 새로 얻는 것은 ①의 `N vs A` 역전 하나뿐인데
> 그건 이미 SF=0.5 에서 확인돼 문서에 있다(N 195ms vs A 303ms). ②·⑥ 은 표본 실행으로
> 이미 다른 버전·다른 규모에서 재현됐다. **10시간을 들여 살 것이 없다** — 중단을 권했다.

실제 경과(사용자 환경, SF=10 전체): `INSERT INTO li_a` 가 **7,388초(2시간 3분)에 10.60GB**,
목표 11.9GB 의 89%. 그게 **네 단계 중 첫 단계**다. 그리고 남은 것 중 마지막이 제일 나쁘다 —
C(테넌트별 DB 25개)는 `SELECT * FROM li_a WHERE l_nationkey=$n` 을 25번 도는데, 이건
**②에서 7.8배로 측정한 바로 그 흩어짐 패턴**이다. 12GB 테이블을 1GB 버퍼 풀로 6,000만 번
랜덤 접근한다. SF=0.5 에서 56초였던 단계가 여기서는 시간 단위가 될 수 있다.

#### ONLY 가 준비를 안 줄이고 있었다

위를 계산하다 보니 드러났다. `ONLY=2`(A vs A′ 만 본다)로 돌려도 **파티션 25개와 DB 25개를
다 만들고 있었다.** 규모가 작을 때는 안 보이지만 SF=10 에서는 그 둘이 준비 시간의 대부분이다.

→ 절별로 필요한 복사본만 만든다: `① 전부 · ② A·A′ · ③ A · ④ 전부 · ⑤ (없음) · ⑥ A·A′·B`.
  SF=0.5 실측으로 전부 215초 → `ONLY=2` 91초 → `ONLY=5` 0초.
  ⑤는 `CREATE TABLE` 이 `ERROR 1503` 으로 거절당하는 것을 보는 절이라 복사본이 하나도 필요 없다.

> 곁가지로 하나 배웠다. 테스트하면서 `... | head -22` 로 출력을 잘랐더니 SIGPIPE 로 스크립트가
> 죽어 **정리가 안 돌았고**, 남은 `li_*` 2개를 스크립트 버그로 의심했다. 정리 코드는 멀쩡했다.
> **출력을 자르는 것만으로 스크립트의 뒷정리를 건너뛸 수 있다** — `head` 로 확인할 때는
> 잔여물 검사를 같이 믿으면 안 된다.

### 멀티테넌시 분리 훈련 — 책 밖 주제, `scripts/tpcds/mt-tenant-isolation.sh` (§X-1)

매장을 테넌트로 삼아(12개, 200만 행) A 공유 테이블(+RLS) / B LIST 파티션 / C 테넌트별 스키마를
같은 데이터·같은 인덱스 정책으로 만들고 여섯 가지를 잰다. 약 2분, 끝나면 전부 지운다.

- **① 단일 테넌트 조회는 안 갈린다** (2.6 / 2.8 / 2.7 / 1.8 ms). 전략 선택 기준이 아니다.
- **② RLS 1.00x.** 정책 조건이 `Index Cond` 로 들어가 복합 인덱스를 그대로 탄다.
- **③ 파티션은 격리가 아니다.** 조건 없는 조회가 A·B 는 200만 행, RLS·C 는 166,658 행.
- **④ "테넌트 선두 복합 인덱스"는 가로지르는 질문에 없는 것과 같다.** A 는 Parallel Seq Scan
  40.7ms, B/C 24.5/13.1ms. A 에 날짜 인덱스를 더 주면 22.5ms 가 되지만 인덱스 27MB vs 14MB.
- **⑤ DDL 팬아웃** — C 는 인덱스 하나에 DDL 12번. B 는 1번에 자동 전파.
- **⑥ 시끄러운 이웃을 둘로 나눠 쟀다.** 순수 CPU 이웃(4세션)에서는 A·C 모두 느려진다(1.39x /
  1.14x, 차이는 편차 안) — 이름공간 격리는 자원 격리가 아니다. 테넌트 집계 이웃에서는 A 만
  1.35x 느려진다 — 테넌트 7 의 행이 힙 18,752 페이지 중 **16,404 페이지에 흩어져** 이웃 조회가
  10배의 페이지를 워커 3개로 훑기 때문이다. B 의 1.20x 는 같은 1,558 페이지인데 병렬 계획을
  받아 워커를 띄운 탓이고(같은 크기의 C 는 직렬), 이건 비용 모델의 임계 문제라 규칙으로 옮기지 않았다.

**tpch 판 — `scripts/tpch/mt-tenant-isolation.sh`.** 같은 주제의 **다른 질문**이라 복제가 아니다.
tpcds 는 테넌트(매장)가 팩트에 직접 있지만, tpch 는 테넌트(국가)가
`lineitem → orders → customer` 로 2조인 떨어져 있다. 그래서 RLS 를 쓸 컬럼도 파티션 키도 없고,
**비정규화가 격리의 전제 조건**이 된다. 전략은 N(정규화) / A(비정규화) / B(A+파티션 25) / C(스키마 25).

- **① 여기서는 갈린다** — N 99.5ms (조인 2개) vs A 61.7 / B 31.0 / C 23.7ms.
  tpcds 에서는 ①이 전략 무관 2~3ms 였다.
- **③ RLS 가 구조적으로 불가능하다** — `CREATE POLICY ... USING (l_nationkey = 1)` 이
  `column does not exist` 로 실패한다. 조인 정책은 가능하지만 계획에 노드 4개를 밀어 넣고,
  그 비용이 그 테이블을 읽는 모든 쿼리에 붙는다.
- **⑤ 테넌트 이동 — tpcds 에 없던 축이고 tpch 판의 핵심.** 고객이 국가를 옮기면:
  N 0.164ms(customer 1행) vs A 1.811 / B 1.106~1.577ms. **N 이 압도한다** — ①에서 2조인 값을
  치른 정규화가 여기서는 정확히 그 이유로 이득이다. 행이 실제로 파티션을 넘는다(DELETE+INSERT).
  프루닝 가치는 인덱스에 달렸다: `o_custkey` 인덱스가 있으면 1.4배, 없으면 **18배**
  (277.3ms vs 15.2ms). §T-3 의 "NL 이 무너지는 건 안쪽 인덱스의 부재"와 같은 구조.
- **⑥** N 652.8 / A 229.7 / B 282.8 / C 186.4ms, C 는 쿼리가 1,978자(`UNION ALL` ×25).
  (SF=0.5 고정 순서 값이다. **"C 가 제일 빠르다"는 부분은 뒤에서 정정됐다** —
  아래 "고친 스크립트의 SF=10 결과" 절.)

→ 두 판을 같이 읽으면 **"테넌트 키가 팩트 행에 있는가"가 먼저 답해야 할 질문**이라는 게 나온다.
없으면 격리 전략 선택 문제가 아니라 비정규화 여부의 문제이고, 그 결정은 §T-9 의 계산으로
돌아간다 — ⑤가 보여주듯 전파 비용이 조회 이득을 넘어서는 워크로드도 있다.

**MySQL / InnoDB 판 — `scripts/tpch/mt-tenant-isolation-mysql.sh`.** 앞의 두 판이 "테넌트 키가
팩트에 있는가"를 물었다면 이 판은 **"엔진이 바뀌면 같은 전략이 같은 값을 갖는가"** 를 묻는다.
같은 데이터(lineitem 300만)·같은 메모리(buffer pool 1GB = shared_buffers 1GB)로 맞췄다.
전략에 **A′(테넌트를 PK 선두로)** 가 하나 더 생긴다 — PostgreSQL 에서는 없는 구분이다.

- **① 순서가 뒤집힌다.** N 195ms < A **303ms**. 비정규화를 하고도 느려졌다.
  InnoDB 보조 인덱스는 행 위치가 아니라 **PK 값**을 담으므로 A 는 12만 번 클러스터드 인덱스를
  되찾아간다. A′ 46 / B 52 / C 39ms. PostgreSQL tpch 판(N 이 제일 느림)과 반대다.
- **② 클러스터드 PK 가 6배** — A 287ms vs A′ 48ms. tpcds ⑥의 "흩어짐"을 PostgreSQL 은
  `CLUSTER`(일회성)로 풀었지만 InnoDB 는 PK 설계로 **상태가 유지된다.**
- **③ RLS 가 없다.** 뷰에 세션 변수를 직접 못 쓴다(`ERROR 1351`) → 저장 함수를 한 겹 끼운다.
  핵심은 **격리가 정책이 아니라 권한에서 나온다**는 것 — 앱 계정이 원본 테이블 SELECT 권한을
  갖는 순간 방어가 사라진다. PostgreSQL RLS 는 테이블에 붙어 누가 오든 적용된다.
- **⑤ 파티션 키는 모든 유니크 키에 포함돼야 한다**(`ERROR 1503`). 그래서 "테넌트로 파티션" =
  "테넌트를 PK 에" = "물리 배치 변경"이 **하나로 묶인다.** PostgreSQL 에서는 셋이 독립이었다.
- **⑥ ②의 청구서, 단 규모에 따라.** 점 이동(119행)은 네 전략이 사실상 같다(0.97~5.13ms).
  대량 이관(121,257행)에서 갈린다 — A 4,426 vs A′ **6,791ms**, **A′ 가 보조 인덱스를 하나 더
  적게 갖고도 1.5배 느리다.** PK 를 바꾸는 UPDATE 는 제자리 수정이 아니라 클러스터드 인덱스
  삭제+삽입이고 보조 인덱스 엔트리도 새 PK 로 고쳐야 한다.
- MySQL 은 스키마 = 데이터베이스라 C(테넌트별 스키마)와 D(테넌트별 DB)의 경계가 흐리다.

→ **테넌트를 PK 선두에 놓는 결정은 테넌트가 잘 안 바뀔 때만 옳다.** ②의 6배와 ⑥(나)의 1.5배를
워크로드 비율로 저울질해야 한다. tpcds 의 매장이면 좋고, 고객의 국가처럼 움직이면 다시 생각한다.

환경 메모: 이 컨테이너에 Docker 데몬이 없어 **MySQL 8.0.46 을 apt 로 호스트에 직접 설치**했다
(PostgreSQL 과 같은 방식). `mysqld_safe --user=mysql` 로 띄우고 `/etc/mysql/mysql.conf.d/zz-lab.cnf`
에 `innodb_buffer_pool_size=1G`, `local_infile=ON` 을 넣었다. 적재는 JDBC 대신
`LOAD DATA LOCAL INFILE` 로 했다(.tbl 은 `FIELDS TERMINATED BY '|' LINES TERMINATED BY '|\n'`).
lineitem 3,000,491 행으로 PostgreSQL 쪽과 정확히 같다.

**MySQL 판에서 자초한 함정 하나**: ⑥을 벽시계로 한 번씩 쟀더니 네 전략이 29~37ms 로 다 같아
보였다 — mysql 클라이언트 연결 비용 25~30ms 가 4ms 짜리 작업을 삼킨 것이다. PostgreSQL tpch
판에서 **똑같은 실수를 이미 기록해 두고도 반복했다.** MySQL 8.0 의 `EXPLAIN ANALYZE` 는 UPDATE 를
지원하지 않아(`<not executable by iterator executor>`) 그 길도 막혔고, **한 연결 안에서 N회
반복하고 서버 시각으로 나누는** 방식으로 해결했다. → 엔진이 바뀌면 측정 도구도 다시 골라야 한다.

**tpch 판에서 자초한 함정 둘** (둘 다 "측정이 아니라 관측 방법"의 문제였다):
1. `information_schema.columns WHERE table_name='lineitem'` 로 컬럼을 셌더니 C 가 만든
   `mt_n*.lineitem` 25개가 같이 잡혀 **"l_nationkey 가 25번"** 이라는, 그 절의 결론과
   정반대인 출력이 나왔다. `table_schema='public'` 을 걸어 고쳤다.
2. 테넌트 이동을 **벽시계로** 쟀더니 네 전략이 42~47ms 로 다 같아 보였다 — psql 연결
   오버헤드 약 30ms 가 1ms 짜리 차이를 통째로 삼킨 것이다. "차이 없음"으로 쓸 뻔했고,
   `EXPLAIN (ANALYZE)` 의 서버 실행시간으로 바꾸니 0.164 vs 1.8ms 로 11배가 드러났다.
   → 밀리초 단위를 비교할 때 벽시계는 도구가 아니다.

**자기 함정 셋** (tpcds 판, 문서 §X-1 끝에도 적었다):
1. 순수 CPU 이웃 `sum(i*i)` 가 int4 를 넘쳐 pgbench 가 exit 2 로 조용히 죽었고, 이웃 없이 잰
   "감소 없음"이 한 번 결과로 나왔다. 이웃 프로세스의 종료 코드를 검사하게 고쳤다.
2. 정리 SQL 을 한 `-c` 에 몰아 보냈더니 `DROP ROLE` 이 "권한이 남아 있다"로 실패하며
   **앞의 DROP TABLE 까지 롤백**됐다. 정리가 한 번도 안 되고 두 번째 실행이 첫 실행의 테이블을
   재사용했다 — ⑤가 "인덱스가 이미 있다"로 41ms 에 끝나서 드러났다. 문장을 나누고
   `DROP OWNED BY` 를 먼저 하도록 고쳤고, 준비 단계에 행수 검사를 넣었다.
3. B 의 이웃 효과를 "파티션 잠금 비용"이라 쓰려다 `-M prepared` 에서도 그대로여서 접었다.
   대기 이벤트를 0.1초 간격으로 표본 추출해 B 에만 `IPC:BgWorkerShutdown` 이 16% 나오는 것을
   보고 병렬 워커라는 것을 알았다. 원인을 짐작으로 적지 않고 재서 다행이었다.

**네 번째 칸 — `scripts/tpcds/mt-tenant-isolation-mysql.sh` (TPC-DS × MySQL/InnoDB).**
2×2 를 채우는 마지막 판이다. 질문: **PostgreSQL 이 `CLUSTER`(일회성)로 풀던 흩어짐을 InnoDB 에서
PK 설계로 없앨 수 있는가, 그리고 그것으로 충분한가.** tpcds 의 테넌트는 매장이라 tpch 판이 받았던
청구서(테넌트 이동)가 없다 — 이상적인 조건이다. 전략 A(원본 PK+보조 인덱스) / A′(테넌트가 PK 선두)
/ B(A′+LIST 파티션 12) / C(테넌트별 DB 12). 2분 13초, 끝나면 전부 지운다(남은 객체 0 확인).

- **① 좁은 범위(한 매장의 한 달)는 안 갈린다** — A 38 / A′ 50 / B 40 / C 42ms. 오히려 A′ 가
  조금 느리다. 보조 인덱스 `(store, date)` 가 이 질문에 딱 맞기 때문이다. **물리 배치는 좁은
  범위에서 값을 못 낸다** — ①은 전략 선택의 근거가 못 된다.
- **② 범위를 넓히면(한 매장 전체) A 365ms vs A′ 51ms, 7배.** 그리고 정체를 증명했다 — A 에
  커버링 인덱스 `k_cover(ss_store_sk, ss_net_profit)` 를 주니 **50ms**. 즉 비용은 행 수가 아니라
  **클러스터드 인덱스 되찾기 횟수**다. PostgreSQL 은 같은 문제를 힙 페이지 분산(16,404/18,752,
  `ctid`)으로 쟀지만 InnoDB 엔 힙이 없다 — 같은 병이 다른 지표로 나타난다.
- **③ 가설이 반증됐다 — 절을 그 기록으로 다시 썼다.** "이웃이 A′ 에서 6배 싸니 피해도 줄 것"으로
  썼는데, 재 보니 이웃 1회 384→60ms(6.3배 싸짐)인데 피해자 지연 증가분은 +0.0100s→**+0.0130s**
  로 늘었다. 부하는 `비용 × 빈도`인데 고정 횟수로 도는 이웃은 싸질수록 더 자주 때린다.
  엄밀히는 **'같은 이웃'을 비교한 것이 아니어서** 통제된 비교가 애초에 불가능하다. 비율 대신
  증가분(절대값)으로 읽어야 한다(A′ 는 피해자 자신이 더 느려 분모가 다르다).
  → 남는 결론: **물리 배치는 넓은 범위 한 방을 싸게 만들지, 이웃 문제를 풀지 않는다.**
- **④** A·A′·B 전부 2,000,000행 유출(내 몫 166,658). 격리는 테넌트별 DB 와 뷰+권한뿐,
  앱 계정이 원본 직접 접근하면 `ERROR 1142`. 네 칸 전부 **파티션은 격리가 아니다.**
- **⑤ 같은 `ERROR 1503`, 다른 대가.** tpch 에서는 이 제약이 강제한 선택의 청구서가 대량 이관
  1.5배였는데, tpcds 에서는 매장이 안 움직여 청구서가 없다 — 제약이 손해가 아닌 드문 경우.
- **⑥ 그 전제를 데이터로 확인** — `매장수 12 / 팩트에_등장하는_매장 12 / SCD_이력컬럼 2`.
  `store` 에 `s_rec_start_date`·`s_rec_end_date` 가 있다 = **SCD Type 2** = 속성이 바뀌면 새 행을
  추가하지 기존 매출의 `ss_store_sk` 를 옮기지 않는다. 사실상 불변 축이다.
  → 이 칸이 네 조합 중 **PK 선두 전략이 가장 잘 맞는 자리**다.

**이 판에서 자초한 함정 둘:**
1. **한글 별칭을 백틱 없이 써서 ⑥이 `ERROR 1064` 로 깨졌는데, 그 아래 결론 문장은 그대로
   적혀 있었다.** 즉 한 번도 돌아본 적 없는 쿼리의 결과를 단정하고 있었다. 백틱으로 고치고
   실패를 삼키지 않도록(`2>/dev/null` 제거) 바꿨다 — 근거가 없어지면 주장도 멈춰야 한다.
2. ③에서 **측정이 내가 쓴 결론과 반대로 나왔다.** 고치고 싶은 유혹이 있었지만 원인을 파고드니
   측정 설계 자체의 한계였고(고정 횟수 부하), 결과를 바꾸는 대신 **가설 반증 기록으로 절을 다시
   썼다.** 문서 §X-1 과 스크립트 주석 양쪽에 그대로 남겼다.

**네 칸 전부에서 같았던 것 셋** — 파티션은 격리가 아니고, 격리는 권한 경계에서만 나오며,
시끄러운 이웃은 어떤 물리 배치로도 안 풀린다. 나머지는 전부 칸에 따라 값이 바뀐다.

### 정정 — buffers 열이 큰 규모에서 **틀린 값**을 찍고 있었다 (스크립트 8곳)

사용자가 SF=10(lineitem 6,000만)에서 `tpch/mt-tenant-isolation.sh` 를 돌린 출력에서 드러났다.
①의 buffers 가 시간과 전혀 안 맞았다 — A 가 **113 buffers 인데 1,121ms**, C 가 72 buffers 인데 113ms.

**원인: `grep -m1 -oE 'shared hit=[0-9]+...'`.**
PostgreSQL 은 **값이 0 인 항목을 아예 생략한다.** 테이블이 `shared_buffers` 보다 훨씬 크면
top 노드가 `Buffers: shared read=739268` 처럼 `hit=` 없이 나오고, 그러면 이 정규식이 그 줄을
**건너뛰어 더 깊은 노드**(예: Bitmap Index Scan 의 `hit=113`)를 집는다.
에러가 없으니 **작은 숫자가 그냥 결과처럼 보인다.**

SF=0.5 에서는 대부분 캐시에 있어 `hit=` 이 늘 있었기 때문에 여태 안 드러났다. 고친 뒤 같은
자리에서 `C 스키마 … hit=0 read=1536` 이 찍히는 것으로 기전이 확인됐다 — 옛 정규식이라면
이 줄을 통째로 건너뛰었을 값이다.

**8곳 전부 고쳤다** (첫 `Buffers: shared` 줄을 잡고 hit/read 를 각각 0 기본값으로 읽는다):
`tpch/mt-tenant-isolation.sh` · `tpcds/mt-tenant-isolation.sh`(2곳) · `tpch/t2-selectivity-sweep.sh` ·
`tpch/t2-crossover-verify.sh` · `tpch/join-method-compare.sh` · `tpcds/t9-preaggregation.sh` ·
`tpcds/t2-selectivity-sweep.sh`.

> **영향 범위:** 문서에 실린 buffers 수치 중 **shared_buffers(1GB)보다 큰 대상을 읽은 것**은
> 다시 재야 한다. SF=0.5 실측(lineitem 478MB)은 대부분 캐시 적중이라 영향이 없지만,
> §T-8 의 500,750 → 349,914 같은 큰 값은 top 노드에 `hit=` 이 있었는지 확인이 필요하다.
> **시간과 buffers 가 같은 방향으로 안 움직이면 그 열을 의심하라**는 것이 이번 교훈이다.

### mt-tenant-isolation ①⑥ 을 교차 측정으로 — 세 가지 결함을 한꺼번에

SF=10 출력을 세 번 받아 보고 드러난 것들이다. 셋 다 **이 랩이 이미 원칙으로 적어 둔 것을
스스로 안 지킨** 경우였다.

1. **시간과 buffers 를 다른 실행에서 재고 있었다.** `best_ms` 는 워밍업 뒤 4회 최소값인데
   `bufs_of` 는 따로 돌았고, bash 가 인자를 왼쪽부터 평가하므로 **buffers 가 먼저(콜드),
   시간이 나중(웜)** 이었다. SF=10 에서 A·B·C 가 전부 `hit=0` 으로 찍힌 것이 그 증상이다.
2. **고정 순서, 교차 없음.** N → A → A+RLS → B → C 를 한 번씩 돌았다. 앞 전략이 캐시를
   밀어내 뒤가 불리해지는데 그 차이를 전략 탓으로 읽게 된다(§T-0 원칙 6).
   실제로 한 실행에서 **A+RLS 가 A 보다 빨라** 보였다 — 물리적으로 불가능한 값이다.
3. **편차를 안 찍었다.** 최소값만 주면 "이 차이가 노이즈 안인가"를 읽는 사람이 판단할 수 없다.
   사용자가 같은 스크립트를 세 번 돌려서야 노이즈 폭이 약 ±10% 라는 걸 알 수 있었다 —
   **그건 표가 해 줬어야 할 일이다.**

→ `measure_set` 을 넣어 셋을 한꺼번에 고쳤다. 한 번의 `EXPLAIN (ANALYZE, BUFFERS)` 에서
  시간과 buffers 를 같이 뽑고(`one_run`), 라운드마다 전략을 **교차**하며, 최소 시간이 나온
  **그 실행의** buffers 와 `(최대−최소)/최소` 를 ±% 로 함께 찍는다. ①과 ⑥ 모두 적용했다.

**효과가 바로 나타났다** — A 와 A+RLS 의 buffers 가 `hit=21576 read=0` 으로 **완전히 같게**
찍힌다. RLS 오버헤드를 시간(노이즈에 묻힌다)이 아니라 **접근량**으로 말할 수 있게 됐다.

> **교차는 공짜가 아니다.** 순서 편향은 없앴지만 전략들이 서로 캐시를 밀어내 편차가 커진다 —
> SF=0.5 에서 N 이 ±214~326% 로 찍힌다(원본 14GB 를 훑어 다른 전략의 캐시를 날린다).
> 이건 고장이 아니라 **그 수치가 원래 그만큼 불안정하다는 보고**다. 고정 순서로 재면 편차가
> 작아 보이지만 그건 순서가 만든 안정성이라 더 나쁘다 —
> **안 보이는 편향보다 보이는 편차가 낫다.** 그래서 스크립트가 그 문장을 같이 찍는다.

### 고친 스크립트의 SF=10 결과 — 예측 하나가 맞고, 옛 결론 하나가 틀렸다

사용자가 고친 스크립트로 SF=10 을 돌린 최종 출력이다. 문서(§X-1 tpch 판 ①⑥)에 반영했다.

① N 3,291.3 ±14% (hit 383,882 + read 1,645,148) / A 1,279.5 ±23% (read 424,670) /
A+RLS 1,313.2 ±10% (read 424,670) / B 119.4 ±12% (read 29,391) / C 114.6 ±6% (read 29,440)

⑥ N 9,373.6 ±6% (1,533,670) / A 2,674.2 ±11% (740,132) / B 4,018.7 ±14% (740,153) /
C 2,604.4 ±22% (741,024)

- **예측이 맞았다** — 교차 측정을 넣으며 "편차가 큰 것은 고장이 아니다"라고 적으면서
  달았던 단서, 즉 데이터가 `shared_buffers` 보다 훨씬 커지면 교차의 벌이 사라진다는 것.
  N 의 편차가 SF=0.5 의 ±214~326% → SF=10 의 **±14%** 로 내려앉았다. 아무도 캐시에
  못 남으면 서로 밀어낼 것도 없다.
- **A vs A+RLS 가 SF=10 에서도 buffers 바이트 동일**(read 424,670). 시간 차 2.6% 는
  편차 안이라 주장하면 안 되고, 접근량으로 말하면 **정확히 0** 이다.
- **A vs B/C 14.4배**(424,670 : 29,391). SF=0.5 에서 14.3배 — 스케일 불변이므로
  캐시도 계획도 아닌 **구조적 페이지 흩어짐**이다.
- **⑥ B/A = 1.50배인데 buffers 는 0.003% 차이.** 읽는 양을 통제했더니 남은 1.50배가
  파티션 `Append` 자체의 값으로 분리됐다. ①에서 B 를 14.4배 빠르게 한 그 파티션이
  전 테넌트 질문에서는 반대로 청구한다.

**정정 — "⑥에서 C 가 제일 빠르다"는 내가 쓴 결론이 측정 노이즈였다.** SF=0.5 고정 순서
단발 측정에서 C 186.4 vs A 229.7 ms(19% 차)로 적어 뒀는데, SF=10 교차 측정에서
C 2,604 ±22% 와 A 2,674 ±11% 는 구분되지 않는다. 게다가 C 는 `UNION ALL` 25갈래가 각각
상수 nationkey 를 달아 **`GROUP BY` 를 구조적으로 건너뛴다** — A 와 같은 쿼리 모양이
아니므로 애초에 like-for-like 비교가 아니었다. **⑥에서 깨끗한 비교는 A vs B 뿐이다.**

같은 실수를 §4(NOTIFY vs 폴링 ⑥)에서도 했다. 고정 순서 + 단발이면 어느 절에서든 같은
착시가 나온다는 뜻이라, 새 절을 쓸 때 교차 측정을 기본값으로 삼는다.

### ⑥의 N 이 SF=10 에서 죽는다 — 공유메모리 한계

같은 실행에서 ⑥의 N(6천만 행 × 2조인)이 이렇게 죽었다:

```
ERROR: could not resize shared memory segment "/PostgreSQL.2552065148"
       to 268435456 bytes: No space left on device
```

디스크가 아니라 **`/dev/shm`(동적 공유메모리)** 이다. 이 스크립트는 `WORK_MEM=4096MB` 로 도는데,
병렬 해시가 워커마다 256MB 세그먼트를 잡으려다 넘긴 것이다. A·B·C 는 단일 테이블이라 병렬
해시를 안 써서 멀쩡히 돌았다 — **N 만 못 잰 것이고, 데이터나 계획의 문제가 아니라 환경 한계다.**

**정정 — 처음 준 처방(`WORK_MEM=512MB`)이 틀렸다.** 사용자가 그대로 돌렸는데 **같은 256MB
세그먼트를 요구하며 똑같이 실패했다.** 원인을 다시 잡으면: PostgreSQL 의 DSA 는 세그먼트를
1MB 에서 시작해 **배로 키우며**(…64→128→256MB) 잡으므로, 요구 크기는 `work_mem` 이 아니라
**총 할당량**이 정한다. `work_mem` 을 낮춰도 같은 계단을 밟는다. 실제 제약은 `/dev/shm` 의 여유다.

→ 스크립트를 이렇게 고쳤다:
- 원인을 DSA 배증으로 정확히 적고, **"work_mem 을 낮춰도 안 된다"를 명시**한다.
- 확인 명령(`df -h /dev/shm`, `ls -la /dev/shm` — 죽은 실행이 남긴 `PostgreSQL.*` 누적 확인)과
  처방(`mount -o remount,size=8G /dev/shm`, `--shm-size`, `dynamic_shared_memory_type='mmap'`)을 찍는다.
- **그래도 숫자를 남긴다** — `max_parallel_workers_per_gather=0` 으로 다시 재서 표에
  `(직렬 강제)` 라고 **표시하고** 싣는다. 조건이 다르므로 다른 행과 직접 비교하면 안 된다는
  경고도 같이 찍는다. 실패를 삼켜 `?` 만 남기는 것보다, **조건을 밝힌 값**이 낫다.

> 교훈: 환경 한계로 못 재는 칸이 생겼을 때 선택지는 셋이다 — 비워 두기 / 조건을 바꿔 재고
> 표시하기 / 고장 난 값을 그냥 싣기. 셋째만 하면 안 되고, 첫째보다 둘째가 낫다.

**이어서 — buffers 와 시간이 서로 다른 캐시 상태였다.**
버그를 고치고 다시 돌린 SF=10 출력에서 A·B·C 가 전부 `hit=0` 으로 찍혔다. 원인은 측정 구조다:
`best_ms` 는 워밍업 뒤 4회 최소값인데 `bufs_of` 는 **워밍업 없이 한 번**만 돌고,
`printf` 인자 평가 순서상 **`best_ms` 보다 먼저** 실행된다. 그래서 buffers 열은 가장 차가운
실행이고 시간 열은 데워진 실행이었다 — **두 열이 같은 실행을 설명하지 않았다.**

→ `bufs_of` 가 한 번 버리고 두 번째를 읽게 고쳤다(tpch·tpcds MT 양쪽).
  SF=0.5 에서 `hit=21576 read=0` 처럼 제대로 잡히는 것으로 확인했다.

> 접근량 비교(총 블록 수)만 보면 차가운 값도 쓸 수 있지만, **hit/read 구분이 의미를 가지려면
> 두 열이 같은 조건이어야 한다.** "buffers 가 많아서 느리다"를 주장하려면 더욱 그렇다.

**재정정 — 진짜 원인은 `docker-compose.yml` 의 `shm_size: 1g` 였다.**
"`/dev/shm` 여유를 보라"는 두 번째 처방도 빗나갔다. 사용자가 확인해 보니 호스트는
**63GB 중 62GB 가 비어 있었고 고아 세그먼트도 없었다.** 그런데도 PostgreSQL 이 256MB 를
못 얻었다 — **그 사실 자체가 PostgreSQL 이 그 `/dev/shm` 을 안 보고 있다는 증거**다.
단서는 출력의 `libpod_lock` 이었다(호스트에서 podman/docker 를 쓴다는 뜻). 컨테이너 안의
`/dev/shm` 은 호스트와 **별개**이고, 이 저장소의 compose 가 `shm_size: 1g` 로 묶고 있었다.

DSA 는 세그먼트를 1MB 부터 배로 키우며 잡고 **이전 것을 그대로 둔다** — 256MB 하나를 얻으려면
누적 511MB 가 이미 잡혀 있어야 하고, 조인마다 Parallel Hash 노드가 붙으니 곱으로 늘어난다.
SF=0.5 에서는 1g 로 충분했고 SF=10 에서 부족해진 것이다.

→ `docker/docker-compose.yml` 의 `shm_size` 를 **8g** 로 올리고, 왜 그 값이고 규모와 어떻게
  연동되는지 주석으로 붙였다. 스크립트의 진단도 **"호스트가 아니라 컨테이너 안을 보라"**
  (`docker exec <컨테이너> df -h /dev/shm`)로 고쳤다.

> **세 번 틀리고 네 번째에 맞혔다. 빗나간 순서가 그대로 교훈이다** —
> ① `work_mem` 탓(실행이 반증), ② 호스트 `/dev/shm` 부족 탓(실측이 반증),
> ③ 고아 세그먼트 탓(실측이 반증), ④ **컨테이너 경계**.
> 공통점은 셋 다 **"어느 네임스페이스의 자원인가"를 안 물은 것**이다.
> 컨테이너에서 나는 자원 에러는 호스트 수치로 판정하면 안 된다.

### §T-2/T-4 확장 — 인덱스를 만들었더니 느려진 두 쿼리 (`scripts/tpch/t2-index-regression.sh`)

**사용자가 SF=10 에서 `index` 명령 전후를 돌려 보낸 결과에서 시작됐다.** 둘이 뒤집혔다 —
q06 1,077 → 2,477ms(2.30배), q13 11,489 → 27,865ms(2.43배). 나머지는 같거나 좋아졌다
(q09 13.1배, q05 1.79배, q18 1.67배). **깨지는 방식이 둘 다 다르다.**

- **① q06 — 전환점 밖 + lossy 비트맵.** `Parallel Seq Scan` → `Parallel Bitmap Heap Scan`.
  `l_shipdate` 1994년 범위가 **15.1%** 로 전환점 밖인데 인덱스를 골랐고, 거기에 더해 TID 비트맵이
  `work_mem` 을 넘겨 페이지 단위로 뭉개졌다: `exact=138,270 / lossy=123,836`,
  `Rows Removed by Index Recheck: 4,291,203`. buffers 는 비슷한데 I/O 가 1,361 → 3,075ms.
  → **갈림길이 둘이고 처방이 다르다**(인덱스를 쓰지 마라 vs 제대로 쓰게 하라). 2×2 로 잰다.
  SF=0.5 에서도 **1.79배 악화가 재현된다**(218 vs 122ms) — 선택도는 규모와 무관하므로.
  다만 lossy 는 안 생긴다(비트맵이 64MB 에 들어간다) → 그때는 (나) 갈림길이 없다는 뜻이고,
  스크립트가 `lossy 블록` 열로 그걸 알려 준다.
- **② q13 — 인덱스가 조인 방식을 갈아치웠다.** `Hash Right Join` → `Merge Left Join` +
  `Index Scan using idx_orders_custkey`. buffers **30만 → 1,500만(48배)**, I/O 만 14.4초.
  필터가 99.1% 를 통과시키니 사실상 전체 스캔인데 거기에 인덱스 순서 접근을 붙인 것이다.
  → **전체를 읽는 쿼리에 인덱스 순서 접근을 붙이면 진다.** 손해가 행수에 비례하므로
  **SF=0.5 에서는 재현되지 않는다**(플래너가 Merge 경로를 안 고른다).
  그래서 스크립트가 기본 계획의 조인 방식을 보고 **"이 규모에서는 재현되지 않았다"를 먼저 찍는다** —
  작은 규모의 "문제 없네"를 결론으로 쓰지 않게 하기 위해서다.
- **q13 의 손잡이는 둘이고 독립이다.** 인덱스만 문제가 아니라 **q13 은 인덱스가 있든 없든 직렬**이다
  (§T-6 확장 ①). 그래서 ②를 2×2 로 만들었다 — A(`enable_indexscan=off`, 계획 되돌리기) ×
  B(`parallel_tuple_cost=0.01`, 병렬 얻기). SF=0.5 실측: A 0.93x / B **2.10x** / A+B 2.02x.
  A 쪽 함정이 이 규모에서는 재현되지 않아 A 가 되돌릴 것이 없고, 오히려 `customer_pkey` 의
  Index Only Scan 까지 막혀 buffers 가 는다(15,361 → 17,298). **B 는 규모와 무관하게 값을 낸다** —
  직렬 판정을 정하는 것은 선택도가 아니라 그룹 수이기 때문이다.
  → 스크립트가 `A단독 × B단독` 의 곱과 실제 `A+B` 를 나란히 찍어 **두 손잡이가 독립인지 숫자로
  판정**하고, A 가 값을 못 내면 그 이유(함정 미재현)를 바로 아래에 연결해 준다.
  `parallel_tuple_cost` 는 `0.05` 로는 안 켜지고 `0.01` 에서 켜졌다 — 값은 환경마다 다르므로
  워커 열로 확인한다.
- **③ 대조군.** q06 최종 통과율 1.9% / q13 99.1% / q09 5.5%.
  → **인덱스가 값을 내는 조건은 "필터가 선택적인가"가 아니라 "인덱스가 그 선택성을 아는가"다.**
  q06 은 최종 1.9% 인데 `l_discount`·`l_quantity` 가 인덱스에 없어, 인덱스가 아는 날짜만으로는 15.1% 다.

**부수 확인 — 어제 만든 §T-6 확장의 예측이 셋 다 맞았다:**
- q05 워커가 1 → 4 로 늘었다. 인덱스가 조인 모양을 바꿔 **구동 스캔이 supplier(17MB)에서
  `Parallel Seq Scan on lineitem` 으로 옮겨 갔다** — ②의 "워커 수는 구동 스캔이 정한다" 그대로다.
- q18 의 하위 집계가 **병렬화됐다**(`Partial HashAggregate` + `Gather` + `Finalize`,
  `Parallel Seq Scan on lineitem_1`). ③이 지목한 `loops=5` 중복이 사라져 temp write 가
  30.5GB → 8.2GB. **처방이 실제로 작동하는 경로를 확인한 셈이다.**
- q13 은 인덱스가 생겨도 **여전히 직렬**이다(`Gather` 없음). ①의 `parallel_tuple_cost` 문제가
  그대로고, 이제 28초짜리가 됐다.

> 이 스크립트는 서버 설정을 바꾸지 않는다(세션 `SET` 만). `DROP=1` 로 `idx_orders_custkey` 를
> 실제로 지웠다 만드는 절이 있는데, SF=10 이면 재생성에 수십 초 걸리므로 기본은 꺼져 있다.

### T-9 NOTIFY 경계/적체 — 한 줄 누락이 절 하나를 지우게 했다

§8 에 두 항목으로 남아 있던 것(경계 쓰기율 미측정 / 적체 구간 미재현)을 둘 다 채웠다.
`scripts/tpch/t9-notify-vs-poll.sh` 에 ⑤⑥을 더하고 `ONLY=` 가드를 넣었다.

**⑤ 경계 — 초당 1,000~1,600 커밋 부근.** 폴링 1ms 를 상대로 `-R` 을 50~3200 으로 훑었다.
NOTIFY 왕복은 873 → 2,428 → 3,001 → 1,541 로 오르다 꺾이고, 폴링은 6,759 → 3,436 → 1,564 로
단조 감소해 **-R 1600 에서 만난다.** 정체는 간단하다 — **폴링의 왕복은 시간이 정하고 NOTIFY 의
왕복은 트랜잭션 수가 정한다.** 다만 "1ms 간격 = 초당 1,000회"가 아니다. 왕복 자체에 시간이 걸려
이 장비에서는 약 680회였고, **경계를 정하는 것은 설정값이 아니라 그 실측 왕복률**이다.

**⑥ 적체 — 기전까지 규명했고, 중간에 내가 한 번 틀렸다.**
적체는 쓰기율로 안 만들어진다(이 장비의 pgbench 로는 워커를 못 이긴다). 주문 5,000건을
고객 1에게 몰아 **등급 변경 1건 = 파생 20,000행 갱신**으로 만들었다.

**기전(문장 단위 계측):** `denorm_drain` 을 계측판으로 바꿔 재니 —
고객 등급 전파 UPDATE **9,714ms** / 주문 전파 241ms / lineitem UPSERT 88ms /
큐 claim 43ms / 깊이 count 8ms. **drain 시간의 약 97% 가 한 문장**이다.
그리고 drain 은 한 배치 안의 같은 고객을 `DISTINCT` 로 접어 UPDATE 를 한 번만 한다 →
**총 비용 = (cust 항목이 들어 있던 배치 수) × 회당 비용**, 배치 안에 1건이든 10건이든 같다.

**그런데 세 방식의 그 배치 수가 같다** (110~115), 총 cust 시간도 같다(8.4~8.8초).
합계가 측정 시간 10초에 육박하니 **워커는 100% 포화**이고, 그 상태에서 잔량을 정하는 것은
깨우는 방식이 아니라 **비싼 항목의 도착률 × 항목당 비용**이다.

⚠️ **정정 — ⑥을 한 번 반대로 적었다.** 처음에는 세 방식을 **고정 순서로 1회씩** 쟀고,
항상 맨 앞이던 NOTIFY 가 지연 123~135ms 로 혼자 나빠 보여서 "예상이 반증됐다 — 적체에서
방식 차이가 가장 크게 벌어지고 NOTIFY 가 최악"이라고 썼다. **틀렸다.** 3라운드 교차로
다시 재니 34~37ms 로 셋이 구분되지 않는다(계측판 drain 으로도, 배치 간격 분해로도 동일).
**순서가 만든 값이었고, §T-0 원칙 6(교차 측정)을 스스로 어겨서 생긴 오답이다** —
§T-8 에서 똑같은 실수를 하고 원칙으로 적어 둔 바로 그것이다.
→ **처음 가설이 맞았다: 적체 구간에서는 깨우는 방식이 의미를 잃는다.**
  실무 규칙도 그에 맞춰 바뀐다 — 밀리면 깨우는 방식이 아니라 **항목당 비용**(팬아웃 전파를
  쪼개거나 증분화)이나 **도착률**에 손대야 한다.
→ ⑥을 ROUNDS 라운드 교차 측정으로 고치고, `denorm_stat` 의 배치 간격에서 'cust 포함 배치 수'와
  'cust 합 시간'을 뽑아 **워커를 건드리지 않고** 같은 일을 한다는 증거를 같이 찍게 했다.

**진짜 소득 — 3년 묵은 미스터리의 원인:**
`/tmp/t9n_skew.sql` 에 **`END;` 가 없었다.** `BEGIN;` 으로 열고 커밋이 없으니 매 반복의 쓰기가
연결 종료 시 통째로 롤백된다. 그런데 **pgbench 는 "number of failed transactions: 0" 으로
보고하고 tps 도 정상으로 찍는다.** 그러면 큐가 비고 워커가 아무 일도 안 하는데 출력은
"지연 0 / 왕복 2" 라 **고장이 아니라 결과처럼 보인다.** 예전에 이 절을 원인도 모른 채
통째로 삭제한 이유가 이것이다.
→ 같은 유형이 더 있는지 `t9-*.sh` 의 pgbench 파일 8개를 전부 기계적으로 훑었고(BEGIN 있고
   END 없는 것), **문제는 그 하나뿐**이었다.

**그 밖에 고친 것 셋:**
1. **⑥이 주문 소유자만 되돌리고 파생 테이블을 안 고쳤다.** 그러면 이후 모든 drain 이 "다른 값을
   찾아 고치는" 교정 작업을 떠안아 **⑤의 결과가 통째로 달라진다**(낮은 쓰기율에서도 잔량이 붙었다).
   데이터 원복만으로 부족하고 `full_refill` 까지 해야 절 사이 상태가 안 샌다. 끝에 파생 불일치
   행수를 찍어 확인한다.
2. **반복 실행이 쌓는 부풀음.** 이 실습은 lineitem 에 행을 넣었다 지우기를 수만 번 반복하므로
   여러 번 돌리면 drain 이 느려져 측정이 아니라 누적 상태를 재게 된다. 절 시작에
   `VACUUM (ANALYZE)` 를 넣었다. 왕복 열의 추세와 교차 지점은 그 드리프트와 무관하게 재현된다.

3. **스크립트가 스스로 안 치우고, `restore-lab.sh` 도 못 잡았다.** 실행 뒤 `t_enq_*` 트리거 3개와
   `l_linenumber>=90` 인 lineitem 5,892행이 남았는데 점검은 **"실습 잔여물 없음"** 이었다.
   잔여물 검사가 `t_sync%` 만 보고 `t_enq%` 를 안 봤고, 행수 오염은 아예 항목이 없었다.
   둘 다 검사에 넣고, 스크립트도 끝에 스스로 치우며 남은 수를 찍게 했다.
   (lineitem 행이 3,000,491 → 3,006,383 이 되어 있었다. **에러가 아니라 숫자만 달라지는 오염**
   이라 정확히 `restore-lab.sh` 가 막아야 하는 종류였다 — 정정 8번과 같은 구멍.)

> 이 컨테이너에는 psycopg2 가 없어 `pip install psycopg2-binary` 가 필요하다(워커가 쓴다).

### M-4/6/7 을 MySQL/InnoDB 로 (`scripts/sysbench/m4-m7-mysql.sh`)

sysbench 바이너리가 없어 미실행으로 남아 있던 항목이다(`apt-get install -y sysbench` 로 해결).
같은 세 질문을 InnoDB 에 던졌고, 셋 다 pgbench 판과 **비교 가능한 형태**로 나왔다.

- **① 무릎은 두 엔진 모두 코어 수(4)에 있었다. 증상이 다르다.**
  스크립트가 `직전 TPS×` / `직전 지연×` 를 같이 찍어 무릎을 **데이터가 가리키게** 했다
  (내가 단정하지 않는다). 4→8 에서 처음 `TPS× < 지연×` 가 된다(1.21 vs 1.64).
  다만 pgbench 는 4→8 에서 TPS 가 **줄었는데**(4,642→4,367) 여기서는 안 줄고 32까지 포화한다 —
  `oltp_read_write` 는 14문장 중 10이 읽기라 CPU 가 비는 틈을 추가 스레드가 메운다.
  → **TPS 만 보면 무릎을 못 찾는다.** 포화 구간에서 TPS 는 계속 최고치다.
- **② M-6 — 가설 둘을 세우고 하나를 기각했다.** MySQL 은 커밋마다 redo·binlog **둘**에
  fsync 한다. 2×2 로 재니 둘 다 꺼도 **1.12배**뿐이었다(PostgreSQL 은 2.2배).
  · (가) 그룹 커밋 때문? → **기각.** 쓰기 전용에서 스레드 1이 1.81배, 8이 1.84배로 **같다.**
  · (나) 커밋 비중 때문? → **채택.** 같은 손잡이가 읽기 섞이면 1.18배, 쓰기만 하면 1.84배.
  → **커밋 내구성의 값은 엔진이 아니라 트랜잭션에서 커밋이 차지하는 비율이 정한다.**
    두 벤치마크의 배수를 나란히 놓고 "엔진이 다르다"고 읽으면 틀린다.
- **③ M-7 — 방향이 같다.** `innodb_redo_log_capacity` 는 8.0.30 부터 **동적**이라 재기동이 없다.
  1GB → 8MB 에서 TPS −22%, p99 +36%, **max 25.4ms → 367.1ms(14.5배)**.
  PostgreSQL 은 −12% / +10% / **54배**. 배수는 달라도 모양이 같다 —
  평균은 조금, 최악은 자릿수로. 엔진 문제가 아니라 구조 문제다.

**자초한 함정 둘:**
1. **③에서 압력을 안 만들고 "영향 없음"을 쓸 뻔했다.** 처음엔 기본 워크로드로 1GB vs 64MB 를
   쟀는데 TPS 932 vs 922, max 33 vs 26 으로 차이가 없었다. `Innodb_os_log_written` 이 양쪽
   같았던 게 단서였다 — **64MB 조차 남아돌아 로그를 한 번도 안 감은 것이다.**
   쓰기 전용 + 8MB 로 바꾸니 드러났고, 표에 **redo 기록량 열**을 넣어 압력이 걸렸는지
   독자가 확인할 수 있게 했다. 없는 압력에서의 "영향 없음"은 결과가 아니다.
2. **sysbench 출력 파싱 — 라벨 안의 숫자에 걸렸다.** `grep -oE '99th percentile:[ ]+[0-9.]+'`
   에서 숫자만 뽑으면 `99th` 의 **99** 가 먼저 잡힌다. 그래서 p99 칸에 99 가 들어가고,
   그 값이 개행을 물고 있어 뒤의 max 칸은 아예 비었다. awk 로 필드 위치를 집게 고쳤다.

> 내구성·redo 설정은 **전역**이라 남으면 다른 측정을 조용히 바꾼다. 시작할 때 값을 저장하고
> `trap` 으로 원복하며, 끝에 원래 값과 나란히 찍어 확인한다.

### verify-lab DB-10 (CDC) — `wal_level=logical` 로 올려서 검증 완료

인계노트에 "wal_level 이 replica 라 판정 불가로 남았다"로 있던 항목이다. 올려서 돌렸고
**CONFIRMED**, 검증 항목 4개 전부 통과했다:

- 기본 identity 의 DELETE 에는 PK 만 남는다 — `DELETE: id[integer]:1`
- `REPLICA IDENTITY FULL` 이면 전체 값이 남는다 — `DELETE: id[integer]:2 name[text]:'bob' amount[integer]:200`
- 소비되지 않은 슬롯이 WAL **402,616 바이트**를 붙잡고 있었다(슬롯 활성 여부 false)

**그런데 여기서 두 가지가 더 나왔다.**

1. **자바 주석이 사실과 달랐다.** `ChangeDataCaptureCase` 가 "compose.yaml 에 설정돼 있다"고
   적고 있었는데, `docker/postgres/postgresql.conf` 는 `wal_level = replica` 다. 그래서 이 케이스가
   계속 판정 불가로 남았던 것이다. 주석과 evidence 메모를 사실대로 고쳤다.
2. **`wal_level` 은 성능 설정처럼 안 보이지만 측정 기준이다.** logical 로 올린 채 §T-8 의
   쓰기 비용을 다시 재 봤더니 FPI 제외 WAL 이 네 조건 모두 일정하게 늘었다:

   | 조건 | replica | logical | 차이 |
   |---|---|---|---|
   | ① 기준 | 373 B | 456 B | +83 |
   | ② +(filler) | 424 B | 505 B | +81 |
   | ③ +(abalance) | 473 B | 552 B | +79 |
   | ④ 3개 전부 | 651 B | 729 B | +78 |

   **UPDATE 당 약 80바이트의 상수 오버헤드**다(논리 디코딩용 정보). TPS 는 안 변한다.
   비율도 희석된다 — ④/① 이 replica 1.75배 → logical 1.60배.
   → 그래서 **랩의 기준은 replica 로 유지**하고, DB-10 을 돌릴 때만 일시적으로 올린다.
   그리고 이 드리프트를 `restore-lab.sh` 가 잡도록 `chk wal_level` 을 넣었다 —
   **아무 에러 없이 숫자만 20% 틀리는** 종류라 정확히 그 스크립트가 있는 이유다.

### T-9 격리수준 — `FOR SHARE` 수정본의 나머지 절반 (`scripts/tpch/t9-isolation-levels.sh`)

§8 에 "RR/SERIALIZABLE 에서는 직렬화 실패로 재시도가 필요할 수 있다"로 남아 있던 항목이다.
필요한 게 맞았는데, 그보다 중요한 것이 먼저 나왔다.

- **① 같은 해저드를 세 격리수준에서 돌리면 드리프트는 셋 다 0 이다. 그런데 의미가 다르다.**
  RC 는 B 의 쓰기가 **성공**하고, RR/SER 은 **`could not serialize access due to concurrent
  update` 로 죽는다.** 드리프트가 없는 건 안전해서가 아니라 쓰기가 아예 안 일어나서다.
  → 스크립트가 "B 의 쓰기" 열과 "파생 테이블" 열을 **따로** 찍는 이유다. 한 열만 보면
  정확히 반대로 읽게 된다. t9-concurrency.sh 의 "드리프트 0 이 안전을 뜻하지 않는다"와 같은 구조.
- **② 부하(고객 50명으로 좁혀 경합, 8 clients):**
  RC 실패 **0**, RR 실패 20(약 1%), SER 실패 **223(약 14%)**. 재시도(`--max-tries=10`)를 붙이면
  RR 은 전부 복구되고 TPS 도 안 주는데, SER 은 재시도 177회에 TPS 가 RC 대비 **-19%** 이고
  10번을 다 쓰고도 1건이 실패했다. RR 은 "내가 잠근 행이 바뀌었다"만 잡고 SER 은
  **읽기-쓰기 의존성까지** 잡아서 나는 차이다.
- **③ 실패가 잔해를 남기지 않는다 — 그게 위험하다.** 수백 건 실패 뒤 파생 불일치 0 행.
  트랜잭션이 통째로 롤백되니 트리거가 쓴 행도 같이 사라진다. 그래서 상위 격리수준의 대가는
  '깨진 데이터'가 아니라 **안 된 일**이고, **정합성 점검으로는 안 잡힌다.** 실패율을 재야 안다.

→ **결론 10**: 격리수준을 올리는 것은 파생 데이터 정합성의 해법이 아니다. 이 워크로드에서는
`RC + FOR SHARE` 가 이미 정합성을 주므로 올려서 새로 얻는 게 없고 비용만 있다.
재시도 정책 없이 `SERIALIZABLE` 을 켜면 14% 의 쓰기가 조용히 사라진다.

**구현 메모:**
- pgbench 16 의 `--max-tries` / `--failures-detailed` 가 이 측정을 가능하게 한다(14 이상 필요).
  스크립트가 버전을 확인하고 낮으면 중단한다.
- `PGOPTIONS="-c default_transaction_isolation='repeatable read'"` 는 **동작하지 않는다.**
  PGOPTIONS 는 공백으로 인자를 나누므로 값 안의 공백을 백슬래시로 이스케이프해야 한다:
  `-c default_transaction_isolation=repeatable\ read`. 따옴표로 감싸면 조용히 무시되고
  READ COMMITTED 로 돈다 — 처음에 그래서 세 수준이 전부 같은 값이 나왔다.
- 커스텀 스크립트로 pgbench 를 돌릴 때 `-n` 이 필요하다. 없으면 `pgbench_branches` 등을
  vacuum 하려다 에러를 뿜는다(tpch DB 에는 그 테이블이 없다).
- 부하가 `customer` 등급을 바꾸므로 **시작 전에 백업하고 끝에 되돌린다.** lineitem 쪽은
  넣었다 지우는 트랜잭션이라 순변화가 없다. 끝에 원복 여부를 숫자로 확인한다.

### T-8 파생 — 인덱스의 쓰기 비용 (`scripts/pgbench/t8-dml-cost.sh`)

§8 에 "절차만 있고 수치가 비어 있다"로 남아 있던 항목이다. 돌려 보니 **문서의 전제가 틀렸다.**

- **① 개수가 아니라 갱신 컬럼이다.** pgbench 의 tpcb-like 는 `abalance` 만 UPDATE 한다.
  인덱스를 하나씩 늘렸을 때 `(filler)` 는 HOT 비율이 68.0→67.5% 로 **안 움직이고**,
  같은 개수인 `(abalance)` 는 **0.0%** 로 무너진다. 레코드 WAL(FPI 제외)은
  373 → 424 → 473 → 651 B(3개 전부), **1.75배.**
  ②도 완전히 공짜는 아니다 — 기준선에서 이미 HOT 이 아니던 1/3 이 그 인덱스를 갱신한다.
  **깨뜨리는 것과 얹히는 것은 다르고, 둘 다 있다.**
- **② fillfactor 가 HOT 의 다른 전제고, 포화가 있다.** 100 → 90 에서 HOT 이 67.5% → **100%**,
  70 까지 더 내려도 이득 없음. 그리고 이 표가 ①의 기준선(68%)을 설명한다 — pgbench 기본값이
  `fillfactor=100` 이라서다. **fillfactor 를 먼저 고치면 ②의 비용도 같이 사라진다.**
- **③ 가설을 세웠다가 반증됐다.** "부하를 올려 병목을 옮기면 TPS 하락이 드러날 것"으로
  clients 8/16/32/64 를 훑었는데, 배수가 0.94~0.95 로 **추세가 안 나왔다.** 네 번 돌려도
  8~32 의 순서가 회차마다 바뀐다. clients=64 가 매번 가장 낮긴 하지만(0.89~0.93)
  기준 자체의 편차도 같이 커져(±1~10%) 그 안에 걸친다.
  → **결론이 가설의 반대가 됐다: TPS 로는 이 비용을 잡을 수 없다.** 전역 지표가 국소 변화를
  삼킨 것(Millsap 8장). 그래서 스크립트가 배수 옆에 **기준 자체의 편차**를 같이 찍는다 —
  배수만 찍으면 노이즈를 발견으로 읽게 된다.

**이 실습에서 자초한 함정 셋 (전부 측정 자체를 무의미하게 만드는 종류였다):**
1. **`VACUUM FULL` 이 한 번도 안 돌았다.** `TRUNCATE …; VACUUM FULL …;` 를 한 `-c` 로 보냈더니
   psql 이 암묵적 트랜잭션으로 감싸서 `VACUUM cannot run inside a transaction block` 이 났는데,
   `>/dev/null` 로 삼키고 있었다. 조건 사이 부풀음 제거가 통째로 안 된 채로 측정된 것이다.
   문장을 나누고, 준비 단계 전용 `qx`(실패하면 중단)를 만들어 다시는 삼키지 않게 했다.
2. **UPDATE 당 WAL 이 6배 흔들렸다** (②가 3,037B → 다시 재니 432B). 원인은 체크포인트 직후의
   전체 페이지 이미지(FPI)였다 — 측정 구간에 체크포인트가 걸리느냐로 값이 뒤집힌다.
   측정 직전 `CHECKPOINT` 로 출발점을 고정하고, `pg_stat_wal` 로 **FPI 몫을 빼서** 보고하게 했다.
   FPI 가 WAL 의 약 90% 라, 빼기 전 숫자로는 조건 차이가 아예 안 보인다.
3. `padr 동시 클라이언트 18` — 한글 라벨을 인용 안 해서 `$2` 가 "클라이언트"가 됐다.

> pgbench 16 의 `--max-tries` / `--failures-detailed` 를 이 과정에서 확인했다.
> 격리수준별 재시도 측정(§8 의 `FOR SHARE` 항목)에 그대로 쓸 수 있다.

### verify-lab — problem-solving 의 검증 51케이스 이식 (+ Grafana)

`ruke79/problem-solving` (브랜치 `claude/gradle-8-14-migration-g00czw`)의 verify-core /
verify-labs 에서 다섯 분류를 이식했다 — spring 7 · jpa 7 · concurrency 5 · jvm 7 · db 25.
케이스 1개 = 면접 질문 1개 = "답변의 명제를 실행으로 재현할 수 있는가".

**모듈**: `:verify-core`(프레임워크, 원본 그대로) / `:verify-lab`(51케이스 + 적재 sink).
원본 11개 분류 중 5개만 가져왔으므로 security/graphql/redis/wiremock/otel 의존성은 뺐다.

**이 환경 실행 결과**: PostgreSQL 16.13 (프라이머리 5432 + 스트리밍 레플리카 5433) 에서
**51건 전부 CONFIRMED — REFUTED 0 / INCONCLUSIVE 0 / ERROR 0.**

처음엔 DB-24(복제 지연)가 INCONCLUSIVE 였다. `scripts/verify/setup-replica.sh` 로
Docker 없이 `pg_createcluster` + `pg_basebackup -R` 스탠바이를 만들어 붙이자
CONFIRMED 로 바뀌었다. 핵심은 `recovery_min_apply_delay=2s` 다 — 프라이머리와 레플리카가
같은 호스트라 복제가 수 ms 안에 따라잡으면 "쓰기 직후 옛 값이 보인다"는 **관측 창 자체가
열리지 않는다**. 실측으로도 확인했다: 쓰기 직후 레플리카에서 0행 → LSN 까지 따라온 뒤 1행.
결과를 만든 것이 아니라 실무에서 불규칙하게 나타나는 지연을 관측 가능한 크기로 고정한 것이고,
지연이 안 걸린 환경에서는 케이스가 스스로 INCONCLUSIVE 로 남긴다(비결정 케이스).

**환경에서 손본 것 세 가지** (`scripts/verify/setup-verifylab.sh` 가 처리):
1. `verifylab` DB/계정 신설 — 케이스가 테이블을 만들고 지우므로 tpch 와 분리 필수
2. `wal_level=logical` — DB-10(CDC) 논리 디코딩 요구. ALTER SYSTEM 후 재시작.
   **끝나면 `replica` 로 되돌린다** — 이 랩의 측정 기준이 replica 이고, logical 이면
   UPDATE 당 WAL 이 약 80바이트 늘어 §T-8 수치가 달라진다(§4의 "verify-lab DB-10" 항목).
   `setup-verifylab.sh` 는 안내만 하고 바꾸지 않는다.
3. `CREATEROLE` + `createrole_self_grant='set,inherit'` — DB-13(RLS)이 테넌트 롤을 만들어
   `SET ROLE` 한다. **PG16 부터 CREATEROLE 은 만든 롤의 ADMIN 만 받고 SET 권한은 못 받는다** —
   처음엔 permission denied 가 났고, self_grant 설정이 PG16 의 정석 해법이다.

**verify-lab-kafka (후속 이식)**: MSA 명제를 실물 브로커로 검증하는 8번째 모듈.
Docker 데몬이 없어 **Kafka 3.9.1 tarball 을 받아 KRaft 단일 노드를 자바 프로세스로 직접
띄웠고**(scripts/verify/kafka-local.sh 로 재현 가능), **7케이스 전부 CONFIRMED** —
파티션 순서/컨슈머 랙/DLQ/Exactly-Once/리밸런스/핫 파티션/스키마 호환성.
결과는 같은 verify_result 테이블에 적재되므로 Grafana 에 kafka 분류가 수정 없이 나타난다.
이 모듈은 DataSource 자동설정을 꺼 두므로(브로커 없이도 컨텍스트가 떠야 함) sink 는
DriverManager 로 직접 붙는 PlainJdbcResultSink 다.

**Grafana**: 결과를 `verify_result` 테이블에 run_id 단위로 적재하는
`VerificationResultJdbcSink` 를 붙였다(md 리포트는 판정 근거용으로 그대로 두고, 테이블은
시계열용 — 목적이 달라 둘 다 남긴다). `docker/verify/compose.yaml` 이 PG + Grafana 를 띄우고
프로비저닝(datasource + 대시보드 JSON)까지 자동이다. 대시보드는 3개 섹션(전체 요약 / 케이스 상세 / Kafka)에 패널 17개 + 분류 필터 변수.

**여기서 설계 결함을 하나 잡았다.** 처음엔 모든 패널이 "가장 최근 run_id 하나"를 봤는데,
verify-lab 과 verify-lab-kafka 는 **서로 다른 run_id 로 적재된다** — 그래서 나중에 돌린
모듈만 보이고 다른 모듈이 통째로 사라졌다(CONFIRMED 가 58 이 아니라 51 로 나왔다).
`-Dverify.only=` 로 한 건만 돌리면 전체가 1건으로 보이는 증상도 같은 원인이었다.
**분류별 최신 실행**(`DISTINCT ON (category)`)으로 고치고, `*-selected` 실행은
전체 그림에서 제외했다. Grafana 를 띄울 수 없는 환경이라 **패널 SQL 18개를 실제 DB 에
그대로 돌려 검증**했다(전부 성공, 매크로·변수는 치환) — 이 결함도 그 과정에서 드러났다.

부수 소득: 분류별 총 소요시간이 kafka 48.1초(케이스당 6.9초) vs spring 86ms(12ms) 로
**500배 이상 차이**가 난다. 실물 브로커를 띄워 검증한다는 것의 대가가 수치로 보인다.
**Grafana 렌더링까지 실행 검증했다.** Docker 데몬이 없어 처음엔 못 띄웠는데,
`dl.grafana.com` 은 프록시 정책에 막혀 있어 **Docker Hub 레지스트리 API 로 공식 이미지
레이어를 받아 풀었다** — 블롭이 CloudFront 로 리다이렉트돼 또 막히자 `mirror.gcr.io`
(Docker Hub 풀스루 캐시)로 우회했다. 데몬 없이 tarball 처럼 rootfs 를 펴서 실행한 것이다.
띄운 뒤 **커밋된 프로비저닝 파일 그대로** 데이터소스·대시보드가 올라오는 것을 API 로 확인하고
(`Database Connection OK`), 사전설치된 Chromium 으로 **렌더링 스크린샷**을 찍었다
(`docs/img/grafana-verification-lab.png`). 콘솔 에러 0.

여기서 **패널 버그를 하나 더 잡았다** — "Kafka 마지막 실행" stat 패널이 `No data` 였다.
`max(run_at)` 이 timestamptz 하나만 돌려주면 Grafana 가 시간 컬럼으로만 보고 값 필드가
없다고 판단한다. `extract(epoch FROM max(run_at))*1000` 으로 숫자를 돌려주고
`dateTimeAsIso` 단위로 표시하도록 고쳤다. **SQL 을 DB 에 직접 돌리는 검증으로는 못 잡는
결함이었다** — 쿼리 자체는 정상이고 Grafana 의 필드 해석에서만 깨졌기 때문이다.

## 5. 문서에서 정정한 잘못된 서술

측정 과정에서 **내가 처음에 쓴 내용 중 15건이 사실과 달랐고 모두 정정**했다.
기록으로 남기는 이유는, 같은 함정을 다시 밟지 않기 위해서다.

1. **"q09에서 NL 강제 시 참혹해진다"** → 실제로는 NL이 4.6배 빨랐다.
   NL이 무너지는 조건은 필터 폭이 아니라 **안쪽 조인키 인덱스의 부재**(있으면 216ms, 없으면 60초 초과).
2. **`join_collapse_limit=1`로 콤마 조인 순서 강제** → 효과 없음. 명시적 `JOIN ... ON` 구문이라야 적용된다.
3. **"statistics_target을 올리면 오차가 준다"** → 균일 분포에서는 전혀 줄지 않는다
   (target 1~1000에서 추정 8,319/8,696/10,204/8,280, 실제 9,015). 치우친 데이터에서만 의미 있다.
4. **"`extract()`를 쓰면 Parallel Seq Scan이 된다"** → VACUUM된 테이블에서는 Index Only Scan + Filter.
   출력을 3줄만 잘라 보고 단정한 실수였다.
5. **"customer 드라이빙(휴리스틱)이 항상 빠르다"** → 장비에 따라 반대.
6. **T-8에서 "커버링 인덱스가 결합 인덱스보다 확실히 낫다"** → 조건별로 나눠 batch 측정했을 때
   나온 착시였다(커버링 284ms vs Hash 310ms). **같은 라운드 안에서 교차 측정하니 사실상 동률**
   (②313 / ③293 min, median은 331 / 334로 역전). 시간대 드리프트가 조건 간 차이보다 컸다.
   → §T-0에 "비교할 조건은 교차(interleave)해서 재라"를 원칙으로 추가했다.
7. **"트리거를 붙이면 반정규화가 완벽히 동기화된다"** → **단일 세션 한정이었다.**
   드리프트 0을 확인하고 그렇게 썼는데, 동시성에서는 `READ COMMITTED` 이상현상으로 조용히
   어긋난다(겨냥 실험에서 재현). 더 나쁜 건 8클라이언트 무작위 부하로도 **드러나지 않았다**는
   점이다 — 거기서도 드리프트는 0이었다. `FOR SHARE` 로 고쳤다.
   → 교훈: 정합성은 부하 테스트가 아니라 **트랜잭션 겹침을 손으로 따져서** 검증해야 한다.
8. **재적재(`load`) 후 `index` 를 안 돌린 채 pgbench 를 실행했다** → lineitem 에 PK 가 없어
   `ON CONFLICT DO NOTHING` 이 무력화되고 중복 347건이 들어갔다. 인덱스 없는 상태의 측정값
   (101 tps)도 무의미했다(정상 상태는 5,702 tps — **39배 차이**).
   → 교훈: 측정 전 **스키마 전제부터 확인**한다. 이상하게 느린 수치는 튜닝 대상이 아니라
   환경 오류의 신호인 경우가 많다.
9. **pgbench 를 `-d tpch` 로 호출했다** → pgbench 에서 `-d` 는 `--dbname` 이 아니라
   **`--debug`** 다(dbname 은 위치인자). 즉 모든 pgbench 측정이 **디버그 추적 출력이 켜진 채**
   이뤄졌다. 절대 tps 가 눌렸다 — 트리거 OFF 기준선이 3,949 → **5,702 tps** 로 정정됐고
   (락 범위 실험의 1% 지점은 6,071 → 9,338), 전 수치를 재측정해 교체했다.
   다행히 **비교 양쪽에 동일하게 걸린 오버헤드라 비율은 거의 그대로**였다
   (락 범위 손해 2.22 → 2.21배, 정합성 비용 1.8배 유지).
   → 교훈: 벤치마크 도구의 **플래그 의미를 확인**한다. 특히 한 글자 옵션은 도구마다 다르다.
10. **`timeout 20 sql "..."` 로 경합 측정을 했다** → `timeout` 은 외부 바이너리라
    **셸 함수를 실행할 수 없다.** `failed to run command 'sql'` 로 즉시 실패하고,
    측정된 것은 실패에 걸린 4ms 였다. 즉 `t9-lock-range.sh` ②의 경합 측정은
    **명령이 아예 실행되지 않은 채** 기록됐다. `psql` 을 직접 호출하도록 고쳐 재측정했다.
    → 교훈: 측정 대상이 **정말 실행됐는지**를 값의 크기로 검증한다. 4ms 는 "빠르다"가 아니라
    "안 돌았다"의 신호였는데, 기대하던 방향의 결과라서 의심하지 않았다.
    같은 이유로 `pgbench` 호출부에 `PGPASSWORD` 가 없어 tps 가 빈 값으로 나온 것도 발견해 고쳤다
    (세 스크립트 모두 `export PGPASSWORD` 로 통일).
11. **등급 변경 시간을 `random()` 값으로 재고 최소값을 취했다** → 새 값이 옛 값과 같으면
    `IS DISTINCT FROM` 가드에 걸려 트리거가 no-op 이 된다. 값이 10종뿐이라 5회 중 한 번쯤
    no-op 이 섞이는데, **최소값을 취하는 순간 정확히 그 no-op 만 골라내게 된다.**
    5,000주문 고객의 naive 트리거가 2.1ms 로 나와(1,000주문의 52.9ms 보다 빠르게) 들통났다.
    시퀀스로 매번 다른 값을 넣도록 고쳤다.
    → 교훈: **최소값 집계는 "실패한 시행"에 가장 취약하다.** 빠른 쪽 꼬리가 무엇인지 확인한다.

    잠그는 행이 1,000건을 넘는 구간에서 **1.42~1.45배**였다(5,000행 기준 153.6 → 222.9ms).

    → 결론의 방향(경합이 지배적)은 유지되지만, "공짜"라는 표현은 사실이 아니었다.
    → 교훈: **배수가 1에 가깝다는 이유로 "비용 없음"이라 쓰지 않는다.**
    변동 폭 안이라 판단했으면 반복 횟수를 늘려 확인했어야 했다.
13. **중앙값 함수가 짝수 개일 때 "둘 중 작은 쪽"을 냈다** — `a[NR/2]` 만 취했다.
    2라운드로 잰 포화 실험에서 배치 2,000 이 120ms / 적체 1,786 이라는 값이 나왔고,
    "배치 500과 2,000 사이에 절벽이 있다"는 결론을 쓸 뻔했다. 3라운드로 다시 재니
    3,122ms / 적체 35,813 이었다 — **절벽은 없었고, 낙관 편향이 만든 착시였다.**
    가운데 두 값의 평균을 쓰도록 고쳤다.
    → 교훈: **집계 함수 자체가 편향을 만들 수 있다.** 특히 표본이 2~4개로 적을 때
    min/median/mean 중 무엇을 쓰는지가 결론을 바꾼다. 11번과 같은 계열의 실수다.
14. **큐 튜닝 격자를 조건당 1회씩만 재고 표를 만들었다** → 라운드 교차 + 중앙값으로 다시 재니
    배치 축의 절대값이 30배까지 달랐고(6,338 → 210ms), 워커 축은 아예 순서가 뒤바뀌었다.

    dead tuple 이 **뒤에 오는 조건을 불리하게** 만드는 누적 편향(라운드 교차로도 안 지워진다).

    → 교훈: 교차 측정은 **시간대 드리프트**를 지우지만 **상태 누적**은 못 지운다.
    쓰기를 동반하는 측정에서는 조건 사이에 상태를 되돌리는 단계가 따로 필요하다.
15. **`denorm_drain` 의 반환형을 int → record 로 바꾸며 `CREATE OR REPLACE` 만 썼다** —
    PostgreSQL 은 **CREATE OR REPLACE 로 반환형을 바꿀 수 없고**, 그 에러가 heredoc 의
    `2>/dev/null` 에 삼켜져 옛 함수가 그대로 남았다. 새 워커는 매 루프
    `SELECT applied, depth FROM denorm_drain(...)` 에 실패했고, **전 지표가 0 인 표**가

    → 교훈: 시그니처를 바꾸면 REPLACE 가 아니라 DROP+CREATE 다. 그리고 **전부 0 인 표는
    "빠르다"도 "조용하다"도 아니라 "안 돌았다"다** — 10번(4ms)과 같은 계열의 신호였다.

    → 교훈: 측정 결과에는 **어느 조건에서 잰 것인지**를 결론과 같은 크기로 적는다.

    골랐다. 실제 규칙은 "좁은 쪽이 이긴다"가 아니라 **"작은 쪽이 이긴다"** 이고,
    tpch 에서 좁은 쪽이 이긴 것은 그것이 마침 더 작았기 때문이다(우연히 일치했다).

    tpcds 는 둘이 어긋나는 사례라서 진짜 원인이 드러났다.
18. **"사전 집계는 이미 접혀 있으니 유지 비용도 작다"** → 반대다. 점 변경 하나를 반영하는
    비용이 반정규화 140ms vs MV `REFRESH` 5,260ms = **38배**. PG 의 REFRESH 는 증분이 아니고
    `CONCURRENTLY` 도 전량 재계산 후 교체다. **접힘은 저장량의 성질이지 갱신 비용의 성질이
    아니다.** → 읽기 이득과 쓰기 비용은 **항상 따로 재야 한다**(§T-9 tpcds 판).

19. **"work_mem 이 실제로 듣는 것은 대략 팩트 1.5억 행 이후"** → **30배 틀렸다. 약 457만 행이다.**
    200만 행에서 64MB 와 4GB 의 측정값이 바이트까지 같길래 "이 규모에서는 무의미"까지는
    맞게 썼는데, 임계치를 어림하면서 자릿수를 틀렸다. 실제 계산은 단순하다 —
    이 형상의 HashAggregate 가 200만 행에 28.7MB 를 쓰므로 64MB 를 넘기는 지점은
    `2,000,000 × 64 / 28.7 ≈ 457만 행` 이다.
    **사용자가 대규모 데이터에서 t7 을 돌려 몇 시간 걸리던 것이 4GB 로 몇 분에 끝나면서 드러났다.**
    뒤늦게 work_mem 을 낮춰 가며 넘치는 지점을 실측해 확인했다(200만 행, ③ UNION):

    | work_mem | HashAggregate | 시간 |
    |---|---|---|
    | 64MB | Batches: 1, 28,689kB | 347 ms |
    | 32MB | Batches: 1, 26,641kB | 321 ms |
    | 16MB | Batches: 1, 25,617kB | 322 ms |
    | 8MB | **Batches: 5**, 20,529kB + **Disk 7,072kB** | 511 ms |
    | 4MB | HashAggregate 포기 → Sort+Unique(external merge) | 375 ms |

    → 교훈 둘. 첫째, **"현재 규모에서 효과 없음"을 "일반적으로 중요하지 않음"으로 옮겨 적으면
    안 된다.** 임계치를 넘는 순간 계단처럼 뛰는 값은 평소에 0 이어도 위험도가 0 이 아니다.
    둘째, 어림수를 쓸 거면 **나눗셈이라도 실제로 해 봐야 한다** — 이건 측정 실패가 아니라
    산수 실패였고, 측정값(28.7MB)은 처음부터 손에 있었다.

    **덧붙임 — 원인을 찾아보니 ③이 아니라 ②였다.** 위 정정을 하면서 "그럼 몇 시간이 걸린
    이유가 ③의 유출인가"를 확인하려고 절별로 쟀는데, ③의 유출은 2배쯤 느려지는 일이라
    시간 단위를 설명하지 못했다. 진짜 원인은 ②였다 —
    `work_mem` 이 모자라면 PostgreSQL 이 `hashed SubPlan` 을 **아예 포기하고** 평범한
    `SubPlan` 으로 떨어진다. 디스크로 흘리는 게 아니라 **바깥 행마다 재실행**이라
    비용이 곱셈으로 뛴다. 200만 행에서도 1초 → **180초 초과**였다.

    | work_mem (200만 행) | 서브플랜 | 시간 |
    |---|---|---|
    | ≥ 32MB | `hashed SubPlan` | 약 1초 |
    | ≤ 30MB | `SubPlan` | **180초 초과** |

    전환점은 서브쿼리 **추정 행수 × 약 17바이트**다. 그래서 2,880만 행에는 490MB 가 필요한데
    기본값이 64MB 라 7.6배 부족했고, 그래서 몇 시간이 걸린 것이다.
    → **2.88억 행(10배)에는 4.9GB 가 필요하다. 지금 기본값 4096MB 로도 부족하다.**
    → 교훈: 유출(느려짐)과 **계획 붕괴**(곱셈)를 같은 것으로 다루면 안 된다.
    `Batches>1` / `Disk Usage` 만 보고 있었으면 ②는 영영 못 찾았을 것이다 —
    hashed SubPlan 포기는 그 지표에 **아무것도 남기지 않는다.**
    `DIAG=1 ./scripts/tpcds/t7-complex-sql.sh` 가 이 점검을 대신한다.

## 6. 측정 위생 (§T-0) — 가장 중요한 절

1. **한 번에 한 변수만.** `index`는 인덱스+ANALYZE를 함께 하므로 `analyze`로 분리한다.
2. **단발 EXPLAIN ANALYZE를 성능 지표로 쓰지 않는다.** 세션 최초 JIT은 유독 비싸다.
3. **JIT이 결과를 지배하는지 확인한다.** `JIT: Total`을 `Execution Time`과 비교.
4. **캐시 상태를 의식한다.** `--warmup` 옵션과 `Buffers: read` 확인.
5. **VACUUM 여부가 계획을 바꾼다.** `relallvisible` 확인.
6. **비교할 조건들은 교차(interleave)해서 잰다.** 조건 A를 10회, 그다음 조건 B를 10회 재는
   batch 방식은 그 사이의 시간대 드리프트를 조건 차이로 착각하게 만든다.
   한 라운드 안에서 A→B→(A→B)… 로 번갈아 재고, 라운드를 반복한다.

실제로 이 원칙을 어겨 오판한 사례가 세션 중 세 번 있었다 —
인덱스 생성 직후 단발 측정에서 C가 B보다 느리게 나왔다가(캐시 미충전) 반복 측정에서 뒤집혔고,
`extract()` 계획을 3줄만 보고 잘못 단정했으며,
**T-8에서 batch 측정으로 커버링 인덱스가 이긴 것처럼 보였다가 교차 측정에서 동률로 밝혀졌다**(원칙 6).

#### ⑥에 남아 있던 고정 결론 둘 — 그리고 고치다 한 번 더 틀렸다

사용자가 고친 스크립트로 같은 조건을 다시 돌렸다. ②가 **7.8배로 두 번 다 같게** 나왔고
(171/21.9, 158/20.2), 벽시계 값은 15% 가까이 움직였는데 서버 시간 배수는 소수점까지
같았다 — 왕복비를 빼고 재는 것의 값이 여기서 드러난다.

그 출력에서 ⑥에 아직 박혀 있는 결론 둘을 발견했다.

1. **"(가) 점 이동에서는 네 전략이 사실상 같다."** 두 실행 모두 B 가 최댓값이었고
   A 대비 1.25배·1.45배였다. 반복되는 순위는 노이즈가 아니다.
2. **"②의 이득(6배)"** — 실측은 7.8배였다. §T-9 의 "1.5~3.2배"와 같은 계열이다.

**고치면서 한 번 더 틀렸다.** (가)의 문장을 "B 가 가장 비싸다"로 바꿨는데, 내 환경에서
돌려 보니 `A′ 5.32 / B 5.31` 인 실행에서도 그대로 찍혔다. **최댓값이 누구인지도 재야
한다** — '같다'를 '특정 전략이 최대다'로 바꾼 것은 가정을 다른 가정으로 바꾼 것일 뿐이다.
지금은 awk 로 최댓값 라벨을 뽑아 이름을 찍는다.

덧붙여 (가)에서 N 을 빼고 비교하게 했다. N 은 `customer` 1행만 건드리므로 구조적으로
제일 싸고, 그 N 을 넣고 '최대/최소'를 말하면 A·A′·B 사이의 차이가 N 에 가려진다.
표본 실행의 ①에서 N 이 다른 모집단이었던 것과 같은 성질의 문제다 —
**비교 가능한 것끼리만 묶는다.**

> **②의 배수는 버퍼 풀 상태에 크게 의존한다.** A 의 비용은 흩어진 행을 되찾는 랜덤
> 접근이라 그 페이지가 캐시에 있으면 싸고 없으면 디스크로 나간다. ①을 먼저 돌려 데운
> 실행에서 7.8배가 두 번, `ONLY=26` 으로 ①을 건너뛴 차가운 실행에서는 **26~28배**가
> 나왔다. 같은 장비·같은 데이터인데 3.5배 차이다. 스크립트가 ①을 건너뛴 실행에는
> 그 경고를 같이 찍는다. **바뀌지 않는 것은 배수가 아니라 방향이다.**

#### 재적재가 막혀 있었다 — 매트뷰 잔여물이 schema 를 통째로 거절한다

`t9-concurrency.sh` 는 **원본 테이블을 커밋 변경**하므로 끝에 재적재를 권한다.
사용자가 그대로 따라 했는데 세 명령이 연쇄로 실패했다.

```
schema → ERROR: cannot drop table lineitem because other objects depend on it
         Detail: materialized view mv_q03 depends on table lineitem
load   → ERROR: duplicate key value violates unique constraint "region_pkey"
index  → 성공 (멱등이라 그냥 건너뛴 것)
```

**두 번째 에러가 특히 나쁘다.** schema 가 실패한 줄 모르고 load 를 이어 돌리면
'중복 키'라는, 원인과 아무 관계 없는 에러가 나온다. 그리고 `index` 만 성공하니
겉보기에는 "뭔가 됐다"로 읽힌다. 실제로는 `lineitem 60,003,058 행` — 원본
59,997,159 보다 5,899 행 많은, **오염된 상태 그대로**였다.

원인은 세 겹이다.

1. `t9-preaggregation.sh` 가 `mv_q03` 를 만들고 **정리 명령을 찍기만** 했다
   (`t9-trigger-sync` 와 같은 패턴 — 그건 앞에서 고쳤는데 이건 놓쳤다).
2. `restore-lab.sh` 의 잔여물 검사에 **매트뷰가 없었다.** 그래서 `--check` 가
   "잔여물 없음"이라고 말하는 동안 재적재를 막는 물건이 앉아 있었다.
3. `schema-postgres.sql` 의 `DROP TABLE IF EXISTS` 에 `CASCADE` 가 없었다.

고친 것:

- **`schema-postgres.sql` / `schema-postgres.sql`(tpcds) → `DROP TABLE ... CASCADE`.**
  여기서 CASCADE 로 지워지는 것은 실습 잔여물이므로 없어져야 맞다.
- **`t9-preaggregation.sh` 2종이 직접 지운다**(`KEEP=1` 로 남길 수 있다).
- **`restore-lab.sh` 가 매트뷰를 본다** — `mv_q03` / `mv_brand_month` / `mv_baked`.
  남아 있으면 "**매트뷰가 남아 있으면 schema 재적재가 막힌다**"와 DROP 문을 같이 찍는다.

재현해서 확인했다. 매트뷰를 심어 두고 `--check` → `매트뷰 tpch 1` 로 잡히고,
그 상태로 `schema` 를 돌리면 `DROP TABLE IF EXISTS lineitem CASCADE` 가 통과하며
매트뷰까지 정리된다(이전에는 여기서 죽었다).

> **교훈은 '정리 명령을 찍기만 하지 않는다'의 반복이다.** `t9-trigger-sync` 에서
> 같은 것을 고치면서 **같은 패턴을 쓰는 다른 스크립트를 안 찾아봤다.**
> 한 군데서 결함을 고치면 `grep` 으로 같은 모양을 한 번 훑는 습관이 필요하다.

#### '정리 명령을 찍기만 한다'를 이번엔 전부 훑었다

사용자가 `--check` 에서 `tpch 트리거 1` 을 보고 "지금 돌리는 스크립트와 상관없는
오염인가"를 물었다. 트리거 이름이 `t_sync_cust` 하나뿐이었고, **그 조합을 만드는
스크립트는 `t9-lock-range.sh` 뿐이다**(다른 것들은 3종을 한꺼번에 단다).

매트뷰 건에서 "한 군데 고치면 같은 모양을 grep 으로 훑어야 한다"고 적어 놓고
안 했다. 이번에는 했다:

| 스크립트 | 이전 | 지금 |
|---|---|---|
| `t9-trigger-sync` | 출력만 → 고침 | 직접 지움 |
| `t9-preaggregation` ×2 | 출력만 → 고침 | 직접 지움 |
| `t9-lock-range` | **출력만** | 직접 지움 + `o_custkey` 복원 |
| `t9-change-queue` | **출력만** | 직접 지움 + `o_custkey` 복원 |
| `t9-queue-tuning` | **출력만** | 직접 지움 + `o_custkey` 복원 |
| `t9-concurrency` | **출력만** | 트리거·denorm 은 지움, 나머지는 복구 불가라고 명시 |

**`t9-lock-range` 에는 백업이 아예 없었다.** `setsize()` 가
`UPDATE orders SET o_custkey=(2+(o_orderkey%1000)) WHERE o_custkey=1` 로 주문 5,000건을
한 고객에게 몰아 인위적 대형 계정을 만드는데, 원본을 어디에도 안 남겼다.
`t9-change-queue`·`t9-queue-tuning` 은 `orders_cust_bak` 을 갖고 있었으므로
**같은 랩 안에 이미 있던 패턴을 이 스크립트만 안 쓰고 있었던 것**이다. 그것을 넣고
끝에서 되돌린다.

확인: 돌린 뒤 `o_custkey=1` 인 주문이 11건(자연 분포, 평균 10.0)으로 돌아왔다.
고치기 전이라면 5,000건이 남았을 자리다. `--check` 도 "잔여물 없음".

`t9-concurrency` 만 예외로 남는다 — pgbench 워크로드가 무작위로 바꾼 것은 백업이
없어 되돌릴 수 없다. 그래서 **'지운 것'과 '못 되돌린 것'을 나눠서** 말하게 했다.

#### ②가 아예 실행되지 않은 채 결과로 찍히고 있었다

사용자의 SF=10 `t9-lock-range` 출력에서 ②가 `naive 3ms / FOR SHARE 2ms` 로 나왔다.
문서 실측은 `58ms / 2,735ms`(47배)다. 그런데 스크립트는 "통째로 막힌다"를 그대로 찍었다.

원인: `tsql()` 만 래퍼를 안 거치고 **psql 을 직접 불렀다.**

```bash
tsql(){ timeout "$1" psql -h ... -tAc "$2"; }     # ← 여기
```

호스트에 클라이언트가 없으니 `psql: command not found` 로 즉시 끝났고,
`>/dev/null 2>&1` 이 그것을 삼켰다. **2ms 는 락을 안 기다린 시간이 아니라
명령이 실행조차 안 된 시간이었다.**

8개 스크립트에 docker 폴백을 넣으면서 `PSQL`·`q` 같은 주 헬퍼만 바꾸고 **같은 파일 안의
다른 헬퍼를 안 봤다.** 다시 훑어 넷을 더 찾았다 — `t9-lock-range`·`t9-change-queue` 의
`tsql()`, `t8-dml-cost` 의 `qp()`, `t9-isolation-levels` 의 `qf()`.

`tsql` 은 바깥 `timeout` 대신 **서버의 `statement_timeout`** 으로 바꿨다. 함수는
`bash -c` 하위 셸에 안 보여서 `timeout` 과 래퍼를 같이 못 쓰고, 어차피 여기서 재려는
것이 '락을 얼마나 기다리는가'라 서버에서 끊는 게 맞다(전송 경로와 무관해진다).

고친 뒤 재현: **naive 56ms / FOR SHARE 2,736ms.** 문서의 58 / 2,735 와 거의 일치한다.

#### 그리고 ③의 "손해" 열은 애초에 재현되지 않는다

| 측정 | 1% | 10% | 100% |
|---|---|---|---|
| 문서 (SF=0.5) | 0.95 | 1.00 | **2.47** |
| 사용자 (SF=10) | 1.23 | 1.31 | **0.99** |
| 재실행 (SF=0.5) | 0.94 | 0.98 | **0.50** |

100% 열이 2.47 → 0.99 → 0.50 으로 튄다. 100% 에서는 naive 도 FOR SHARE 도 같은
지점에서 직렬화되므로 락이 더 보탤 것이 없고, 그래서 **어느 쪽이 앞서는지가 실행마다
바뀐다.** 그런데 문서는 2.47 배를 근거로 "적중률이 낮으면 공짜, 겹치면 급격히 비싸진다"를
결론 9 로 박아 뒀다.

**세 측정에서 한결같은 것은 `naive` 절대값의 붕괴다**(7,691→67.8 / 866→63.4 / 5,787→44.5).
결론 9 의 근거는 그쪽이어야 했고, 문서에도 이미 "FOR SHARE 손해 배수보다 naive 절대값이
더 중요하다"고 적혀 있었다 — **맞는 문장을 써 놓고 틀린 숫자를 근거로 삼았다.**
문서에 정정 표를 넣고, 스크립트는 방향을 측정에서 읽어 문장을 고르게 했다.

#### `--force-tpch` 가 SF=10 데이터 파일을 갈아엎었다

사용자가 `./scripts/restore-lab.sh --force-tpch` 를 돌렸더니 첫 단계가 이거였다:

```
./gradlew :tpch:bootRun --args="generate --sf=0.5 --dir=./data/tpch"
  → orders.tbl: 750000 rows, lineitem.tbl: 3000491 rows
```

**SF=10 으로 만들어 둔 `.tbl` 파일이 기본값 SF=0.5 로 덮어써졌다.** 사용자가
알아채고 중간에 물어봐서 알았다 — `--force-tpch` 는 "데이터가 있어도 다시 **적재**한다"는
뜻이지 "데이터 파일을 다시 **만든다**"는 뜻이 아니어야 했다.

**그리고 MySQL 경로에는 이 가드가 이미 있었다:**

```bash
# 데이터 파일은 PostgreSQL 쪽과 공유한다. 이미 있으면 generate 를 건너뛴다
if [ -n "$genarg" ] && [ ! -d "$HERE/$mod/data/$mod" ]; then mgen "$mod" "$genarg"; fi
```

`--mysql` 을 만들면서 이 문제를 예상하고 가드를 넣었는데, **같은 파일의 PostgreSQL
경로에는 안 넣었다.** 오늘 반복된 패턴 그대로다 — 한쪽을 고치고 나란히 있는 다른
쪽을 안 본다.

고친 것: 데이터 파일이 있고 `SF`/`SALES` 를 **명시적으로 주지 않았으면** `generate` 를
건너뛰고 기존 파일로 적재한다. 스케일을 바꾸려면 `SF=10 ...` 처럼 명시한다.
`${SF+1}` 로 '변수가 설정됐는지'를 기본값 대입 **전에** 기억해 둔다.

확인: `md5sum` 을 앞뒤로 재서 파일이 그대로인 것을 확인했다
(`cb0e3044...` → 적재 후에도 `cb0e3044...`, `기존 데이터 파일을 그대로 쓴다` 출력).

> **파괴적 동작의 이름을 정확히 짓는다.** `--force-tpch` 는 '재적재'를 뜻했는데
> '재생성'까지 했다. 이름이 실제 동작보다 좁으면 사용자는 안전하다고 믿고 누른다.

#### ③의 "손해" 열 — 5회를 재고 나서야 정확히 말할 수 있었다

사용자의 SF=0.5 실행이 100% 에서 **2.07배**로 나와, "재현되지 않는다"던 내 정정과
반대 방향이었다. 한 번의 재실행(0.50)에 근거해 문서를 고친 것이 성급했을 수 있어
같은 조건으로 두 번 더 돌렸다. 다섯 점을 모으니 이렇다:

| 적중률 | 5회 측정값 | 최대/최소 |
|---|---|---|
| 1% | 0.95 / 0.94 / 1.01 / 0.97 / 0.99 | **1.1배 (안정)** |
| 10% | 1.00 / 0.98 / 1.18 / 1.21 / 1.08 | 1.2배 |
| **100%** | **2.47 / 0.50 / 2.07 / 1.05 / 1.85** | **4.9배** |

**정정은 맞았지만 이유가 달랐다.** "규모(SF)에 따라 방향이 바뀐다"가 아니라
**"100% 열만 표본이 작아서 흔들린다"** 가 맞다 — 그 조건은 tps 가 40~90 이라
12초에 트랜잭션이 500~1,000건밖에 안 담긴다(1% 조건은 7만 건이 넘는다).
게다가 100% 에서는 naive 도 FOR SHARE 도 같은 지점에서 직렬화되므로 락이 더 보탤 것이
적어, 남은 차이가 잡음에 묻힌다. SF=10 의 0.99 도 '규모 차이'가 아니라 같은 불안정
구간 안의 한 값으로 읽는 게 맞다.

> **한 점으로 문서를 고치려 한 것이 성급했다.** 사용자의 2.07 이 없었으면 "SF 에 따라
> 뒤집힌다"는 **또 다른 틀린 단정**을 문서에 남길 뻔했다. 재현이 안 되는 값을 만나면
> 새 설명을 쓰기 전에 **같은 조건으로 몇 번 더 재는 것**이 먼저다.

고친 것: 스크립트가 조건별 트랜잭션 수를 세서 **2,000건 미만이면 "이 배수는 믿지 말 것"**
과 5회 스프레드를 같이 찍는다. 그리고 안정적인 것(naive 절대값)을 앞세운다.

구현 중에 `set -u` 에 걸렸다 — `RUN_TX` 를 `run()` 안에서 설정했는데 `r=$(run)` 이
서브셸이라 부모로 안 넘어와 `unbound variable` 로 죽었다. 표본 크기는 부모에서
`tps × 초` 로 센다.

확인(고친 뒤 실행): `100% 열은 12초에 약 686건, 1% 는 약 70,753건` 이 찍히고
경고가 같이 나온다. ②도 세 번 더 재서 **57ms / 2,735ms** 로 일관됐다.

#### 적재가 느렸다 — COPY 경로가 있는데 안 쓰고 있었다

사용자가 SF=10 을 재적재하다 "load 속도를 빠르게 하는 법이 없나"라고 물었다.
`restore-lab.sh` 가 `gradlew load`(JDBC 배치)를 부르고 있었는데,
**같은 저장소에 `scripts/tpch/load-postgres-copy.sh`(COPY)가 이미 있었다.**

실측(SF=0.5, 300만 행, 같은 장비·같은 파일):

| 경로 | 시간 |
|---|---|
| `gradlew load --db=postgres` (JDBC 배치) | **120초** |
| `load-postgres-copy.sh` (COPY) | **17초** |

**7.1배.** 헤더 주석에 "5~10배 빠름"이라고 적혀 있던 값이 실측으로 확인됐다.
SF=10 이면 이 차이가 수십 분이 된다.

두 가지를 고쳤다.

1. **COPY 스크립트에 docker 폴백.** 이 스크립트는 원래부터 파일을 STDIN 으로
   흘려보내므로(`\copy ... FROM STDIN`) `docker exec -i` 로 그대로 이어진다 —
   7GB 를 컨테이너로 복사할 필요가 없다. 호스트에 psql 이 없는 환경에서 이것 때문에
   빠른 경로를 못 쓰고 있었다.
2. **`restore-lab.sh` 가 COPY 를 쓴다.** 있으면 그쪽, 없으면 JDBC 로 떨어진다.

적재 세션에만 `synchronous_commit=off` 와 `maintenance_work_mem=1GB` 를 건다.
**서버 전역은 안 건드린다** — 오늘 wal_level·redo capacity 로 여러 번 덴 부분이라,
되돌릴 것이 없는 세션 스코프로만 한다.

> 이번에도 "같은 저장소 안에 이미 있는 것을 안 봤다"이다. `--mysql` 의 generate 가드,
> PostgreSQL 쪽 psql 폴백, `orders_cust_bak` 백업 패턴에 이어 네 번째다.

#### "예외 없이 두 자릿수 배로 무너진다" — 8회를 모으니 이것도 부정확했다

②의 `tsql` 수정이 사용자 환경에서 확인됐다(**naive 79ms / FOR SHARE 2,745ms**, 35배).
그 실행의 ③ 데이터를 앞선 7회와 합쳐 8점을 만드니, 바로 전에 내가 문서에 써 넣은
"1% → 100% 에서 **예외 없이 두 자릿수 배**로 무너진다"가 틀렸다 — 사용자 환경은 **9배**다.

| | 1% | 10% | 100% | 1%→100% |
|---|---|---|---|---|
| 장비 A (SF=0.5, 5회) | 5,662~7,691 | 306~391 | **44.5~72.4** | 79~130배 |
| 장비 B (SF=0.5, 1회) | 761 | 566 | **83.6** | 9배 |
| 장비 B (SF=10, 2회) | 742~866 | 524~684 | **63.4~80.2** | 9~14배 |

**더 나은 관찰이 나왔다. 안정적인 것은 '붕괴 배수'가 아니라 '100% 열의 절대값'이다** —
규모도 장비도 안 가리고 44~84 tps 다. 그 조건에서 하는 일이 고객1 의 denorm 20,075 행
갱신이고, 그 행수는 `setsize 5000` 이 만들어 내므로 **SF 와 무관하게 같기 때문**이다.
구조가 정하는 바닥값이다.

반대로 1% 열은 장비를 탄다(761 vs 5,700). 같은 장비 B 에서 SF=0.5 와 SF=10 이 거의
같으므로 규모가 아니라 클라이언트·전송 경로 쪽이다 — 경합이 없으면 서버가 한가해
병목이 바깥에 있고, 경합이 생기면 서버 일이 지배해 환경 차가 사라진다.

> **오늘 세 번째로 같은 자리를 고쳤다.** "2.47배가 맞다" → "재현 안 된다" →
> "SF 에 따라 뒤집힌다(쓸 뻔)" → "표본이 작아 흔들린다" → "배수가 아니라 100% 열을 봐라".
> 매번 **새 데이터가 앞의 설명을 좁혔다.** 한 점, 세 점, 다섯 점, 여덟 점.
> 교훈은 '더 재라'가 아니라 **'몇 점으로 말하는지를 문장에 넣어라'** 다 —
> "5회 측정에서 0.50~2.47" 은 새 데이터가 와도 안 틀리지만
> "예외 없이 두 자릿수 배" 는 9배 하나로 무너진다.

#### 래퍼가 `-U` 를 끼워 넣어 `--version` 을 깨뜨렸다

`t9-isolation-levels.sh` 가 이렇게 멈췄다:

```
  [중단] pgbench 를 찾을 수 없습니다 (경로: docker).
```

**컨테이너에 pgbench 는 멀쩡히 있었다.** 확인:
`pgbench` 는 `postgresql-16` 패키지에 들어 있고(contrib 아님), 공식 postgres 이미지가
`postgresql-$PG_MAJOR` 를 설치하므로 들어 있다.

진짜 원인은 내가 만든 래퍼다:

```bash
PGBENCH(){ docker exec -i ... "$CONTAINER" pgbench -U "$PGUSER_" "$@"; }
PGBV=$(PGBENCH --version ...)      # → pgbench -U tuner --version
```

실측:

```
pgbench --version          → pgbench (PostgreSQL) 16.13     ✓
pgbench -U tuner --version → unrecognized option '--version'  ✗
pgbench -U tuner -V        → invalid option -- 'V'            ✗
```

**메타 옵션(`--version`, `--help`)은 다른 옵션이 앞서면 안 먹는다.** 래퍼가 인자를
앞에 끼워 넣는 설계라면 메타 옵션에는 래퍼를 쓰면 안 된다 — 별도 경로로 부른다.

그리고 실패 메시지가 또 원인을 가렸다. "pgbench 를 찾을 수 없습니다"는 `2>/dev/null` 로
버린 stderr 안에 답이 있었는데 그걸 안 보여 줬다. 이제 **받은 출력을 그대로 찍고**
직접 확인할 명령(`docker exec -i <컨테이너> pgbench --version`)을 같이 준다.

> 오늘 네 번째로 **"도구가 없다"가 아닌 것을 "없다"고 보고한 경우**다.
> (pg_isready 없음 → "클러스터 down" / psql 없음 → "인덱스 없음" /
>  tsql 이 psql 직접 호출 → "안 막혔다(2ms)" / 여기)
> 공통점은 하나다 — **stderr 를 버리고 빈 값을 다른 뜻으로 읽었다.**
> 빈 값을 판정에 쓸 때는 '왜 비었는지'를 같이 남겨야 한다.

#### ②의 표가 통째로 0 이었다 — pgbench 의 `-f` 를 컨테이너로 안 옮겼다

`git pull` 뒤 사용자의 `t9-isolation-levels` 가 끝까지 돌았는데 ②가 이랬다:

```
  READ COMMITTED    없음 (max-tries=1)            0          ?          0
  ... (여섯 줄 전부 0 / ? / 0)
```

그리고 ③이 그 위에서 **"②에서 직렬화 실패를 수백 건 낸 뒤의 상태"** 라고 말했다 —
한 건도 안 났는데. 내 환경(host 경로)에서는 140/135/137/144/115/105 에 실패
0/0/14/0/125/0 으로 교과서처럼 나왔다. **차이는 docker 경로뿐이다.**

원인: `PGBENCH -d "$DB" -n -f "$TMPD/wa.sql" -f "$TMPD/wb.sql" ...` — `-f` 파일이
호스트 경로라 컨테이너 안의 pgbench 가 못 찾는다. 다른 스크립트의 `-f` 는 `pg_stage` 로
감쌌는데 **여기만 놓쳤다**(그 파일에서 `qf()` 만 고치고 이 호출을 안 봤다).

같은 함정이 `tpcds/mt-tenant-isolation.sh` 에도 있었다 — psql 은 폴백이 있는데
`pgbench` 가 맨 호출이었다. 둘 다 고쳤다.

**그리고 더 나쁜 것은 조용히 0 으로 찍힌 것이다.** `2>&1` 로 잡은 pgbench 출력에
에러가 들어 있었는데 아무도 안 봤고, `${TPS:-0}` 가 그걸 0 으로 바꿔 표에 넣었다.
이제 TPS 가 비면 **받은 출력을 찍고 중단**한다.

> 오늘 다섯 번째 같은 계열이다. 이번 것의 교훈은 앞의 넷보다 한 겹 더 나쁘다 —
> 앞의 넷은 "실행이 안 됐는데 실패 메시지가 엉뚱했다"였는데, 이번엔
> **"실행이 안 됐는데 그럴듯한 표가 나왔고, 다음 절이 그 표를 근거로 문장을 썼다."**
> `${VAR:-0}` 는 편의 문법이 아니라 **판정을 오염시키는 기본값**이다.
> 측정값에는 쓰지 않는다.

#### ②가 제대로 돌자 ③이 또 고정 숫자를 말했다

`-f` 스테이징을 고친 뒤 사용자의 SF=10 ②가 제대로 나왔다:

| 격리수준 | TPS | 실패 | 재시도 |
|---|---|---|---|
| RC / RC+재시도 | 9 / 11 | **0** / 0 | 0 / 0 |
| RR / RR+재시도 | 9 / 7 | **2** / 0 | 0 / 4 |
| SER / SER+재시도 | 8 / 6 | **17** / 0 | 0 / 10 |

**절의 주장은 그대로 재현됐다** — RC 실패 0, SER 이 RR 보다 훨씬 많이 실패,
재시도를 붙이면 전부 복구되고 TPS 가 준다.

그런데 ③이 **"②에서 직렬화 실패를 수백 건 낸 뒤"** 라고 찍었다. 실제는 19건이다.
SF=10 은 TPS 가 142 → 9 로 떨어져(파생 6,000만 행이라 트리거 갱신이 디스크로 나간다)
8초에 64~72건밖에 못 돈다. **건수가 규모를 따라가는데 문장은 고정돼 있었다.**

그리고 "SER 은 실패가 RR 의 **10배**" 도 고정값이었다. 5회 실측:
223/20 = 11.2 · 151/19 = 7.9 · 116/17 = 6.8 (SF=0.5) · 17/2 = 8.5 (SF=10).
**평균 8배 안팎이고 10배는 그중 한 값이었다.**

고친 것: 실패 건수와 트랜잭션 수(`tps × 초`)를 기억해 두고 —
- SER/RR 배수를 **측정에서 계산**해 찍는다
- ③이 실제 합계를 말한다(`19건` / `133건`)
- 조건당 300건 미만이면 "건수가 아니라 **비율**로 비교할 것"과 실패율을 같이 찍는다

구현 중 `set -u` 에 또 걸렸다 — 연관 배열 키가 소문자 격리수준인 줄 알았는데
실제로는 **표시용 대문자 라벨**(`SERIALIZABLE`)이었다. `LEVELS` 가
`'serializable:SERIALIZABLE'` 형태고 `LBL="${e#*:}"` 로 오른쪽을 쓴다.
`unbound variable` 로 죽어서 바로 잡혔다 — `set -u` 가 이번엔 도움이 됐다.

#### "SF=10 이 느린 건 행 수 때문인가" — 가설을 세우고 **틀렸다**

사용자가 물었다. SF=0.5 에서 TPS 142, SF=10 에서 7~9 — 16~20배 차이다.

**먼저 확인한 것: 트랜잭션당 일의 양은 규모와 무관하다.** 고객당 주문 10건,
고객당 lineitem 40행은 TPC-H 상수다(실측). 그러니 "행이 많아서 일이 많다"가 아니다.

**세운 가설: 데이터가 `shared_buffers`(1GB)를 넘어서 I/O 가 된다.**
SF=0.5 는 lineitem+orders 가 835MB 라 들어가고, SF=10 은 약 17GB 라 안 들어간다.

**검증 — 틀렸다.** SF=0.5 에서 `shared_buffers` 만 1GB → 48MB(21배 축소)로 줄였더니:

| | TPS (RC/재시도없음) |
|---|---|
| shared_buffers 1GB | 140 |
| shared_buffers 48MB | **111** (1.26배 하락) |
| 48MB + OS 페이지 캐시까지 비움 | **115** (차이 없음) |

**21배 줄여도 1.26배다.** OS 페이지 캐시가 받아 주기 때문이고, 캐시를 비워도
SF=0.5 데이터(약 1.2GB)는 15GB RAM 에 곧바로 다시 들어온다.

→ **`shared_buffers` 로는 설명이 안 된다.** 남은 후보는 데이터가 **RAM 전체**를
  넘는 경우다(SF=10 은 파생 테이블까지 약 24GB). 그러면 인덱스 유지·조회가 진짜
  디스크 I/O 가 되고, 이건 MySQL 쪽에서 본 버퍼 풀 절벽과 같은 계열이다.
  **다만 이 컨테이너에는 SF=10 데이터가 없어 재현하지 못했다 — 확인 안 된 설명이다.**

사용자 쪽에서 판별할 방법(캐시 적중률):

```sql
SELECT pg_stat_reset();                                   -- 실행 전
-- 스크립트 실행
SELECT blks_hit, blks_read,
       round(100.0*blks_hit/nullif(blks_hit+blks_read,0),1) AS hit_pct
  FROM pg_stat_database WHERE datname='tpch';             -- 실행 후
```

`hit_pct` 가 낮으면 I/O 가 맞고, 99% 이상이면 병목이 다른 데 있다.

> **곁가지로 측정 조건을 깨뜨릴 뻔했다.** 되돌리려고 `ALTER SYSTEM RESET shared_buffers`
> 를 썼는데, 그건 **설정 파일 기본값(128MB)** 으로 돌아가지 랩 조건인 1GB 로 돌아가지
> 않는다. `--check` 가 잡아 줘서 바로 고쳤다. **RESET 은 '원래대로'가 아니라
> '내가 안 정한 상태로'다** — 원래 값이 ALTER SYSTEM 으로 정해져 있었다면 다르다.

#### "2시간째 멈춰 있다" — 멈춘 게 아니라 파생 테이블을 17번 다시 만들고 있었다

사용자가 SF=10 에서 `t9-change-queue` 를 돌리다 ③-b 에서 2시간을 기다렸다.
그리고 다른 AI 의 분석을 가져와 "어떻게 생각하냐"고 물었다. 그 분석의 진단은
**"큐에 쌓인 부채를 워커가 감당 못 해 시스템이 지연에 빠진 것"** 이었다.

**틀렸다.** 워커 대기는 `QW -ge 600` 으로 60초 상한이 걸려 있어 거기서 멈출 수 없다.
진짜 원인은 `refill()` 이다 — lineitem 전체를 orders·customer 와 조인해 파생 테이블을
다시 만드는 일인데, 이 스크립트는 그걸 **17회** 한다(①4 + ②1 + ③ 5×2 + ④1 + ⑤1).

실측: SF=0.5(300만 행)에서 refill 1회 **6.5초**. 17회면 110초.
SF=10(6,000만)이면 선형이어도 **36분**, 데이터가 RAM 을 넘으면 그보다 나쁘다.

→ 공용 가드 `scripts/_scale-guard.inc` 를 만들어 §T-9 일곱 스크립트에 붙였다.
  lineitem 이 SF=1 수준을 넘으면 **재생성 횟수 × 실측 단가**로 추정치를 찍고 멈춘다.

| 스크립트 | refill | SF=10 추정 |
|---|---|---|
| `t9-change-queue` | 17회 | **36분** |
| `t9-concurrency` · `t9-notify-vs-poll` · `t9-lock-range` | 4회 | 8분 |
| `t9-queue-tuning` | 3회 | 6분 |
| `t9-trigger-sync` | 2회 | 4분 |
| `t9-isolation-levels` | 1회 | 2분 |

**그리고 가드는 "SF=0.5 로 돌려라"고 권한다.** §T-9 가 재는 것은 쓰기 지연·피해 반경·
정합성 지연의 트레이드오프이고, 오늘 SF=0.5 와 SF=10 양쪽에서 같은 방향으로 재현됐다.
**규모를 키워서 새로 배우는 것이 없다** — 그래서 막지 않고(FORCE=1) 말해 준다.

붙이면서 두 번 틀렸다: 가드를 `sql()` 정의보다 **앞**에 넣어 `sql: command not found` 가
났고(일곱 개 중 여섯 개), `t9-isolation-levels` 는 `$NLI` 를 정의 전에 참조했다.
둘 다 SF=0.5 실행으로 바로 잡혔다 — **가드를 넣을 때도 넣고 돌려 봐야 한다.**
