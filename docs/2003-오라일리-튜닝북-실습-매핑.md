# 2003 오라일리 튜닝 명저 × SQL Tuning Lab 실습 매핑

Dan Tow 《SQL Tuning》과 Cary Millsap 《Optimizing Oracle Performance》의 장별 핵심 개념을
이 프로젝트(sql-tuning-lab)에서 **직접 실행 가능한 실습**으로 매핑한 문서다.

두 책은 Oracle 기준으로 쓰였지만 원리는 DBMS 독립적이다. 이 랩은 PostgreSQL / MySQL /
ClickHouse에서 같은 원리를 재현한다. 먼저 용어부터 환산한다.

## 0-1. DB 접속 (세 가지 클라이언트)

각 실습의 SQL은 아래 클라이언트에서 직접 실행하거나,
쿼리 파일을 `queries/`에 추가해 `run` 명령으로 돌린다.

```bash
# PostgreSQL — tpch / tpcds / pgbench_lab
docker exec -it tuninglab-postgres psql -U tuner -d tpch
docker exec -it tuninglab-postgres psql -U tuner -d tpcds
docker exec -it tuninglab-postgres psql -U tuner -d pgbench_lab

# MySQL — tpch / tpcds / sysbench_lab
docker exec -it tuninglab-mysql mysql -u tuner -ptuner tpch
docker exec -it tuninglab-mysql mysql -u root  -proot  sysbench_lab   # 전역 변수 변경용

# ClickHouse — gharchive
docker exec -it tuninglab-clickhouse clickhouse-client \
  --user tuner --password tuner --database gharchive
```

한 줄만 실행할 때는 접속하지 않고 바로 던져도 된다:

```bash
docker exec tuninglab-postgres psql -U tuner -d tpch -c "SELECT count(*) FROM lineitem"
docker exec tuninglab-mysql mysql -u tuner -ptuner tpch -e "SELECT count(*) FROM lineitem"
docker exec tuninglab-clickhouse clickhouse-client --user tuner --password tuner \
  --query "SELECT count() FROM gharchive.github_events"
```

클라이언트별로 알아둘 것:

| | 실행시간 표시 | `--query`/`-c` 에 여러 문장 | 스크립트 파일 |
|---|---|---|---|
| psql | `\timing on` 필요 | `-c "a; b"` 가능 | `\i file.sql` |
| mysql | 기본 출력 | `-e "a; b"` 가능 | `source file.sql` |
| clickhouse-client | 기본 출력 | `--multiquery` 붙여야 함 | `--queries-file file.sql` |

> ClickHouse 접속 정보는 `docker/docker-compose.yml`의
> `CLICKHOUSE_USER` / `CLICKHOUSE_PASSWORD` 에서 오고,
> `gharchive` 데이터베이스는 `clickhouse-lab` 의 `schema` 명령이 만든다.
> 즉 `schema` 를 아직 실행하지 않았다면 `--database gharchive` 는 실패한다.
> 그때는 `--database` 를 빼고 접속한 뒤 `SHOW DATABASES` 로 확인한다.

## 0-2. ClickHouse 는 용어가 다르다

컬럼 저장 엔진이라 위 대응표가 그대로 적용되지 않는다. 별도로 정리한다.

| 개념 | PostgreSQL | ClickHouse |
|---|---|---|
| 실행계획 (추정) | `EXPLAIN` | `EXPLAIN indexes = 1` (granule pruning 표시) |
| 실행계획 (실측) | `EXPLAIN (ANALYZE, BUFFERS)` | `EXPLAIN PIPELINE` + `system.query_log` 조회 |
| 읽은 데이터량 | `Buffers: shared hit/read` | `system.query_log.read_rows`, `read_bytes` |
| 인덱스 | B-Tree (`CREATE INDEX`) | `ORDER BY` 절 = Primary Key (테이블 정의에 내장) |
| 통계 갱신 | `ANALYZE` | 불필요 (파트 메타데이터 사용) |
| 테이블 크기 | `pg_relation_size()` | `system.parts` (압축/비압축 모두 조회 가능) |

ClickHouse 에는 `EXPLAIN ANALYZE` 가 없다. 실측값은 실행 후 로그에서 꺼낸다:

```sql
-- 방금 실행한 쿼리들의 실측 비용 (clickhouse-client 에서)
SYSTEM FLUSH LOGS;
SELECT query_duration_ms, read_rows, formatReadableSize(read_bytes) AS read,
       formatReadableSize(memory_usage) AS mem, substring(query, 1, 60) AS q
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time > now() - INTERVAL 10 MINUTE
ORDER BY event_time DESC LIMIT 10;
```

`read_rows` 가 ClickHouse 판 LIO 다. Primary Key 정렬이 잘 맞으면
전체 행수의 일부만 읽고 끝나며(granule pruning), 어긋나면 전부 읽는다 —
§T-2에서 본 "선택도 vs 실제로 읽는 양"의 컬럼 스토어 버전이다.

## 0-4. 모듈별 명령어 대응 — 이 문서의 예시는 `:tpch` 기준이다

**PART 1(T-0~T-9)의 명령 예시는 대부분 `:tpch` 로 적혀 있다.** 원리는 모듈과 무관하지만
**명령을 그대로 복사하면 다른 모듈에서는 틀린다.** 아래 표로 환산해서 쓴다.

### 명령 동사는 같고, 인자가 다르다

`schema` / `load` / `analyze` / `vacuum` / `index` / `run` 은 `:tpch` 와 `:tpcds` 가 동일하다.
차이는 **데이터 생성 인자와 쿼리 이름**뿐이다.

| | `:tpch` | `:tpcds` |
|---|---|---|
| 데이터 생성 | `generate --sf=0.5` (스케일 팩터) | `generate --sales=1000000` (store_sales 행수) |
| 기본 데이터 경로 | `./data/tpch` (`.tbl`) | `./data/tpcds` (`.dat`) |
| 공식 생성기 | `scripts/tpch/gen-official-dbgen.sh` (dbgen) | `scripts/tpcds/gen-official-dsdgen.sh` (dsdgen) |
| 고속 적재 | `scripts/tpch/load-postgres-copy.sh` | `scripts/tpcds/load-postgres-copy.sh` |
| §T-2 선택도 스윕 | `scripts/tpch/t2-selectivity-sweep.sh` | `scripts/tpcds/t2-selectivity-sweep.sh` |
| §T-2 전환점 검증 | `scripts/tpch/t2-crossover-verify.sh` | `scripts/tpcds/t2-crossover-verify.sh` |
| §T-3·T-5 조인 방식 | `scripts/tpch/join-method-compare.sh` | `scripts/tpcds/join-method-compare.sh`<br>(같은 파일을 `MODULE=tpcds` 로 호출) |
| §T-4 인덱스 무력화 | (문서 내 SQL) | `scripts/tpcds/t4-index-defeat.sh` |
| 쿼리 이름 | `q01 q03 q05 q06 q09 q13 q18` | `q03_brand_by_year` `q07_demographics`<br>`q19_store_zip` `q67_window_rank` |
| DB 이름 | `tpch` | `tpcds` |

가장 자주 걸리는 것이 **쿼리 이름**이다. `--query=q03` 은 `:tpcds` 에 없다 —
`q03_brand_by_year` 로 써야 한다. 틀린 이름을 주면 사용 가능한 목록을 보여주고 멈춘다.

```
이런 쿼리가 없다: 'q03'
사용 가능: q03_brand_by_year, q07_demographics, q19_store_zip, q67_window_rank
```

> 예전에는 이 경우 **오류 없이 조용히 끝났다** — `SUMMARY (POSTGRES, 0 queries)` 만 INFO 로
> 찍혀서, 돌지도 않은 것을 돌았다고 착각하기 쉬웠다. 이 문서를 쓰면서 발견해 고쳤다.

```bash
# 같은 실습을 tpcds 로 옮길 때
./gradlew :tpch:bootRun  --args="run --db=postgres --query=q03 --explain=true"
./gradlew :tpcds:bootRun --args="run --db=postgres --query=q03_brand_by_year --explain=true"
```

### 어느 실습이 어느 모듈을 쓰는가

| 절 | 기본 모듈 | 다른 모듈로 옮길 수 있나 |
|---|---|---|
| §T-0 측정 위생 | 모듈 무관 | 원칙이므로 전부 적용된다 |
| §T-1 ~ §T-5 | `:tpch` | **`:tpcds` 로 그대로 가능**(위 표로 환산). 스타 스키마라 조인 순서·드라이빙 테이블 관찰에는 오히려 낫다 |
| §T-6 쿼리 다이어그램 | `:tpcds` | TPC-DS 스타 조인이 주제라 tpch 로는 의미가 약하다 |
| §T-7 ~ §T-9 | `:tpch` | `:tpcds` 가능. 단 §T-8·§T-9 의 실측 수치는 tpch `lineitem` 기준이다 |
| §M-1 ~ §M-3, §M-8 ~ §M-11 | `:tpch` | 대부분 모듈 무관(트레이스·LIO·배치 원리) |
| §M-4 ~ §M-7 | `:pgbench-lab` / `:sysbench-lab` | OLTP 부하가 주제라 tpch/tpcds 로는 대체 불가 |

**실측 수치는 옮겨지지 않는다.** 이 문서의 표에 적힌 ms·buffers 값은 전부
tpch SF=0.5(lineitem 300만 행) 기준이다. 다른 모듈·다른 스케일에서는 숫자가 달라지는 것이
정상이며, 비교해야 할 것은 절대값이 아니라 **경향**(어느 쪽이 빨라졌는가, 계획이 어떻게 바뀌었는가)이다.

### 명령 체계가 아예 다른 모듈

`:pgbench-lab` / `:sysbench-lab` / `:clickhouse-lab` 은 `schema→load→index` 구조가 아니다.
위 표로 환산되지 않으므로 각 모듈의 명령을 따로 쓴다(인자 없이 실행하면 사용법이 나온다).

| 모듈 | 명령 |
|---|---|
| `:pgbench-lab` | `init --scale=10` · `run --clients=8 --seconds=30` · `monitor` · `reset-stats` |
| `:sysbench-lab` | `prepare --tables=4 --table-size=100000` · `run --threads=8 --seconds=30 [--hot=true]` · `monitor` |
| `:clickhouse-lab` | `schema` · `load --from=... --to=... --hours=0-23` · `run [--query=...]` · `experiment --name=compression\|mv\|orderby` · `compare-compression` |

# PART 1. Dan Tow 《SQL Tuning》

## T-0 | 측정 위생 — 이걸 먼저 읽지 않으면 나머지 실습이 다 헛돈다

두 책 모두 "측정한 것만 믿어라"라고 말하지만, 2003년에는 없던 함정이 지금은 몇 개 더 있다.
아래 네 가지를 지키지 않으면 **원인을 잘못 짚게 된다**.

**① 한 번에 한 변수만 바꾼다.**
`index` 명령은 인덱스 생성과 통계 갱신(`ANALYZE`)을 **함께** 수행한다.
따라서 "index 전 → index 후"만 비교하면 개선이 인덱스 덕인지 통계 덕인지 알 수 없다.
통계 효과를 분리하려면 `analyze` 명령으로 통계만 먼저 갱신하고 한 번 측정한다.

**② EXPLAIN ANALYZE 한 번의 숫자를 성능 지표로 쓰지 않는다.**
`run` 명령은 새 커넥션을 열고 EXPLAIN을 먼저 수행하므로, 그 실행은 **세션 최초 실행**이다.
PostgreSQL의 JIT은 세션에서 처음 켜질 때 LLVM 비트코드 로딩 때문에 유독 비싸다.
성능 비교는 반복 측정한 `run`의 min/avg 값으로 하고, EXPLAIN 출력은 *계획의 모양*을 보는 데 쓴다.

**③ JIT이 결과를 지배하고 있는지 확인한다.**
EXPLAIN 출력 맨 아래 `JIT:` 블록의 `Timing ... Total`을 `Execution Time`과 비교한다.
Total이 실행 시간의 상당 부분이면, 측정하고 있는 것은 쿼리가 아니라 컴파일러다.
PostgreSQL은 추정 비용이 `jit_above_cost`(기본 100,000)를 넘으면 JIT을 켜고,
`jit_inline_above_cost` / `jit_optimize_above_cost`(각 500,000)를 넘으면 인라이닝·최적화까지 켠다.
**통계가 나쁘면 비용이 부풀려지고, 부풀려진 비용이 불필요한 JIT을 유발한다**는 연쇄에 주의한다.

**④ 캐시 상태를 의식한다.**
`run`의 기본 `--warmup=1`은 버퍼를 데운 뒤 측정한다(warm 측정).
cold 측정을 원하면 `--warmup=0`으로 두고, 필요하면 재시작한다.
EXPLAIN의 `Buffers: shared hit=... read=...`에서 read가 0이면 전부 메모리에서 처리된 것이다.

**⑤ VACUUM 여부가 계획을 바꾼다.**
갓 적재한 테이블은 visibility map 이 비어 있어 Index Only Scan 이 불리하게 평가된다.
그래서 **적재 직후와 운영 중인 테이블은 같은 쿼리에도 다른 계획**을 낸다(§T-4에 실측 사례).
어느 상태에서 측정하고 있는지 항상 알고 있어야 하며, 필요하면 명시적으로 맞춘다:

```sql
SELECT relallvisible, relpages FROM pg_class WHERE relname = 'orders';
```

```bash
./gradlew :tpch:bootRun --args="vacuum --db=postgres"   # VACUUM ANALYZE (통계 + visibility map)
./gradlew :tpch:bootRun --args="analyze --db=postgres"  # 통계만 (visibility map 은 건드리지 않음)
```

**⑥ 측정 전제를 만드는 단계가 그 전제를 깨뜨리지 않는지 본다.**
"통계 없는 상태"처럼 **무언가가 없는 상태**를 재려면, 그것을 만들지 않는 경로로 준비해야 한다.
여기서 실제로 두 군데가 걸린다.

- **적재 스크립트가 스스로 ANALYZE 를 돈다.** COPY 적재 스크립트는 기본적으로 마지막에
  `ANALYZE` 를 수행한다 — 운영에서는 옳지만 §T-1 지점 A 에서는 **정확히 그것이 없어야 한다.**
  그래서 `--no-analyze` 플래그를 두었다. 기본값은 그대로 ANALYZE 다 (§T-2 이후 대부분의
  실습은 통계가 있어야 하므로, 흔한 쪽을 기본값으로 둔다).
- **autovacuum 이 조용히 통계를 만든다.** 기본값은 `autovacuum_analyze_threshold=50`,
  `analyze_scale_factor=0.1`, `naptime=60s` 다. 대량 적재 직후 임계치는 즉시 넘으므로
  **길어야 1분 뒤 자동 ANALYZE 가 걸린다.** 적재하고 잠시 자리를 비우면 A 는 이미 B 가 되어 있다.
  지점 A 가 유독 재현되지 않는다면 대개 이것이 원인이다.

`--no-analyze` 는 **둘을 같이** 처리한다. ANALYZE 만 건너뛰고 autovacuum 을 두면
1 분 뒤 통계가 생겨 플래그가 약속을 어기기 때문이다.

```bash
scripts/tpch/load-postgres-copy.sh ./data/tpch --no-analyze   # ANALYZE 생략 + autovacuum off
# ... 지점 A 측정 ...
scripts/tpch/load-postgres-copy.sh --restore-autovacuum        # 끝나면 반드시 원복
```

원복을 잊으면 원칙 ⑤(VACUUM 이 계획을 바꾸는 문제)가 대신 생긴다.

**실측 확인** (PostgreSQL 16.13, 기본 설정, 20만 행 적재)

| | 통계 컬럼 수 | `reltuples` | `last_autoanalyze` |
|---|---|---|---|
| 적재 직후 | 0 | -1 (모름) | (없음) |
| 70초 뒤 | **2** | **200,000** | **기록됨** |
| `autovacuum_enabled=off` 로 적재 후 90초 뒤 | 0 | -1 | (없음) |

가만히 둔 것뿐인데 1분 만에 통계가 생겼다. 끄면 안 생긴다 — 해법도 같이 확인했다.

일반화하면 이렇다 — **"없음"을 측정하는 실험은 "있음"을 측정하는 실험보다 깨지기 쉽다.**
있는 것은 유지되지만, 없는 것은 시스템이 알아서 채워 넣기 때문이다.

## T-1 | 1장 개요 — "튜닝의 본질은 최적 실행계획 찾기"

책의 3단계(①현재 계획 확인 → ②계획 변경 → ③최선의 계획 판단)를 기본 루프로 삼되,
T-0 ①에 따라 **변수를 하나씩** 바꿔 네 지점에서 측정한다.

```bash
# ── 지점 A: 적재 직후 (인덱스 없음, 통계 없음) ──────────────────
./gradlew :tpch:bootRun --args="run --db=postgres --query=q03 --explain=true"

# ── 지점 B: 통계만 갱신 (인덱스는 아직 없음) ────────────────────
./gradlew :tpch:bootRun --args="analyze --db=postgres"
./gradlew :tpch:bootRun --args="run --db=postgres --query=q03 --explain=true"

# ── 지점 C: 인덱스 추가 ────────────────────────────────────────
./gradlew :tpch:bootRun --args="index --db=postgres"
./gradlew :tpch:bootRun --args="run --db=postgres --query=q03 --explain=true"
```

> **지점 A 를 실제로 재려면 두 가지를 먼저 막아야 한다**(§T-0 ⑥).
> ⓐ 적재 후 `ANALYZE` 가 돌지 않아야 하고, ⓑ autovacuum 도 꺼져 있어야 한다.
> COPY 스크립트의 `--no-analyze` 가 둘을 함께 처리한다(끝나면 `--restore-autovacuum`).
> JDBC `load` 로 넣는 경우에도 ⓑ 는 따로 챙겨야 한다.
>
> A 는 "느린 상태"가 아니라 **"통계가 없는 상태"** 를 재는 지점이다.
> 통계가 생긴 뒤에 잰 A 는 B 를 두 번 잰 것이고, 그러면 이 실습의 결론
> (통계 기여 85% / 인덱스 15%)이 통째로 사라진다.

지점 D(JIT 영향 분리)는 psql에서 세션 변수로 확인한다.
psql 접속은 `docker exec -it tuninglab-postgres psql -U tuner -d tpch`:

> **아래 SQL 과 접속은 `:tpch` 전용이다.** DB 이름도 쿼리도 TPC-H 것이므로 tpcds 에서는
> 그대로 안 돌아간다. 게다가 tpcds 에서는 **JIT 이 애초에 안 켜져서** 이 절차로는 아무것도
> 관찰되지 않는다 — tpcds 판 절차는 이 절 끝의 "지점 D 를 `:tpcds` 에서 보려면" 참조.

```sql
\timing on

-- 먼저 기본 상태로 실행 → 출력 맨 아래 JIT: 블록의 Total 을 확인
EXPLAIN (ANALYZE, BUFFERS)
SELECT l_orderkey, sum(l_extendedprice * (1 - l_discount)) AS revenue,
       o_orderdate, o_shippriority
FROM customer, orders, lineitem
WHERE c_mktsegment = 'BUILDING'
  AND c_custkey = o_custkey AND l_orderkey = o_orderkey
  AND o_orderdate < date '1995-03-15' AND l_shipdate > date '1995-03-15'
GROUP BY l_orderkey, o_orderdate, o_shippriority
ORDER BY revenue DESC, o_orderdate
LIMIT 10;

-- JIT 만 끄고 동일 쿼리 재실행 → JIT: 블록이 사라지고 그만큼 시간이 준다
SET jit = off;
-- (위 EXPLAIN 문을 그대로 다시 실행)
RESET jit;
```

기록할 표(자기 환경의 숫자로 채운다):

| 지점 | 조인 방식 | Execution Time | 그중 JIT | buffers (hit+read) | 추정행 vs 실제행 |
|---|---|---|---|---|---|
| A 적재 직후 | | | | | |
| B 통계만 | | | | | |
| C 인덱스까지 | | | | | |
| D C + jit off | | | | | |

### 참고: 실제 측정값 (SF=0.5, PostgreSQL 16, shared_buffers=1GB, work_mem=64MB)

절대값은 환경마다 다르지만 **비율과 방향**은 재현될 것이다.
각 지점은 워밍업 3회 후 7회 측정한 중앙값이다.

| 지점 | 상태 | 중앙값 | 조인 방식 | 추정행 vs 실제행 |
|---|---|---|---|---|
| A | 통계 ✗ 인덱스 ✗ | 1,296 ms | Merge Join + Parallel Hash Join | 113,139,667 vs 15,164 (**7,461배**) |
| D | A + `SET jit=off` | 734 ms | 〃 | 〃 |
| B | 통계 ✓ 인덱스 ✗ | 375 ms | Parallel Hash Join (Merge Join 소멸) | 추정 정상화 |
| C | 통계 ✓ 인덱스 ✓ | 215 ms | Nested Loop + Index Scan | 51,018 vs 3,791 (13배) |

전체 개선 1,296 → 215 ms 중 **통계가 921 ms(85%), 인덱스가 160 ms(15%)** 를 담당했다.
즉 이 쿼리에서 진짜 범인은 인덱스 부재가 아니라 **통계 부재**였다.
`index` 명령만 실행하고 "인덱스 덕분에 6배 빨라졌다"고 결론 내렸다면 완전히 틀린 진단이다.

A→D 차이 562 ms는 전부 JIT 컴파일이다. A 시간의 43%가 쿼리 처리가 아니라 컴파일이었고,
그 원인은 7,461배 과대추정 → 비용 3,733,552 → JIT 임계값 3개 모두 초과라는 연쇄다.
**나쁜 통계가 나쁜 계획뿐 아니라 불필요한 JIT까지 유발한다**는 것을 수치로 확인할 수 있다.

### 해석 체크포인트

A→B에서 계획이 바뀌고 시간이 크게 줄었다면 개선의 원인은 **인덱스가 아니라 통계**다.
A의 EXPLAIN에서 추정행과 실제행의 배율을 먼저 확인한다. 수백~수천 배 차이가 나면
그 비용 추정 위에 세워진 모든 판단(조인 방식, JIT 여부)이 틀린 전제 위에 있다.

B→C에서 조인 방식이 Hash/Merge에서 Nested Loop + Index Scan으로 바뀌는지 본다.
이것이 T-5·T-6에서 다룰 "로바스트 플랜"의 실물이다.

**측정 함정 실례**: 인덱스를 막 만든 직후 EXPLAIN ANALYZE를 한 번만 돌리면
C가 B보다 *느리게* 나온다(인덱스 페이지가 아직 캐시에 없어 물리 읽기가 발생).
위 표를 만들 때도 단발 측정에서는 C=1,211 ms로 B보다 느렸다가,
워밍업 후 반복 측정하니 215 ms로 뒤집혔다. T-0 ②·④를 반드시 지킬 것.

**LIO가 늘었는데 더 빨라졌다면 그것도 정답이다.** 순차 스캔은 버퍼 접근당 처리 행 수가 많고,
인덱스 probe는 접근 횟수가 많은 대신 개당 비용이 싸다. LIO는 목표가 아니라 지표다.
줄여야 할 것은 LIO 자체가 아니라 *불필요한* 접근이며, 그 판단은 T-8에서 이어진다.

### 같은 실습을 `:tpcds` 로 — 결론이 뒤집힌다

§0-4 의 대응표대로 TPC-DS(store_sales 200만 행, 수록 쿼리 4개 전부)로 같은 실습을 돌렸다.
지점 A 는 `--no-analyze` 로 만들었다(§T-0 ⑥ — ANALYZE 생략 + autovacuum off).
**상태 전환이 순차적이라 교차 측정이 불가능하므로, A→B→C 전 과정을 2회 반복**했다.

| 쿼리 | A (통계✗ 인덱스✗) | B (통계✓) | C (통계✓ 인덱스✓) | 인덱스 효과 |
|---|---|---|---|---|
| `q03_brand_by_year` | 75.3 / 77.7 ms | 70.7 / 71.8 | **4.6 / 4.0** | **19배** |
| `q07_demographics` | 162.8 / 171.7 | **206.1 / 195.5** | 172.3 / 165.4 | 없음 |
| `q19_store_zip` | 132.9 / 134.2 | 148.4 / 141.3 | **37.4 / 35.4** | **3.8배** |
| `q67_window_rank` | 204.9 / 206.7 | 174.7 / 167.6 | 186.1 / 175.9 | 없음 |

(1회차 / 2회차 min, warmup=1 iterations=5. 두 회차의 순서가 모든 칸에서 일치한다.)

**① TPC-H 의 결론이 그대로 오지 않는다.** TPC-H q03 은 통계 85% / 인덱스 15% 였는데,
TPC-DS 에서는 **인덱스가 지배적이고 통계 기여는 미미하거나 음수**다.
이유는 스키마 모양에 있다 — 스타 스키마에서 차원 필터(`i_manufact_id=128` → 2만 중 20건)가
아무리 선택적이어도, **인덱스가 없으면 store_sales 200만 행 풀스캔 말고는 경로가 없다.**
통계는 "어느 경로가 싼가"를 판단하게 해줄 뿐, **없는 경로를 만들어 주지는 못한다.**

**② 통계를 넣었더니 느려진 쿼리가 있다.** `q07_demographics` 는 A→B 에서 22% / 14% 느려졌고
두 회차 모두 재현됐다(각 회차의 p95 와 min 구간이 겹치지 않는다). 계획을 보면 원인이 명확하다.

```
-- B (통계 있음)
Join Filter: (store_sales.ss_item_sk = item.i_item_sk)
Rows Removed by Join Filter: 2305382      ← 230만 행을 조인 후에 버린다
```

통계가 생기자 옵티마이저가 `item` 조인을 Hash Join 에서 **Join Filter(중첩 루프)** 로 바꿨고,
그 판단이 틀렸다. §T-3 의 "옵티마이저의 선택은 검증 대상이다"가 T-1 에서 이미 나타난 것이다.
**통계는 옳은 판단의 재료일 뿐 옳은 판단 자체가 아니다.**

**③ 인덱스 효과도 쿼리마다 극단적으로 갈린다.** q03 은 19배, q19 는 3.8배인데
q07·q67 은 사실상 0 이다. 갈리는 지점은 "차원 필터가 팩트 테이블 접근을 얼마나 줄이는가"다 —
q03 은 `ss_item_sk` 로 20건짜리 아이템만 훑으면 되지만(`Index Scan ... loops=20`),
q67 은 윈도우 함수라 어차피 전체를 정렬해야 한다.

**④ JIT 연쇄가 일어나지 않는다.** TPC-H 지점 A 에서는 부풀려진 비용이 JIT 임계값을 넘겨
시간의 43% 를 컴파일에 썼는데, TPC-DS 에서는 **네 쿼리 모두 A~C 어디서도 JIT 이 안 켜졌다.**
추정 비용이 47,079~66,269 로 `jit_above_cost`(100,000)에 미치지 못하기 때문이다.
지점 D 를 tpcds 에서 관찰하려면 임계값을 낮춰 강제해야 한다 — 아래 참조.

> **주의**: 이 표의 절대값을 TPC-H 표와 비교하면 안 된다(§0-4). 스케일도 스키마도 다르다.
> 비교할 것은 **"통계와 인덱스 중 무엇이 지배했는가"** 라는 구조적 답이고, 그것이 뒤집혔다는 것이
> 이 실습의 결과다.

### 지점 D 를 `:tpcds` 에서 보려면 — 강제로 켜야 한다

위 ④ 때문에 tpch 용 D 절차(`SET jit=off` 로 껐다 켜기)를 그대로 쓰면 **아무 차이가 없다.**
애초에 켜져 있지 않기 때문이다. 먼저 켜지는지부터 확인한다.

```bash
docker exec -it tuninglab-postgres psql -U tuner -d tpcds     # DB 이름이 tpcds 다
```

```sql
\timing on
-- ① 지금 JIT 이 켜지는가? 출력에 JIT: 블록이 없으면 안 켜진 것이다.
EXPLAIN (ANALYZE, BUFFERS) <queries/q67_window_rank.sql 내용>;

-- ② 안 켜진다면 임계값을 낮춰 강제한다 (JIT 이 얼마짜리인지 보기 위해)
SET jit_above_cost = 0;
SET jit_inline_above_cost = 0;
SET jit_optimize_above_cost = 0;
EXPLAIN (ANALYZE, BUFFERS) <같은 쿼리>;

-- ③ 같은 조건에서 JIT 만 끄고 비교
SET jit = off;
EXPLAIN (ANALYZE, BUFFERS) <같은 쿼리>;
RESET ALL;
```

**실측** (q67_window_rank, store_sales 200만 행)

| | Execution Time | JIT |
|---|---|---|
| 기본 (cost 52,909 < 100,000) | 277 ms | **안 켜짐** |
| 강제 발동 | 757 ms | Functions 134, **Total 1,941.9 ms** |
| 강제 조건에서 `jit=off` | **252 ms** | — |

250ms 짜리 쿼리를 위해 **1.9초를 컴파일에 쓴다.** JIT Total 이 Execution Time 보다 큰 것은
병렬 워커별 컴파일 시간이 합산되기 때문이다.
`jit_above_cost` 라는 임계값이 왜 있는지가 이 표에 그대로 나온다 —
**JIT 은 공짜가 아니라, 그 비용을 회수할 만큼 무거운 쿼리에서만 이득**이다.
TPC-H 지점 A 에서 JIT 이 문제가 됐던 것은 JIT 이 나빠서가 아니라,
**나쁜 통계가 비용을 부풀려 회수 불가능한 쿼리에 JIT 을 켜게 만들었기** 때문이다.

## T-2 | 2장 데이터 접근 기초 — 20% / 0.5% 법칙과 풀스캔↔인덱스 전환점

책: 전체 행의 20% 초과 조회는 풀스캔, 0.5% 미만은 인덱스가 유리.
그 전환점이 **내 하드웨어·설정에서 실제로 몇 %인지** 직접 측정하는 것이 이 실습의 목적이다.

선행 조건: `schema` → `load` → `index` 까지 완료된 상태.

### 방법 1 — 스크립트로 한 번에 (권장)

```bash
./scripts/tpch/t2-selectivity-sweep.sh          # 현재 설정
./scripts/tpch/t2-selectivity-sweep.sh 4.0      # random_page_cost=4.0 (HDD 가정) 비교
```

조회 범위를 1일부터 3년까지 넓혀가며 선택도·스캔 방식·buffers·시간을 표로 출력한다.

### 방법 2 — psql 에서 직접

psql 접속 (docker compose 로 띄운 경우):

```bash
docker exec -it tuninglab-postgres psql -U tuner -d tpch
```

접속 후 아래를 실행한다. `interval` 값만 바꿔가며 **여러 번** 실행하는 것이 실습의 전부다:

```sql
\timing on

-- 전체 행수 (선택도 계산용)
SELECT count(*) FROM lineitem;

-- ① 이 범위에 몇 건이 걸리는지 → 선택도 = 이 값 / 전체 행수
SELECT count(*) FROM lineitem
WHERE l_shipdate >= date '1994-01-01'
  AND l_shipdate <  date '1994-01-01' + interval '1 day';

-- ② 같은 범위로 계획 확인
EXPLAIN (ANALYZE, BUFFERS)
SELECT sum(l_extendedprice * l_discount) FROM lineitem
WHERE l_shipdate >= date '1994-01-01'
  AND l_shipdate <  date '1994-01-01' + interval '1 day';
```

`'1 day'` 자리를 `'15 day'` → `'1 month'` → `'3 month'` → `'6 month'` → `'1 year'`
→ `'18 month'` → `'20 month'` → `'2 year'` → `'3 year'` 로 바꿔가며 ①②를 반복하고,
스캔 방식이 바뀌는 지점을 기록한다. `random_page_cost` 비교는 세션 변수로:

```sql
SET random_page_cost = 4.0;   -- HDD 가정
-- ② 를 다시 실행 → 전환점이 앞당겨지는지 확인
RESET random_page_cost;
```

### 참고: 실제 측정값 (SF=0.5 = lineitem 300만 행, PostgreSQL 16, random_page_cost=1.1)

| 범위 | 조회 행수 | 선택도 | 스캔 방식 | 시간 |
|---|---|---|---|---|
| 1 day | 1,281 | 0.043% | **Index Scan** | 3.4 ms |
| 15 day | 18,861 | 0.629% | Bitmap Heap Scan | 47.2 ms |
| 1 month | 39,213 | 1.307% | Bitmap Heap Scan | 50.2 ms |
| 6 month | 226,657 | 7.554% | Bitmap Heap Scan | 174.1 ms |
| 1 year | 453,459 | 15.113% | Bitmap Heap Scan | 289.2 ms |
| 18 month | 679,323 | 22.640% | Bitmap Heap Scan | 327.3 ms |
| 20 month | 756,799 | 25.223% | **Parallel Seq Scan** | 302.1 ms |
| 3 year | 1,363,921 | 45.457% | Parallel Seq Scan | 422.4 ms |

**전환점은 22.6% ~ 25.2% 사이** — 책이 말한 20% 기준과 놀랄 만큼 가깝다.
2003년의 경험칙이 SSD 시대에도 대체로 살아 있다는 뜻이다.
`random_page_cost`를 4.0(HDD 가정)으로 올리면 전환점이 22.6% 아래로 내려간다.
다만 비트맵 스캔은 랜덤 접근을 순차화하므로 이 파라미터에 덜 민감해 이동 폭은 크지 않다.

**책의 "0.5% 미만이면 인덱스"는 절반만 맞다.** plain Index Scan 이 선택된 것은 0.043%뿐이고,
0.1%~22%의 넓은 구간은 전부 **Bitmap Heap Scan**이 가져갔다. 이유는 데이터 클러스터링이다:

```sql
SELECT attname, correlation FROM pg_stats
WHERE tablename='lineitem' AND attname IN ('l_shipdate','l_orderkey');
--  l_orderkey  =  1.0000   (저장 순서와 완전 일치)
--  l_shipdate  = -0.0049   (완전 분산)
```

`l_shipdate`는 상관도가 0에 가까워 인덱스 순서대로 힙을 읽으면 디스크를 헤집는다.
비트맵 스캔은 TID를 미리 정렬해 랜덤 접근을 순차 접근으로 바꾸는 기법으로,
Tow가 "0.5%~20% 구간은 클러스터링·캐시 히트율에 따라 판단"이라고만 남긴 회색지대에 대한
**현대 옵티마이저의 구체적인 답**이다. 2003년 책에 없는 것을 하나 배우는 지점이다.

### 심화 1: 옵티마이저가 바꾼 지점 ≠ 실제로 빨라지는 지점

위 sweep 은 옵티마이저가 **선택한** 계획을 보여줄 뿐, 그 선택이 옳았는지는 말해주지 않는다.
같은 범위에서 두 방식을 **모두 강제 실행**해 직접 비교해야 진짜 교차점을 알 수 있다.

```bash
./scripts/tpch/t2-crossover-verify.sh
```

psql 로 직접 하려면 같은 쿼리에 아래 두 설정을 번갈아 적용해 시간을 비교한다:

```sql
SET enable_seqscan = off;                                -- 인덱스/비트맵 강제
SET enable_bitmapscan = off; SET enable_indexscan = off; -- 순차 스캔 강제
RESET ALL;
```

실측 결과(SF=0.5, PostgreSQL 16, random_page_cost=1.1, 6회 최소값):

| 범위 | 선택도 | 비트맵이 읽은 페이지 | Bitmap 강제 | Seq 강제 | 실측 승자 | 옵티마이저 선택 |
|---|---|---|---|---|---|---|
| 1 month | 1.31% | 35.3% | 26.9 ms | 170.0 ms | Bitmap (6.33x) | Bitmap |
| 3 month | 3.81% | 56.9% | 92.5 ms | 182.6 ms | Bitmap (1.97x) | Bitmap |
| 6 month | 7.55% | 74.5% | 130.7 ms | 196.5 ms | Bitmap (1.50x) | Bitmap |
| 1 year | 15.11% | 92.1% | 202.6 ms | 221.8 ms | Bitmap (1.09x) | Bitmap |
| **18 month** | **22.64%** | **98.4%** | 252.5 ms | 222.5 ms | **SeqScan (1.13x)** | Bitmap ← **어긋남** |
| 20 month | 25.22% | 99.4% | 271.3 ms | 238.2 ms | SeqScan (1.14x) | Parallel Seq Scan |
| 3 year | 45.46% | 101.9% | 368.4 ms | 289.3 ms | SeqScan (1.27x) | Parallel Seq Scan |

**진짜 교차점은 15%~22% 사이인데 옵티마이저는 22%~25%에서 바꿨다.**
그 사이 구간에서는 옵티마이저가 13% 느린 계획을 고르고 있었다는 뜻이다.
비용 모델은 근사치이므로 이 정도 오차는 정상이지만, **"옵티마이저가 골랐으니 최선"이라는
가정은 검증 대상**이라는 것이 요점이다. Tow가 3단계 중 3번째("어떤 계획이 최선인지 판단")를
가장 중요하다고 한 이유가 이것이다.

세 번째 열이 원인을 그대로 보여준다. 선택도 1.31%에서 이미 테이블 페이지의 35%를,
7.55%에서 74.5%를, 22.64%에서는 **98.4%** 를 읽고 있다.
비트맵이 어차피 테이블 전체를 읽는 지점부터는 인덱스 탐색 + 비트맵 생성 비용이 순수 손해다.
**교차점은 "선택도 몇 %"가 아니라 "읽는 페이지가 전체의 몇 %냐"로 결정된다** —
그리고 그 둘의 관계를 정하는 것이 correlation, 즉 클러스터링이다.

### 심화 2: 클러스터링이 전환점을 얼마나 움직이는가

```sql
CLUSTER lineitem USING idx_lineitem_shipdate;   -- 물리 순서를 인덱스 순서에 맞춤 (대용량은 오래 걸림)
ANALYZE lineitem;
```

실측 결과 correlation 이 `-0.0049` → `1.0000` 으로 바뀌고, 스캔 선택이 완전히 뒤집힌다:

| 선택도 | CLUSTER 전 | CLUSTER 후 |
|---|---|---|
| 0.63% | Bitmap Heap Scan | **Index Scan** |
| 7.55% | Bitmap Heap Scan | **Index Scan** |
| 15.11% | Bitmap Heap Scan | **Index Scan** |
| 30.33% | Parallel Seq Scan | **Index Scan** |

**전환점이 사라진다.** 45% 선택도에서도 Seq Scan 이 선택되지 않는다.
같은 데이터·같은 인덱스·같은 쿼리인데 물리적 저장 순서 하나로 결론이 바뀐 것이다.

핵심은 **읽는 페이지 수가 선택도에 비례하게 된다**는 점이다(전체 61,235 페이지 기준):

| 선택도 | CLUSTER 전 읽은 페이지 | CLUSTER 후 | 감소 배수 |
|---|---|---|---|
| 0.043% | 1,252 (2.0%) | 31 (0.05%) | 40x |
| 1.307% | 21,602 (35%) | 838 (1.4%) | 26x |
| 7.554% | 45,667 (75%) | 5,012 (8.2%) | 9.1x |
| 15.113% | 56,458 (92%) | 10,033 (16.4%) | 5.6x |
| 45.457% | 61,235 (100%) | 30,192 (49.3%) | 2.0x |

CLUSTER 전에는 선택도 7.5%에 페이지의 75%를 읽었다(초선형).
CLUSTER 후에는 선택도 7.5%에 페이지의 8.2%를 읽는다(정확히 비례).
**correlation 이란 결국 "선택도 1%가 페이지 몇 %를 뜻하는가"의 환산율이다.**

`random_page_cost` 를 4.0으로 올려도 계획이 거의 바뀌지 않는다.
correlation 이 1.0이면 옵티마이저는 인덱스 접근이 사실상 순차 접근임을 알고
랜덤 페이지 비용을 할인해서 계산하기 때문이다. 비용 모델이 클러스터링을 이미 반영하고 있다는 증거다.

### CLUSTER 의 대가 — 물리 순서는 하나뿐이다

테이블의 물리적 순서는 **하나만** 가질 수 있다. shipdate 로 정렬했다는 것은
기존에 완벽했던 orderkey 정렬을 포기했다는 뜻이다:

```
CLUSTER 전:  l_orderkey = 1.0000   l_shipdate = -0.0009
CLUSTER 후:  l_orderkey = 0.0044   l_shipdate =  1.0000     ← 정확히 맞바꿔졌다
```

실측한 대가(SF=0.5, 8회 최소값):

| 쿼리 | CLUSTER 전 | CLUSTER 후 | 결과 |
|---|---|---|---|
| q06 계열 (l_shipdate 범위) | 226.6 ms / 56,458 buffers | **73.1 ms / 9,998** | **3.1x 개선** |
| q03 (l_orderkey 조인) | 225.8 ms / 500,808 buffers | **273.6 ms / 716,013** | **1.21x 악화** |

q03 이 느려진 이유는 명확하다. 한 주문의 lineitem 4건은 orderkey 순 저장에서 **같은 페이지**에
모여 있었지만, shipdate 순으로 재배치되면 각자 다른 날짜라 **서로 다른 4개 페이지**로 흩어진다.
NL 조인의 74,024번 probe 마다 그 대가를 치르므로 버퍼가 43% 늘었다.

**교훈**: 클러스터링은 공짜 최적화가 아니라 **어느 접근 경로를 우대할지 고르는 선택**이다.
Tow 9장이 "인덱스 추가 비용과 비즈니스 중요도를 비교 평가하라"고 한 판단이 여기에도 그대로 적용된다.
운영에서는 여기에 재클러스터링 비용까지 더해진다 — CLUSTER 는 일회성이라
이후 INSERT/UPDATE 가 쌓이면 순서가 다시 흐트러진다.

실습을 계속하려면 원래 상태로 되돌린다 — `schema` → `load` → `index` 재실행.

### 같은 실습을 `:tpcds` 로 — 스타 스키마에는 "날짜 컬럼"이 없다

```bash
./scripts/tpcds/t2-selectivity-sweep.sh          # 선택도 스윕
./scripts/tpcds/t2-crossover-verify.sh 4         # 강제 실행으로 진짜 전환점 찾기
```

tpch 판은 `lineitem.l_shipdate` 라는 **날짜 컬럼에 직접** 범위 필터를 건다.
스타 스키마에는 그런 컬럼이 없다 — `store_sales` 가 가진 것은 **대리키 `ss_sold_date_sk`** 이고,
사람이 쓰는 조건("1998년 3월")은 `date_dim` 을 거쳐야 한다.
그래서 같은 범위를 두 형태로 걸어 비교한다.

**① 팩트 직접 vs ② 차원 경유 — 전환점이 3~4배 차이 난다** (store_sales 200만 행)

| 선택도 | ① 팩트 직접 (`ss_sold_date_sk`) | ② 차원 경유 (`JOIN date_dim`) |
|---|---|---|
| 0.055% | Index Scan | Bitmap Heap Scan |
| 1.68% | Bitmap Heap Scan | Index Scan |
| 4.98% | Bitmap Heap Scan | Index Scan |
| **9.89%** | Bitmap Heap Scan | **Parallel Seq Scan** ← 전환 |
| 19.98% | Bitmap Heap Scan | Parallel Seq Scan |
| **30.06%** | **Parallel Seq Scan** ← 전환 | Parallel Seq Scan |

**같은 행을 고르는데 전환점이 다르다.** ①은 20~30% 구간에서, ②는 5~10% 구간에서 넘어간다.
차원을 거치면 옵티마이저가 **팩트 쪽 선택도를 조인 전에 알 수 없어** 보수적으로 잡기 때문이다.
실무 쿼리는 대부분 ② 형태다 — ①만 보고 "인덱스가 잘 듣는다"고 판단하면 안 된다.

**진짜 전환점은 어디인가** (양쪽을 강제 실행해 실측, 4회 최소값)

| 선택도 | ① 인덱스경로 | ① SeqScan | 실측 승자 | **옵티마이저 선택** |
|---|---|---|---|---|
| 1.68% | 17.5 ms | 60.3 | 인덱스 | Bitmap ✔ |
| 4.98% | 47.8 | 62.9 | 인덱스 | Bitmap ✔ |
| **9.89%** | 82.5 | **59.3** | **SeqScan** | Bitmap ✘ (1.39배 손해) |
| **19.98%** | 137.8 | **67.9** | **SeqScan** | Bitmap ✘ (**2.03배 손해**) |
| 30.06% | 147.0 | 76.0 | SeqScan | Parallel Seq Scan ✔ |

**진짜 전환점은 5~10% 사이인데 옵티마이저는 30% 가 되어서야 바꾼다.**
그 사이 구간에서 최대 **2.03배** 손해를 본다. tpch 판에서 관찰한 것과 같은 종류의 어긋남이지만
(거기서는 15~22% 진짜 / 22~25% 전환 / 13% 손해) **폭이 훨씬 크다.**

반대로 **② 차원 경유에서는 옵티마이저가 정확했다** — 진짜 전환점도 5~10%, 선택도 9.89%부터
Seq 로 넘어간다. 스윕(①)만 보면 "옵티마이저가 인덱스를 오래 붙든다"처럼 보이지만,
강제 실행으로 재보면 **그 고집이 틀렸고**, 오히려 일찍 포기하는 쪽이 옳았다.
§T-0 ③ 이 말하는 "옵티마이저의 선택은 검증 대상"의 실물이다.

## T-3 | 2·6장 조인 방식 — Nested Loops vs Hash vs Merge

책: NL은 소량+인덱스에 로바스트, Hash는 작은 쪽이 메모리에 들어갈 때 최고,
필터 없는 대량 조인은 Hash/Merge가 유리(9장).

### 방법 1 — 스크립트 (권장)

수록 쿼리를 조인 방식만 바꿔 4가지로 강제 실행하고 비교한다:

```bash
./scripts/tpch/join-method-compare.sh q03      # 좁은 필터 3-way 조인
./scripts/tpch/join-method-compare.sh q05      # 6-way 조인
./scripts/tpch/join-method-compare.sh q09      # 인라인뷰 + LIKE
TIMEOUT=5min ./scripts/tpch/join-method-compare.sh q03   # 제한시간 조정 (기본 60s)
```

**반드시 `index` 를 먼저 실행한 상태에서 돌린다.** 인덱스가 없으면 NL 강제가
반복 풀스캔이 되어 사실상 끝나지 않는다(스크립트가 제한시간에 걸러 `중단` 으로 표시한다).
출력에 `>60s 중단` 이 보이면 실패가 아니라 **"이 조인 방식은 이 데이터에서 쓸 수 없다"는 결과**다.

### 방법 2 — psql 에서 직접

`docker exec -it tuninglab-postgres psql -U tuner -d tpch` 로 접속 후,
아래 쿼리를 **각 SET 조합마다 한 번씩** 실행하고 시간과 buffers 를 기록한다:

```sql
\timing on

-- ① 아무것도 안 건드림 (옵티마이저 자율선택)
RESET ALL;
EXPLAIN (ANALYZE, BUFFERS)
SELECT l_orderkey, sum(l_extendedprice * (1 - l_discount)) AS revenue,
       o_orderdate, o_shippriority
FROM customer, orders, lineitem
WHERE c_mktsegment = 'BUILDING'
  AND c_custkey = o_custkey AND l_orderkey = o_orderkey
  AND o_orderdate < date '1995-03-15' AND l_shipdate > date '1995-03-15'
GROUP BY l_orderkey, o_orderdate, o_shippriority
ORDER BY revenue DESC, o_orderdate
LIMIT 10;

-- ② NL 만 남김 → 위 EXPLAIN 문 재실행
SET enable_hashjoin = off; SET enable_mergejoin = off;

-- ③ NL 금지 (Hash/Merge 만) → 위 EXPLAIN 문 재실행
RESET ALL; SET enable_nestloop = off;

RESET ALL;   -- 실험 후 반드시 원복
```

### 참고: 실측 결과 — 같은 데이터, 다른 장비, 정반대 결론

동일한 SF=0.5 데이터(생성기 시드가 고정이라 행 수까지 같다)를 서로 다른 두 장비에서 측정했다.

**q03 (3-way, c_mktsegment 필터 0.20)**

| 강제 조건 | 사용된 조인 | buffers | 장비 A | 장비 B |
|---|---|---|---|---|
| 자율선택 | Nested Loop x2 | 500,750 | **216 ms** | 234 ms |
| NL 금지 | Hash Join x2 | 77,016 | 429 ms | **144 ms** |

**두 장비의 승자가 반대다.** 장비 A에서는 NL이 2배 빠르고, 장비 B에서는 Hash가 1.6배 빠르다.
buffers 수치는 두 장비가 사실상 동일한데(500,750 vs 500,808) 시간만 뒤집혔다.
같은 SQL·같은 데이터·같은 PostgreSQL 버전인데도 **최적 조인 방식이 하드웨어에 따라 달라진다**는 뜻이다.

더 중요한 것은 장비 B에서 **옵티마이저가 틀렸다**는 점이다.
NL을 골랐는데 Hash가 1.6배 빠르니, LIO도 6.5배 많고 시간도 느린 계획을 선택한 것이다.
Tow의 3단계 중 세 번째("어떤 계획이 최선인지 판단")를 **각자의 환경에서 직접** 해야 하는 이유다.

**q05 (6-way) / q09 (인라인뷰+LIKE) — 장비 B 기준**

| 쿼리 | 자율선택 | 최선 | 차이 |
|---|---|---|---|
| q05 | Hash x3 + NL x2, 283,925 buf, 153.7 ms | NL 금지 → Hash x5, 77,504 buf, **113.9 ms** | 옵티마이저 1.35배 손해 |
| q09 | Hash x1 + NL x4, 92,174 buf, 36.9 ms | NL만 → NL x5, 92,249 buf, **36.4 ms** | 옵티마이저 거의 정확 |

**q09가 LIO의 한계를 보여준다.** NL(92,249)과 Hash(86,593)의 buffers는 거의 같은데
시간은 36.4 ms vs 166.3 ms로 **4.6배** 차이가 난다.
`buffers` 는 만진 페이지 수만 세고, **해시 테이블 구축에 들어간 CPU와 메모리는 세지 않기 때문**이다.

정리하면 LIO는 유용한 프록시지만 진실이 아니다. q03·q05에서는 LIO가 승자를 맞혔고
q09에서는 완전히 빗나갔다. Millsap이 "발생 횟수를 세는 것만으로는 소요 시간을 알 수 없다"고
1장에서 못 박은 이유가 이것이다 — **횟수 지표와 시간 지표는 서로를 대체하지 못한다.**

**NL이 무너지는 조건은 "필터가 넓어서"가 아니라 "안쪽에 쓸 인덱스가 없어서"다.**
직접 확인해 본다:

```sql
-- (a) 조인키에 인덱스가 있는 상태: 필터 없는 전체 조인
SELECT count(*) FROM lineitem l, orders o WHERE l.l_orderkey = o.o_orderkey;
--     자율(Hash) 369 ms  vs  NL 강제 637 ms   → 1.7배 차이

-- (b) 조인키 인덱스를 제거하면
DROP INDEX idx_lineitem_partkey;
SELECT count(*) FROM lineitem l, part p WHERE l.l_partkey = p.p_partkey AND p.p_size = 7;
--     자율(Hash) 214 ms  vs  NL 강제 1,216 ms → 5.7배 차이 ← 여기가 '참혹해지는' 지점
CREATE INDEX idx_lineitem_partkey ON lineitem (l_partkey, l_suppkey);   -- 원복
```

Tow가 NL을 "로바스트하다"고 부른 전제에는 **안쪽 테이블에 조인키 인덱스가 있다**는 조건이
깔려 있다. 그 전제가 깨지면 NL은 반복 풀스캔이 되어 최악의 선택이 된다.

`index` 를 실행하지 않은 상태에서 이 스크립트를 돌리면 NL 강제가 끝나지 않는다.
스크립트가 사전 경고를 띄우고 제한시간으로 잘라내지만, 순서를 지키는 편이 낫다.

### 이 실습에서 얻어야 할 결론

1. **조인 방식에 보편적 정답은 없다.** 필터 선택도, 인덱스 유무, 하드웨어가 함께 결정한다.
2. **옵티마이저의 선택은 검증 대상이다.** 위 q03·q05에서 옵티마이저는 1.3~1.6배 손해를 봤다.
3. **하나의 지표(LIO든 시간이든)만 보지 않는다.** q09에서 둘은 정반대를 가리켰다.
4. 그래도 규칙은 유효하다 — 인덱스 없는 NL은 어디서나 재앙이고, 좁은 필터 + 인덱스는 NL의 영역이다.
   책이 준 것은 **출발점이지 결론이 아니며**, 결론은 각자의 환경에서 측정으로 확정한다.

MySQL에서는 `/*+ NO_BNL(t) */`, `/*+ NO_HASH_JOIN(t) */` 힌트로 같은 실험을 한다.

### 같은 실습을 `:tpcds` 로 — 스타 스키마는 NL 쪽으로 크게 기운다

```bash
./scripts/tpcds/join-method-compare.sh q03_brand_by_year
./scripts/tpcds/join-method-compare.sh q19_store_zip
```

> 이 스크립트는 tpch 판과 **같은 파일을 호출한다**(`MODULE=tpcds` 만 바꾼다).
> 로직을 복사해 두면 한쪽만 고쳐지는 일이 반드시 생기기 때문이다.

**실측** (store_sales 200만 행, 4회 최소값)

| 강제 조건 | q03_brand_by_year | q19_store_zip |
|---|---|---|
| 옵티마이저 자율선택 | **2.013 ms** (Hash×1 + NL×1, 2,144 buf) | **30.969 ms** (Hash×2 + NL×3, 23,332 buf) |
| Hash 금지 | 3.064 (Merge×1 + NL×1) | 33.789 (NL×5) |
| NL 만 | 4.361 (NL×2, 8,233 buf) | 31.889 (NL×5) |
| **NL 금지 (순수 Hash)** | **56.204** (40,510 buf) | **110.773** (43,952 buf) |

**① 순수 Hash 는 28배 / 3.6배 느리다.** tpch 에서는 Hash 가 오히려 이기는 장비도 있었는데
(§T-3 의 장비 B), 스타 스키마에서는 방향이 분명하다 — 차원 필터가 팩트 접근을 크게 줄여 주므로
**NL + 인덱스가 읽는 버퍼 자체가 한 자릿수 배 적다**(2,144 vs 40,510).

**② 여기서는 옵티마이저가 옳았다.** 자율선택이 모든 강제 조합보다 빠르거나 같다.
§T-3 tpch 판에서 옵티마이저가 1.3~1.6배 손해를 본 것과 대비된다.
**"옵티마이저를 믿지 마라"가 아니라 "믿을 수 있는지 매번 확인하라"** 가 맞는 교훈이다 —
같은 옵티마이저가 워크로드에 따라 맞기도 하고 틀리기도 한다.

**③ 다만 T-2 와 합쳐 읽어야 한다.** 조인 방식은 옳게 골랐지만(§T-3),
같은 옵티마이저가 **단일 테이블 스캔 방식에서는 2.03배 틀렸다**(위 T-2 tpcds 절).
판단이 옳은 영역과 틀린 영역이 따로 있다는 뜻이다.

## T-4 | 4장 실행계획 제어(1) — 인덱스를 죽이는 습관, 통계와 히스토그램

책: 인덱스 컬럼에 함수/수식/암묵적 형변환을 적용하면 인덱스가 죽는다.

```sql
-- 인덱스 적용 상태의 tpch에서 비교. 두 쿼리는 완전히 같은 113,835 행을 센다.
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM orders
WHERE o_orderdate >= date '1995-01-01' AND o_orderdate < date '1996-01-01';

EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM orders
WHERE extract(year FROM o_orderdate) = 1995;
```

### 스캔 노드 이름을 보지 말고 `Index Cond` 를 봐라

여기서 흔히 오해가 생긴다. 두 번째 쿼리도 계획에 **인덱스 이름이 등장한다**.
그래서 "인덱스를 타고 있으니 괜찮다"고 착각하기 쉽다. 실측 결과를 나란히 놓으면:

**(a) 범위 비교 — 인덱스가 *길잡이* 로 쓰임**

```
Index Only Scan using idx_orders_orderdate on orders  (rows=113835)
  Index Cond: ((o_orderdate >= '1995-01-01') AND (o_orderdate < '1996-01-01'))
  Buffers: shared hit=101 read=1              ← 102 페이지
Execution Time: 14.2 ms                        ← 단일 프로세스
```

**(b) 함수 적용 — 같은 인덱스가 *뒤지는 대상* 으로만 쓰임**

```
Parallel Index Only Scan using idx_orders_orderdate on orders  (rows=28459, loops=4)
  Filter: (EXTRACT(year FROM o_orderdate) = '1995'::numeric)    ← Index Cond 가 아니다
  Rows Removed by Filter: 159041                                ← 워커당 15만 행을 읽고 버림
  Buffers: shared hit=640                                        ← 640 페이지
Execution Time: 83 ms                          ← 워커 4개를 쓰고도 6배 느림
```

**같은 인덱스, 같은 결과 행수인데 버퍼 6.3배, 시간 6배, CPU는 4코어.**
차이는 딱 하나다. (a)는 `Index Cond` 라서 인덱스가 **찾아갈 범위를 결정**하고,
(b)는 `Filter` 라서 **인덱스 전체를 훑으며 한 건씩 함수를 계산해 버린다**.
(b)에서 인덱스는 "테이블보다 좁은 저장소" 역할만 할 뿐 접근 경로가 아니다.

> **판단 기준**: 계획에 인덱스 이름이 보이는지가 아니라,
> 조건이 `Index Cond` 에 올라갔는지 `Filter` 에 남았는지를 본다.
> `Rows Removed by Filter` 가 크면 그 인덱스는 제 역할을 못 하고 있다.

추정 행수도 망가진다. (b)는 워커당 1,210행으로 추정했지만 실제는 28,459행 —
**23배 과소추정**이다. 표현식에는 통계가 없어 옵티마이저가 기본값을 찍기 때문이며,
이 오차는 상위 조인 단계로 그대로 전파된다(§T-1의 연쇄).

**측정 시 주의**: (b)가 `Parallel Seq Scan` 으로 나오는 환경도 있다.
Index Only Scan 은 visibility map 이 설정되어 있어야 유리해지는데,
갓 적재한 테이블은 VACUUM 전이라 그 조건을 못 갖추기 때문이다. 확인·해소 방법:

```sql
SELECT relallvisible, relpages FROM pg_class WHERE relname = 'orders';
VACUUM ANALYZE orders;   -- 이후 relallvisible 이 relpages 에 근접하고 계획이 바뀐다
```

실측으로 재현되는 차이다 — VACUUM 전 Parallel Seq Scan(13,656 버퍼, 121 ms),
VACUUM 후 Parallel Index Only Scan(640 버퍼, 83 ms).
**적재 직후와 운영 중인 테이블은 같은 쿼리에도 다른 계획을 낸다**는 것을 기억해 둘 것.

다만 위 예제는 선택도가 15%라 §T-2 기준으로도 인덱스가 불리한 구간이다.
**인덱스 무력화만 순수하게 보려면 선택도가 아주 높은(=행이 1건인) 조건으로 실험해야 한다.**
Tow 4장이 든 예제 그대로:

```sql
-- ① 정상: PK 인덱스 사용
EXPLAIN SELECT * FROM customer WHERE c_custkey = 12345;

-- ② 수식으로 무력화 (책이 "인덱스를 끄고 싶을 때 쓰라"고 소개한 바로 그 기법)
EXPLAIN SELECT * FROM customer WHERE c_custkey + 0 = 12345;

-- ③ 암묵적 형변환으로 무력화
EXPLAIN SELECT * FROM customer WHERE c_custkey::text = '12345';

-- ④ 표현식 인덱스로 ③ 되살리기
CREATE INDEX idx_cust_key_text ON customer ((c_custkey::text));
ANALYZE customer;
EXPLAIN SELECT * FROM customer WHERE c_custkey::text = '12345';
DROP INDEX idx_cust_key_text;
```

실측 결과:

| | 계획 | 추정 행수 |
|---|---|---|
| ① `c_custkey = 12345` | Index Scan using customer_pkey | 1 |
| ② `c_custkey + 0 = 12345` | **Seq Scan** | 375 |
| ③ `c_custkey::text = '12345'` | **Seq Scan** | 375 |
| ④ ③ + 표현식 인덱스 | Index Scan using idx_cust_key_text | 1 |

②③의 추정 행수 375에 주목한다. 실제로는 1건인데 375건으로 본다.
**표현식에는 통계가 없어서 옵티마이저가 기본 선택도를 추측**하기 때문이다.
인덱스를 못 쓰는 손해에 더해, 이 375라는 엉터리 추정이 상위 조인 단계로 전파되어
조인 방식·순서까지 망가뜨린다. §T-1에서 본 연쇄가 여기서도 시작된다.

### 통계 정밀도 — 책의 DBMS_STATS/히스토그램에 대응

**단일 컬럼 statistics_target** 은 데이터가 **치우쳐 있을 때만** 의미가 있다.
TPC-H 날짜처럼 균일한 분포에서는 거의 차이가 없다는 것을 먼저 확인해 둔다:

```sql
-- l_shipdate 1주 범위. target 을 바꿔가며 추정/실제 오차를 비교
ALTER TABLE lineitem ALTER COLUMN l_shipdate SET STATISTICS 1;    ANALYZE lineitem;
EXPLAIN (ANALYZE) SELECT count(*) FROM lineitem
  WHERE l_shipdate BETWEEN date '1994-02-01' AND date '1994-02-07';
-- target 을 10, 100, 1000 으로 바꿔 반복
ALTER TABLE lineitem ALTER COLUMN l_shipdate SET STATISTICS -1;   ANALYZE lineitem;  -- 기본값 복귀
```

실측(SF=0.5): target 1→1000 에서 추정 8,319 / 8,696 / 10,204 / 8,280 (실제 9,015).
**오차가 줄지 않는다.** 균일 분포에서는 히스토그램을 아무리 정밀하게 만들어도 얻을 게 없다.
"통계를 정밀하게 = 항상 좋다"는 통념이 틀렸음을 보여주는 지점이다.

**진짜 오차는 다중 컬럼 상관관계에서 나온다.** 옵티마이저는 조건들이 서로 독립이라고
가정하므로, 상관된 컬럼에 조건을 겹치면 선택도를 곱해버려 크게 빗나간다:

```sql
-- l_shipdate 와 l_receiptdate 는 강하게 상관됨 (receipt = ship + 며칠)
EXPLAIN (ANALYZE) SELECT count(*) FROM lineitem
WHERE l_shipdate    BETWEEN date '1994-01-01' AND date '1994-03-31'
  AND l_receiptdate BETWEEN date '1994-01-01' AND date '1994-06-30';
```

실측: 추정 2,278행 vs 실제 22,837행(워커당) → **10배 과소추정**.
§T-1에서 본 것처럼 이런 과소추정은 잘못된 조인 방식 선택과 불필요한 JIT으로 이어진다.

PostgreSQL의 대응 수단은 확장 통계다(Oracle의 다중 컬럼 히스토그램에 대응):

```sql
CREATE STATISTICS st_li_dates (mcv, dependencies)
  ON l_shipdate, l_receiptdate FROM lineitem;
ANALYZE lineitem;
-- 위 쿼리 재실행
DROP STATISTICS st_li_dates;
```

단, 실측에서는 추정이 2,278 → 2,122 로 거의 개선되지 않았다.
`mcv`/`dependencies` 는 **등치 조건**에 효과적이고 **범위 조건**에는 잘 듣지 않기 때문이다.
확장 통계가 만능이 아니라는 것까지 확인하는 것이 이 실습의 결론이다 —
범위 조건의 상관관계는 지금도 옵티마이저의 약점으로 남아 있고,
그래서 §T-0 ①의 "추정 vs 실제 배율을 항상 확인하라"가 필요하다.

MySQL: `ANALYZE TABLE lineitem UPDATE HISTOGRAM ON l_shipdate WITH 100 BUCKETS;`

### 같은 실습을 `:tpcds` 로 — 그리고 tpch 에서 못 보여준 실험 하나

```bash
./scripts/tpcds/t4-index-defeat.sh
```

tpch 판은 문서 안의 SQL 로만 되어 있다. tpcds 판은 스크립트로 만들었다 —
특히 ④는 **tpch 에서는 보여줄 수 없었던 실험**이라 재현 가능한 형태가 필요했다.

**① 함수로 감싸면 Index Cond 가 Filter 로 내려앉는다** (같은 행을 세는 두 쿼리)

| 조건 | 노드 | 조건 위치 | min |
|---|---|---|---|
| `ss_sold_date_sk >= B AND < B+30` | Index Only Scan | **Index Cond** | **4.06 ms** |
| `ss_sold_date_sk - B BETWEEN 0 AND 29` | Parallel Index Only Scan | **Filter** | 37.54 ms |

인덱스 이름이 계획에 보여도 소용없다 — **9.2배** 차이다.

**② 형변환 무력화와 표현식 인덱스** (`item`, 2만 행)

| | 노드 | min |
|---|---|---|
| 정상 (PK) | Index Scan | 0.054 ms |
| `i_item_sk + 0 = 1000` | Seq Scan | 2.961 ms |
| `i_item_sk::text = '1000'` | Seq Scan | 3.475 ms |
| 위 + 표현식 인덱스 | Index Scan | **0.063 ms** |

**③ VACUUM 이 Index Only Scan 을 연다** — VACUUM 전 Bitmap Heap Scan 15.79ms
(`relallvisible 0`) → VACUUM 후 Index Only Scan 4.31ms (`8,896 중 8,850`). **3.7배.**

**④ `statistics_target` — 통념이 반쯤 틀렸다**

`ss_coupon_amt` 는 `0.00` 이 **90.04%**, 나머지 값은 21행 이하인 진짜 편중 컬럼이다.
tpch 는 균일 분포라 이 실험이 아무 차이도 못 냈고(§5 정정 3번), 여기서 처음으로 재봤다.

| target | 최빈값 `0.00` (실제 1,800,830) | 희소값 `3.84` (실제 21) | MCV/히스토그램 |
|---|---|---|---|
| 1 | 추정 1,802,920 (**1.00배**) | 추정 63 (3.00배) | 1 / 2 |
| 10 | 1,802,790 (1.00배) | 63 (3.00배) | 1 / 11 |
| 100 | 1,801,008 (1.00배) | 62 (2.95배) | 1 / 101 |
| 1000 | 1,802,473 (1.00배) | 8 (2.62배) | 6 / 1001 |

**최빈값은 `target=1` 에서도 정확하다.** MCV 목록은 target=1 이어도 한 칸은 담으므로,
90% 를 차지하는 값은 그 한 칸에 들어간다. 반대로 희소값은 target 을 1000 으로 올려도
오차가 남는다 — 21행/200만 = 0.001% 는 **어느 target 에서도 MCV 에 못 들어가기** 때문이다.

> **§5 정정 3번을 다듬어야 한다.** "치우친 데이터에서만 의미가 있다"는 절반만 맞다.
> 지배적 최빈값은 공짜로 잡히므로 target 을 올릴 이유가 없고, target 이 실제로 하는 일은
> **MCV 목록을 늘려 중간 빈도 값들을 담는 것**이다.
> 진짜 변수는 "데이터가 치우쳤는가"가 아니라 **"조회하는 값이 MCV 에 있는가"** 다.

**⑤ 스타 스키마 고유 — 대리키에 형변환을 걸면 조인이 죽는다**

| 조인 조건 | 조인 방식 | min |
|---|---|---|
| `s.ss_item_sk = i.i_item_sk` | Nested Loop | **0.767 ms** |
| `s.ss_item_sk::text = i.i_item_sk::text` | Hash Join | **128.455 ms** |

**167배.** 단일 테이블 필터에서 형변환이 인덱스를 죽이는 것(②)보다 훨씬 파괴적이다 —
스타 스키마는 조인이 전부이므로, 여기서 죽으면 §T-3 에서 확인한 NL 의 이점이 통째로 사라진다.

> 이 스크립트를 처음 만들었을 때 ⑤를 **단발 측정**해서 "형변환 쪽이 더 빠르다"는
> 정반대 결론을 적을 뻔했다(§T-0 ② 위반). 4회 최소값으로 바꾸니 방향이 뒤집혔다.
> 스크립트에 `best_ms()` 를 넣어 모든 측정이 반복되도록 했다.

## T-5 | 4·6장 실행계획 제어(2) — 조인 순서 강제와 드라이빙 테이블

책의 휴리스틱: **가장 좋은 필터 비율을 가진 테이블을 드라이빙으로**, PK 방향(하향) 조인 우선.

### 1단계 — 필터 비율을 직접 계산한다

책의 방법대로 각 테이블의 "조건을 통과하는 행의 비율"을 먼저 구한다. 추측하지 말고 세어본다:

```sql
SELECT 'customer' AS t,
       count(*) FILTER (WHERE c_mktsegment = 'BUILDING')::numeric / count(*) AS filter_ratio
FROM customer
UNION ALL
SELECT 'orders',
       count(*) FILTER (WHERE o_orderdate < date '1995-03-15')::numeric / count(*)
FROM orders
UNION ALL
SELECT 'lineitem',
       count(*) FILTER (WHERE l_shipdate > date '1995-03-15')::numeric / count(*)
FROM lineitem;
```

실측(SF=0.5): customer **0.202**, orders 0.487, lineitem 0.538.
→ 책의 규칙 1("가장 0에 가까운 필터 비율을 드라이빙으로")에 따르면 **customer가 드라이빙**이어야 한다.

### 2단계 — 조인 순서를 강제해 예측을 검증한다

**주의**: `join_collapse_limit = 1` 은 **명시적 `JOIN ... ON` 구문에만** 적용된다.
`FROM a, b, c` 처럼 콤마로 나열하면 이 설정과 무관하게 옵티마이저가 자유롭게 재배열하므로
순서 강제가 되지 않는다(실측으로 확인: 콤마 버전은 세 경우 모두 같은 시간이 나온다).
반드시 아래처럼 `JOIN ... ON` 으로 바꿔 써야 한다.

```sql
\timing on
SET join_collapse_limit = 1;

-- (a) customer 드라이빙 — 책의 휴리스틱이 고른 순서
EXPLAIN (ANALYZE, BUFFERS)
SELECT l_orderkey, sum(l_extendedprice * (1 - l_discount)) AS revenue,
       o_orderdate, o_shippriority
FROM customer
JOIN orders   ON c_custkey  = o_custkey
JOIN lineitem ON l_orderkey = o_orderkey
WHERE c_mktsegment = 'BUILDING'
  AND o_orderdate < date '1995-03-15' AND l_shipdate > date '1995-03-15'
GROUP BY l_orderkey, o_orderdate, o_shippriority
ORDER BY revenue DESC, o_orderdate LIMIT 10;

-- (b) lineitem 드라이빙 — 필터 비율이 가장 나쁜 테이블부터 (나쁜 순서)
EXPLAIN (ANALYZE, BUFFERS)
SELECT l_orderkey, sum(l_extendedprice * (1 - l_discount)) AS revenue,
       o_orderdate, o_shippriority
FROM lineitem
JOIN orders   ON l_orderkey = o_orderkey
JOIN customer ON c_custkey  = o_custkey
WHERE c_mktsegment = 'BUILDING'
  AND o_orderdate < date '1995-03-15' AND l_shipdate > date '1995-03-15'
GROUP BY l_orderkey, o_orderdate, o_shippriority
ORDER BY revenue DESC, o_orderdate LIMIT 10;

RESET join_collapse_limit;   -- 원복 후 (c) 옵티마이저 자율선택으로 (a) 를 재실행
```

|---|---|---|---|---|---|---|
| (a) customer 먼저 (휴리스틱) | Nested Loop x2 | 500,744 | 1 | 75,919 | **232.8 ms** | 261.5 ms |
| (b) lineitem 먼저 (나쁜 순서) | Parallel Hash Join x2 | 77,010 | 4 | 117,327 | 442.6 ms | **216.7 ms** |
| (c) 옵티마이저 자율선택 | (a)와 완전히 동일 | 500,744 | 1 | 75,919 | 240.4 ms | 247.5 ms |

**두 장비 모두 (c) = (a) 다.** 옵티마이저는 어디서든 필터 비율 0.202인 customer 를
드라이빙으로 골랐다. 책의 휴리스틱과 옵티마이저의 판단이 일치한다는 점은 확인된 셈이다.

그런데 **장비 B에서는 그 선택이 셋 중 가장 느렸다.**
"나쁜 순서"라고 이름 붙인 (b)가 오히려 1.21배 빠르다.
비용 추정은 (a) 75,919 vs (b) 117,327 로 (a)를 1.55배 싸다고 봤는데 실측은 반대다 —
**비용 모델이 순위를 뒤집었다.**

원인은 두 가지다. 첫째, (b)는 워커 4개를 띄우는데 (a)는 1개뿐이다.
둘째, (b)의 buffers 가 6.5배 적다. (a)의 버퍼 500,744 중
**301,369개(60%)가 lineitem 인덱스 probe 한 노드**에서 나온다:

```
->  Index Scan using lineitem_pkey on lineitem  (rows=0, loops=74024)
      Index Cond: (l_orderkey = orders.o_orderkey)
      Filter: (l_shipdate > '1995-03-15'::date)
      Rows Removed by Filter: 4          ← 매번 4건 꺼내서 전부 버림

```

74,024번 probe 해서 lineitem 을 약 29.6만 건 힙에서 꺼낸 뒤 shipdate 조건으로 버리고
15,164건만 남긴다. §T-8의 결합 인덱스가 겨냥하는 지점이 정확히 여기다.

### 2003년 휴리스틱이 지금도 맞는가

Tow의 규칙은 "**접근하는 행 수를 최소화하라**"이고, 그 밑에는
"행 하나를 만지는 비용은 어디서나 비슷하다"는 가정이 깔려 있다.
단일 코어 + 느린 디스크 시대에는 타당했다.

지금은 **순차 스캔 + 병렬 처리 + 큰 메모리** 조합의 행당 비용이 랜덤 인덱스 probe보다 훨씬 싸다.
그래서 장비 B에서는 "300만 행을 5개 프로세스로 훑기"가 "74,024번 정밀하게 찾아가기"를 이겼다.

규칙이 폐기된 것은 아니다. 필터 비율로 드라이빙 후보를 좁히는 사고법은 여전히 유효하고
옵티마이저도 같은 결론에 도달했다. 다만 **그 결론이 최선인지는 측정으로 확정해야 한다.**
Tow가 3단계 중 세 번째("어떤 계획이 최선인지 판단")를 가장 중요하다고 한 이유다.

MySQL: `SELECT /*+ JOIN_ORDER(customer, orders, lineitem) */ ...` 또는 `SELECT STRAIGHT_JOIN ...`
(MySQL은 FROM 절 순서를 STRAIGHT_JOIN 으로 강제한다)

### 같은 실습을 `:tpcds` 로 — 스타 스키마에서 드라이빙 테이블 고르기

**1단계 — 필터 비율** (`q03_brand_by_year`, store_sales 200만 행)

| 테이블 | 필터 | 통과 / 전체 | 필터 비율 |
|---|---|---|---|
| `item` | `i_manufact_id = 128` | 20 / 20,000 | **0.10%** ← 가장 선택적 |
| `date_dim` | `d_moy = 11` | 150 / 1,826 | 8.21% |
| `store_sales` | (없음) | 2,000,000 / 2,000,000 | 100% |

Tow 의 휴리스틱은 **가장 좋은 필터부터** 드라이빙하라고 한다 → `item` 예측.

**2단계 — 순서를 강제해 검증** (`join_collapse_limit=1` + 명시적 `JOIN ... ON`, 4회 최소값)

| FROM 절 순서 | min | buffers | 첫 조인 |
|---|---|---|---|
| `item` → store_sales → date_dim | **2.143 ms** | 2,144 | Nested Loop |
| **`date_dim` → store_sales → item** | **60.953 ms** | 40,510 | Hash Join |
| `store_sales` → item → date_dim | 2.043 ms | 2,144 | Nested Loop |
| (옵티마이저 자율선택) | 2.222 ms | — | — |

**휴리스틱이 맞았다.** 필터 비율 8.21% 인 `date_dim` 부터 몰면 **28배** 손해다 —
약한 필터로 시작하면 팩트 테이블 전체를 해시해야 하기 때문이다(buffers 2,144 → 40,510).

> **주의 — `store_sales` 를 먼저 써도 빠르다.** `join_collapse_limit=1` 은 **조인 순서**를 고정할 뿐,
> 각 조인에서 어느 쪽을 inner/outer 로 둘지는 여전히 옵티마이저가 정한다.
> 그래서 "FROM 절 첫 테이블 = 드라이빙 테이블"이 아니다.
> 실제로 무엇이 드라이빙인지는 EXPLAIN 의 **가장 안쪽 노드**를 봐야 안다
> (여기서는 세 경우 모두 `item` 의 인덱스에서 출발한다).
> §5 정정 목록 2번(`join_collapse_limit` 은 콤마 조인에 안 먹는다)과 같은 계열의 함정이다.

## T-7 | 7장 복잡한 쿼리 — 아우터 조인의 필터 위치, NOT IN vs NOT EXISTS, UNION 함정

tpch q13이 교과서 예제다. `o_comment NOT LIKE ...` 필터가 **ON 절**에 있다:

```sql
-- (a) 원본: 필터가 ON 절 → 주문 없는 고객도 보존 (정답)
SELECT c_custkey, count(o_orderkey) FROM customer
LEFT JOIN orders ON c_custkey = o_custkey AND o_comment NOT LIKE '%special%requests%'
GROUP BY c_custkey;
-- (b) 필터를 WHERE 로 이동 → 아우터 조인이 사실상 이너 조인으로 변질 (행수 비교!)
SELECT c_custkey, count(o_orderkey) FROM customer
LEFT JOIN orders ON c_custkey = o_custkey
WHERE o_comment NOT LIKE '%special%requests%'
GROUP BY c_custkey;
```

NOT IN의 NULL 함정(책 7장):

```sql
SELECT count(*) FROM customer WHERE c_custkey NOT IN (SELECT o_custkey FROM orders);
SELECT count(*) FROM customer c WHERE NOT EXISTS
  (SELECT 1 FROM orders o WHERE o.o_custkey = c.c_custkey);
-- 계획(Anti Join 여부)과 시간 비교. o_custkey가 nullable이라면 결과 자체가 달라진다
```

UNION vs UNION ALL(Millsap 12장 사례4와 동일 주제 — 6.5시간→10.9초):

```sql
EXPLAIN ANALYZE SELECT l_orderkey FROM lineitem WHERE l_shipmode='AIR'
UNION     SELECT l_orderkey FROM lineitem WHERE l_shipmode='RAIL';   -- 거대한 중복제거 정렬
EXPLAIN ANALYZE SELECT l_orderkey FROM lineitem WHERE l_shipmode='AIR'
UNION ALL SELECT l_orderkey FROM lineitem WHERE l_shipmode='RAIL';   -- 정렬 없음
```

## T-8 | 9장 조인키+필터 결합 인덱스 (Merged Join and Filter Index)

책: 외래키와 필터 컬럼의 결합 인덱스는 테이블 접근 전에 인덱스 수준에서 행을 버린다.

§T-1에서 본 q03 계획을 다시 보면, lineitem 접근이 전체 LIO의 60%를 쓰고 있었다.
`Index Scan using lineitem_pkey` 에 `Rows Removed by Filter: 4` 가 붙어 있는데,
조인키로 찾은 lineitem 을 힙에서 꺼낸 뒤 `l_shipdate` 조건으로 대부분 버린다는 뜻이다.
조인키 + 필터를 한 인덱스에 합치면 힙에 가기 전에 버릴 수 있다.

### 방법 1 — 스크립트로 한 번에 (권장)


네 조건을 **한 라운드 안에서 교차 측정**해 시간을 비교한다.
(조건별로 몰아서 재면 시간대 드리프트를 조건 차이로 착각한다 — §T-0 원칙 6)

### 참고: 실측 결과 (SF=0.5, PostgreSQL 16.13, 6라운드 교차 측정)

§T-5에서 지목한 지점 — lineitem probe 한 노드가 전체 LIO의 60%(301,369 buffers) — 를
결합 인덱스로 실제로 공략한 결과다.

**계획이 바뀐 자리 (이 실습의 핵심)**

```
[전] ->  Index Scan using lineitem_pkey on lineitem (rows=0, loops=74024)
           Index Cond: (l_orderkey = orders.o_orderkey)
           Filter: (l_shipdate > '1995-03-15'::date)     ← 힙에서 꺼낸 뒤 버림
           Rows Removed by Filter: 4
           Buffers: shared hit=301369

[후] ->  Index Scan using idx_li_orderkey_shipdate on lineitem (rows=0, loops=74024)
           Index Cond: ((l_orderkey = orders.o_orderkey)
                        AND (l_shipdate > '1995-03-15'::date))   ← 인덱스에서 걸러냄
           Buffers: shared hit=228320
```

`l_shipdate` 가 `Filter` → `Index Cond` 로 올라갔고 **`Rows Removed by Filter` 행 자체가 사라졌다.**
책 9장이 말한 "테이블 접근 전에 인덱스 수준에서 버린다"가 그대로 재현된다.

**측정값** (라운드마다 인덱스 상태를 바꿔가며 6회 교차 측정, 워밍업 후)

| 조건 | lineitem probe buffers | 총 buffers | min | median |
|---|---|---|---|---|
| ① NL, 결합 인덱스 없음 | 301,369 | 500,750 | 407.2 ms | 433.3 ms |
| ② NL + 결합 인덱스 | **228,320** | 427,701 | **313.0 ms** | **330.6 ms** |
| ③ NL + 커버링 인덱스 | 224,993 | 424,389 | 292.8 ms | 333.7 ms |
| ④ Hash (인덱스와 무관) | — | 77,016 | 321.9 ms | 360.6 ms |

③은 `INCLUDE (l_extendedprice, l_discount)` 를 더해 `Index Only Scan`(`Heap Fetches: 0`)이 된 것.

**결론 1 — NL 이 Hash 를 다시 이겼다.**
①에서 NL 은 Hash 보다 느렸는데(407 vs 322), ②에서 역전한다(313 vs 322).
§T-3·§T-5에서 "이 장비에서는 Hash 가 낫다"고 판정났던 q03 이,
**인덱스 하나로 판정이 뒤집힌 것**이다. 조인 방식의 우열은 고정된 성질이 아니라
**어떤 접근 경로를 쓸 수 있느냐의 함수**임을 보여준다.

**결론 2 — 절감분은 전부 힙 접근에서 나왔고, 거기서 멈춘다.**
줄어든 73,049 buffers 는 전부 lineitem probe 노드 몫이다(전체 감소분과 정확히 일치).
그런데 ③의 커버링 인덱스로 힙 접근을 **0으로** 만들어도 3,327 buffers 밖에 더 줄지 않는다.
남은 224,993 은 **74,024번의 B-tree 하강 그 자체**이고, 이것이 NL 의 하한이다.

> 74,024 probe × 약 3 buffers(루트→브랜치→리프) ≈ 222,000.
> 실측 224,993 이 이 값에 거의 정확히 수렴한다.

②→③의 이득(min 20ms)에 비해 인덱스는 90MB → 135MB 로 1.5배 커진다.
**커버링까지 갈 필요는 없다** — ②에서 멈추는 것이 옳은 판단이다.

**결론 3 — buffers 최소가 시간 최소가 아니다(§T-3의 재확인).**
Hash 는 buffers 가 77,016 으로 ②의 5.6배나 적은데도 더 느리다.
순차 스캔 61,235 페이지를 읽고 해시 테이블을 짓는 CPU 비용을 `buffers` 가 세지 않기 때문이다.

**측정 위생 메모.** 이 절의 수치는 처음에 잘못 냈다가 고친 것이다.
조건별로 나눠서 batch 측정했을 때는 "커버링+NL 284ms vs Hash 310ms"로 나와
③이 명확히 이긴 것처럼 보였는데, **같은 라운드 안에서 교차 측정하니 ②③④가 훨씬 가까웠다.**
컨테이너 환경의 시간대 드리프트가 조건 간 차이(±10%)보다 컸던 것이다.
§T-0 이 말한 "단발 측정을 성능 지표로 쓰지 않는다"가 조건 비교에도 그대로 적용된다 —
**비교할 조건들은 반드시 교차(interleave)해서 재야 한다.**

### 이어서: orders probe 에도 같은 기법을 적용한다

②를 적용하고 나면 병목이 옮겨간다. lineitem probe 가 228,320 으로 줄면서
이번엔 **orders probe 가 197,553 buffers 로 전체의 46%** 를 차지한다.
노드를 보면 §T-8 도입부와 똑같은 모양이다.

```
->  Index Scan using idx_orders_custkey on orders (rows=5, loops=15183)
      Index Cond: (o_custkey = customer.c_custkey)
      Filter: (o_orderdate < '1995-03-15'::date)    ← 또 힙에서 꺼낸 뒤 버림
      Rows Removed by Filter: 5                      ← 10건 꺼내 5건 버림 (낭비율 50%)
      Buffers: shared hit=197553
```

probe 당 약 13 buffers(= 3 하강 + 10 힙)로, lineitem(약 3)보다 **힙 낭비 비중이 훨씬 크다.**
같은 처방을 적용한다.

```sql
CREATE INDEX idx_ord_custkey_orderdate ON orders (o_custkey, o_orderdate);
ANALYZE orders;
```

**그런데 여기서 실습의 핵심이 나온다 — 만들어도 옵티마이저가 쓰지 않는다.**

```
->  Index Scan using idx_orders_custkey on orders   ← 여전히 좁은 인덱스
      Filter: (o_orderdate < '1995-03-15'::date)     ← Filter 그대로
```

추정 비용을 보면 이유가 보인다. 둘의 차이가 **1.8% 밖에 안 된다.**

| 인덱스 | 크기 | 추정 비용 |
|---|---|---|
| `idx_orders_custkey (o_custkey)` | 6,816 kB | `cost=0.42..1.70` ← 선택됨 |
| `idx_ord_custkey_orderdate (o_custkey, o_orderdate)` | 23 MB | `cost=0.42..1.73` |

`o_orderdate < '1995-03-15'` 의 선택도가 **48.7%** (거의 절반)라 필터로서 약하고,
`random_page_cost=1.1` 에서는 힙 접근이 거의 공짜로 계상되어 **절약분이 비용 모델에 잡히지 않는다.**
반면 넓은 인덱스의 큰 크기는 그대로 비용에 반영된다. 그래서 근소한 차이로 좁은 쪽이 이긴다.

`random_page_cost` 를 올려도 해결되지 않는다 — 1.5 이상에서는 결합 인덱스로 갈아타는 게 아니라
**NL 자체를 포기하고 Parallel Hash Join + Seq Scan 으로 계획이 통째로 바뀐다.**

```sql
-- 좁은 인덱스는 결합 인덱스의 선행 부분집합이므로 중복이다. 지워야 쓰인다.
DROP INDEX idx_orders_custkey;
```

```
->  Index Scan using idx_ord_custkey_orderdate on orders (rows=5, loops=15183)
      Index Cond: ((o_custkey = customer.c_custkey)
                   AND (o_orderdate < '1995-03-15'::date))
      Buffers: shared hit=119766        ← 197,553 → 119,766 (-39.4%)
```

**측정값** (8라운드 교차, 상태당 2회씩 n=16)

| 단계 | orders probe | lineitem probe | 총 buffers | min | median |
|---|---|---|---|---|---|
| ① 원본(인덱스 세트만) | 197,553 | 301,369 | 500,750 | 400.3 ms | 418.1 ms |
| ② + lineitem 결합 | 197,553 | 228,320 | 427,701 | 287.8 ms | 332.1 ms |
| ③ + orders 결합(좁은 것 제거) | **119,766** | 228,320 | **349,914** | **267.5 ms** | **291.4 ms** |

①→③ 으로 총 buffers 30.1% 감소, median 30.3% 단축.

**결론 4 — 인덱스를 만드는 것과 옵티마이저가 그것을 쓰는 것은 별개다.**
`(A)` 와 `(A, B)` 가 함께 있으면 PostgreSQL 은 **더 작다는 이유로 좁은 쪽을 계속 고른다.**
`(A)` 는 `(A, B)` 의 선행 부분집합이라 기능적으로 중복인데도 그렇다.
넓은 인덱스를 만들었다면 **좁은 쪽을 반드시 지워야** 한다 — 안 그러면
디스크만 더 쓰고 계획은 그대로인, 최악의 조합이 된다.

> 좁은 인덱스를 지워도 안전한가? `(o_custkey, o_orderdate)` 는 `(o_custkey)` 로 하는
> 모든 검색을 선행 컬럼 검색으로 그대로 처리한다(§T-2의 B-tree 왼쪽 접두 규칙).
> q05·q13·q18 의 `o_custkey` 조인도 영향받지 않는다.

**결론 5 — 이번엔 비용 모델이 절약분을 과소평가했다.**
§T-3에서는 `buffers` 만 보고 판단하면 틀린다고 했는데(Hash 가 buffers 는 적지만 느림),
여기서는 정반대다. 15,183 loops × 5건씩 총 76,000회의 힙 접근을 아끼는데
비용 모델은 이를 0.03 으로 계상했다. **`buffers` 도 비용 추정도 단독으로는 신뢰할 수 없고,
실측만이 판정한다** — §T-0이 문서 맨 앞에 있는 이유다.

**DML 비용 확인 (인덱스는 공짜가 아니다).** pgbench-lab 에서 인덱스를 늘려가며 TPS 하락을 잰다:

### 참고: 실측 결과 (SF=0.5, PostgreSQL 16.13) — §T-8 이 부딪힌 하한을 넘는다

§T-8 끝에서 lineitem probe 228,320 buffers 가 **인덱스로는 더 줄일 수 없는 하한**임을 확인했다
(74,024회 B-tree 하강 자체). 여기서부터는 접근 경로가 아니라 **쿼리와 모델을 바꿔야** 한다.

**먼저 문제를 정량화한다 — q03 의 필터는 3개 테이블에 흩어져 있다**

| 필터 | 위치 | 선택도 |
|---|---|---|
| `c_mktsegment = 'BUILDING'` | customer | 0.2024 |
| `o_orderdate < '1995-03-15'` | orders | 0.4866 |
| `l_shipdate > '1995-03-15'` | lineitem | 0.5384 |

독립을 가정해 곱하면 0.0499 → 149,646 행이 나와야 하는데 **실제 결과는 15,164 행**이다.
`o_orderdate` 와 `l_shipdate` 가 상관되어 있어(주문한 뒤에 배송한다) 실제 결합 선택도가
**10배 더 강하다**. Tow 2장의 *filter redundancy* 가 그대로 나타난 사례다.

즉 이 쿼리는 최종적으로 lineitem 300만 행 중 **0.505% 만** 필요로 하는데,
필터가 흩어져 있어서 그 조합에 도달하려면 이미 큰 테이블을 다 헤집은 뒤여야 한다.

**해법 A — 필터를 한 테이블로 끌어올린다 (책 10장의 처방)**

```sql
-- customer/orders 의 필터 컬럼을 lineitem 쪽으로 상속시킨다
CREATE TABLE lineitem_denorm AS
SELECT l.l_orderkey, l.l_extendedprice, l.l_discount, l.l_shipdate,
       c.c_mktsegment, o.o_orderdate, o.o_shippriority
FROM lineitem l JOIN orders o ON l.l_orderkey=o.o_orderkey
                JOIN customer c ON o.o_custkey=c.c_custkey;

CREATE INDEX idx_ld_filters ON lineitem_denorm (c_mktsegment, o_orderdate, l_shipdate);
```

세 필터가 **하나의 `Index Cond` 로 합쳐진다.** 조인은 0개가 된다.

```
->  Bitmap Heap Scan on lineitem_denorm (rows=15164)
      ->  Bitmap Index Scan on idx_ld_filters
            Index Cond: ((c_mktsegment = 'BUILDING') AND (o_orderdate < '1995-03-15')
                         AND (l_shipdate > '1995-03-15'))
            Buffers: shared hit=867        ← 인덱스 867 블록으로 15,164 행을 특정
```

**해법 B — 결과 자체를 사전 집계한다 (Materialized View)**

```sql
CREATE MATERIALIZED VIEW mv_q03 AS <q03 의 GROUP BY 까지>;
CREATE INDEX ON mv_q03 (revenue DESC, o_orderdate);
```

**측정값** (10라운드 교차, 세 방식 모두 결과 해시가 동일함을 먼저 검증했다)

| 방식 | 조인 | buffers | min | median |
|---|---|---|---|---|
| ① 원본 (인덱스 세트만) | 3 | 500,750 | 400.3 ms | 418.1 ms |
| ③ §T-8 최선 (결합 인덱스 2개) | 3 | 349,914 | 310.3 ms | 324.7 ms |
| ④ 반정규화 (필터 끌어올림) | **0** | **6,169** | **51.0 ms** | **53.4 ms** |
| ⑤ 사전 집계 MV | 0 | **12** | **0.1 ms** | **0.1 ms** |

③→④ 만으로 buffers 57배, 시간 6배가 줄어든다.
**§T-8 에서 인덱스를 아무리 다듬어도 못 넘던 벽을, 모델을 바꾸니 한 번에 넘는다.**

**그런데 공짜가 아니다 — 대가를 같이 잰다**

| 항목 | ④ 반정규화 | ⑤ 사전 집계 MV |
|---|---|---|
| 저장 | 테이블 220MB + 인덱스 69MB = **289MB** | 512 kB |
| (원본에 컬럼 3개만 추가한다면) | 행당 22 B × 300만 = **63MB** | — |
| 생성/갱신 비용 | — | `REFRESH` **343 ms** |
| 전파 팬아웃 | 고객 1건 변경 → **40행** 갱신 | 전체 재계산 |
| 갱신 실측 | 28.5 ms → **404.8 ms (14배)** | 343 ms |
| 적용 범위 | 이 필터 **조합**이면 재사용 가능 | **이 쿼리·이 파라미터 전용** |

⑤가 0.1ms 인 것은 사실상 답을 미리 적어둔 것이기 때문이다. 대가는 **범용성**이다 —
MV 정의에 `o_orderdate < '1995-03-15'` 가 박혀 있어서 **날짜나 세그먼트가 바뀌면 쓸 수 없다.**
조회 조건이 자유로운 화면이라면 조합마다 MV 를 만들어야 하므로 성립하지 않는다.

④의 대가는 **쓰기다.** 고객 한 명의 등급을 바꾸는 데 정규화 상태에서는 1행 28.5ms 인데,
반정규화 상태에서는 40행을 찾아 고쳐야 해서 404.8ms 가 든다 — **14배**.
Tow 가 "완벽한 트리거로 동기화하면 기능적으로는 안전하지만 공짜가 아니다"라고 한 지점이다.

**결론 6 — 인덱스가 못 넘는 벽은 모델을 바꿔야 넘는다.**
§T-8 의 교훈이 "접근 경로를 최적화하라"였다면, §T-9 의 교훈은
**"접근 경로로 못 가는 지점이 있고, 거기서는 문제의 형태 자체를 바꿔야 한다"** 이다.
다만 그 순서를 지켜야 한다 — 인덱스로 되는 것을 반정규화로 풀면
**쓰기 비용 14배를 지불하고 몇 밀리초를 사는** 나쁜 거래가 된다.
이것이 Tow 가 반정규화를 책의 맨 마지막에, "다른 방법이 없을 때만"이라고 못박은 이유다.

**반복 쿼리 통합 실측**

| 방식 | 3회 측정 |
|---|---|
| (a) 서버 내부 루프 1,000회 | 5.7 / 5.5 / 5.8 ms |
| (b) `IN` 목록 1회 | 3.5 / 2.7 / 2.8 ms |
| (a') **클라이언트 왕복** 1,000회 (TCP) | 255 / 288 / 240 ms |
| (b') 같은 것을 1회 | 66 / 70 / 71 ms |

(a)/(b) 는 서버 안에서만 도는 것이라 2배 차이지만, 실제 애플리케이션 형태인 (a')/(b') 는
**왕복 1회당 약 0.18ms × 999회 ≈ 180ms** 가 순수 오버헤드로 붙는다.
(b') 의 66ms 는 대부분 psql 기동 비용이므로, 쿼리 자체 차이는 거의 없고
**전부 왕복 비용**이라는 것이 요점이다. 원격 네트워크(RTT 0.5~1ms)라면 이 값이 5배로 뛴다 — §M-9.

### 트리거 동기화 — Tow 가 전제한 "완벽한 동기화"의 실제 비용

앞의 ④는 전파 비용을 **수동 UPDATE** 로 쟀다. 하지만 Tow 10장의 전제는
"엄밀히 설계된 트리거로 자동 동기화하면 기능적으로는 안전하다"는 것이다.
그 전제를 실제로 구현하고 오버헤드를 잰다.

**먼저 ④의 설계 결함을 고쳐야 한다.** ④의 `lineitem_denorm` 에는 `l_linenumber` 가 없었다.
조회 전용이면 상관없지만 **행을 특정할 수 없으므로 동기화가 불가능하다.**
반정규화 테이블을 만들 때 원본의 키를 반드시 함께 가져와야 하는 이유다.

**트리거 3종** (`scripts/tpch/t9-trigger-sync.sh` 에 전문)

| 트리거 | 대상 | 하는 일 | 팬아웃 |
|---|---|---|---|
| `t_sync_li` | lineitem INSERT/UPDATE/DELETE | denorm 행 반영. **INSERT 시 상위 두 테이블을 조회해 상속 컬럼을 재계산** | 1 |
| `t_sync_ord` | orders UPDATE | 그 주문의 denorm 행에 날짜·우선순위 전파 | 약 4 |
| `t_sync_cust` | customer UPDATE | 그 고객의 모든 주문의 denorm 행에 등급 전파 | 약 38 |

**정확성 검증** — 네 가지 변경 유형을 모두 확인했다(전부 `ROLLBACK`).

| 검증 | 결과 |
|---|---|
| customer 등급 변경 → 대상 38행 | 38/38 반영 |
| orders 날짜 변경 → 대상 4행 | 4/4 반영 |
| lineitem DELETE | denorm 행 삭제됨 |
| lineitem UPDATE | 새 값 반영됨 |

**오버헤드 측정** (단일 세션 내 `\timing`, 6라운드 교차, 최소값)

| 작업 | 전파 팬아웃 | 트리거 OFF | 트리거 ON | 배수 |
|---|---|---|---|---|
| `customer` 1행 UPDATE | 38행 | 0.153 ms | 0.223 ms | **1.5배** |
| `orders` 1행 UPDATE | 4행 | 0.291 ms | 0.806 ms | **2.8배** |
| `lineitem` 1행 UPDATE | 1행 | 0.348 ms | 1.098 ms | **3.2배** |
| `lineitem` DELETE (1주문) | 4행 | 0.140 ms | 0.315 ms | 2.2배 |
| `lineitem` INSERT 약 1,200행 | 1,200행 | 14.267 ms | 34.775 ms | 2.4배 |

> **배수는 실행마다 흔들린다.** 같은 스크립트를 3라운드로 다시 돌리면
> `orders` 3.7배 / `lineitem` UPDATE 4.0배까지 올라간다(컨테이너 부하 편차).
> **안정적으로 재현되는 것은 절대 배수가 아니라 아래의 순서**다 —
> `customer`(가장 쌈) < `DELETE` < `orders` < `lineitem` UPDATE(가장 비쌈).
> 절대값이 필요하면 각자 환경에서 라운드를 늘려 재야 한다(§T-0).

**결론 7 — 비용은 팬아웃이 아니라 "위를 되짚어야 하는가"가 결정한다.**
직관적으로는 38행을 고치는 `customer` UPDATE 가 가장 비쌀 것 같지만 **1.5배로 가장 싸다.**
트리거가 한 번 발화해 38행을 **집합 단위 UPDATE** 한 번으로 처리하기 때문이다.
반대로 `lineitem` 1행 UPDATE 는 고작 1행을 고치는데 **3.2배로 가장 비싸다** —
상속 컬럼(`c_mktsegment`, `o_orderdate`, `o_shippriority`)을 채우려면
**조인 트리를 거슬러 올라가 orders 와 customer 를 매번 다시 조회해야** 하기 때문이다.

> 반정규화의 쓰기 비용을 추정할 때 팬아웃만 보면 틀린다.
> **"이 변경을 반영하려면 상속 값을 다시 유도해야 하는가"** 를 함께 봐야 한다.

**드리프트 검사** — 커밋되는 혼합 워크로드(등급 변경 50건, 주문일 변경 200건,
배송일 변경, DELETE 21주문, INSERT 51주문)를 가한 뒤 원본과 대조했다.

| 원본 기준 행수 | denorm 행수 | 누락·불일치 | 유령 행 |
|---|---|---|---|
| 3,000,583 | 3,000,583 | **0** | **0** |

**단일 세션에서는 트리거가 완벽한 동기화를 달성한다.** 다만 그 대가가
**모든 쓰기에 붙는 1.5~3.2배**이고, 이것은 조회가 있든 없든 **영구히** 지불된다.

> ⚠️ **여기까지는 단일 세션 결과다.** 아래 §동시성에서 이 결론이 뒤집힌다 —
> 위 문장을 "트리거면 안전하다"로 읽으면 안 된다.

### 동시성 — 단일 세션 결론이 뒤집히는 지점

위 드리프트 0은 **한 세션이 순차 실행**한 결과다. 여러 세션이 동시에 쓰면 어떻게 되는지
`pgbench` 로 확인한다.

```bash
./scripts/tpch/t9-concurrency.sh          # 기본 8 클라이언트 / 20초
```

**처리량** (8 clients, 20초, 좁은 키 범위에 집중시켜 경합 최대화)

| 조건 | tps | 평균 지연 | 데드락 | 동시 워크로드 후 드리프트 |
|---|---|---|---|---|
| A. 트리거 OFF | 5,702 | 2.03 ms | 0 | — |
| B. 트리거 ON (소박한 구현) | 3,562 | 3.02 ms | 0 | **0** |
| C. 트리거 ON + `FOR SHARE` | 3,593 | 2.87 ms | 0 | **0** |

동시 쓰기 처리량은 **약 1.4~1.5배 비용**(5,702 → 2,700 내외)이고 **데드락은 없었다.**

**그런데 B의 "드리프트 0" 은 안전하다는 증명이 아니다.**
워크로드가 `cust` 와 `ord` 를 독립적으로 뽑기 때문에, "T2가 고른 주문이 하필 T1이 지금
고치고 있는 고객의 것"인 경우가 거의 안 생긴다. 조건을 **겨냥해서** 다시 만들어 본다.

```
세션 A: BEGIN; UPDATE customer SET c_mktsegment='HAZARD' WHERE c_custkey=1;   -- 아직 커밋 안 함
        (트리거가 고객 1의 기존 주문들의 denorm 행을 갱신)
세션 B:        INSERT INTO lineitem (고객 1의 주문에 새 행);
        (트리거가 customer 를 읽는다 → READ COMMITTED 라 아직 옛 값이 보인다)
세션 A: COMMIT;
```

| | denorm 에 기록된 등급 | 실제 고객 등급 | 드리프트 |
|---|---|---|---|
| 소박한 트리거 | `SEG2` (옛 값) | `HAZARD` | **발생** |

**A의 갱신은 아직 없던 행을 지나쳤고, B는 아직 안 보이는 새 값을 읽었다.**
둘 다 자기 트랜잭션 안에서는 옳게 동작했는데 결과는 어긋난다 —
`READ COMMITTED` 에서 파생 데이터를 트리거로 유지할 때의 전형적인 함정이다.

**수정**: lineitem 트리거가 상위 행을 **읽을 때 잠근다.**

```sql
SELECT c.c_mktsegment, o.o_orderdate, o.o_shippriority INTO seg, od, sp
  FROM orders o JOIN customer c ON o.o_custkey=c.c_custkey
 WHERE o.o_orderkey = NEW.l_orderkey
   FOR SHARE OF o, c;        -- 동시 갱신 중이면 커밋을 기다렸다가 최신 값을 읽는다
```

같은 겨냥 실험을 다시 돌리면 `FIXED` / `FIXED` 로 **드리프트가 사라진다.**
처리량도 3,562 → 3,593 tps 로 **사실상 비용이 없다**(측정 편차 범위).

> 단 B와 C는 `FOR SHARE` 외에 구현도 달라졌으므로(`INSERT…SELECT` → `SELECT INTO` + `INSERT`)
> 둘의 tps 차이를 `FOR SHARE` 만의 효과로 읽으면 안 된다. 말할 수 있는 것은
> **"FOR SHARE 를 넣어도 처리량이 눈에 띄게 나빠지지 않았다"** 까지다.

### 나머지 두 경로 — orders / customer 트리거도 같은 병을 앓는다

위에서 고친 것은 `sync_li`(lineitem INSERT 경로) 하나뿐이다. 트리거가 **잠그지 않고
상위를 읽는 지점**을 전부 세어 보면 셋이다.

| 트리거 | 잠그지 않고 읽는 것 | 상태 |
|---|---|---|
| `sync_li` | orders + customer (상속 컬럼 유도) | 위에서 `FOR SHARE` 로 수정 |
| `sync_ord` | `o_custkey` 변경 시 customer | **미점검** |
| `sync_cust` | 대상 주문 목록을 구하는 orders | **미점검** |

겹침 후보를 손으로 열거하고, 같은 행을 만져 **행 락이 직렬화해 줄 것**(H4·H5)은
실험에서 제외했다.

| # | 시나리오 | 결과 |
|---|---|---|
| **H1** | 고객 등급변경(미커밋) ∥ 주문을 **그 고객으로 이동** | **드리프트** |
| **H2** | 고객 등급변경(미커밋) ∥ 주문을 **그 고객에서 빼냄** | 안전 |
| **H2'** | 위와 **순서를 뒤집으면**(주문 이동을 먼저 열고 등급변경이 나중 커밋) | **드리프트** |
| **H3** | 주문 날짜변경(미커밋) ∥ 그 주문에 lineitem INSERT | **드리프트** |
| H4 | 같은 customer 를 두 세션이 동시 변경 | 행 락이 직렬화 (실험 생략) |
| H5 | orders 변경 ∥ 같은 주문의 lineitem DELETE | 행 락이 직렬화 (실험 생략) |

실측 예: H1 에서 주문이 고객 1로 옮겨왔는데 denorm 에는 옛 등급이 박힌다.

| | denorm 기록 | 실제 | 드리프트 |
|---|---|---|---|
| H1 (소박한 구현) | `MACHINERY` | `H1NEW` | **발생** |
| H2' (소박한 구현) | `H2REV` | `MACHINERY` | **발생** |
| H3 (소박한 구현) | `1998-06-06` | `2001-09-09` | **발생** (수동 3/3) |

> **H3 의 재현 조건이 까다롭다.** 두 psql 세션을 직접 띄워 수동으로 하면 3/3 재현되는데,
> `t9-concurrency.sh` 안에서는 재현되지 않는다(스크립트 출력에 `drift=f` 로 나온다).
> B 가 A 의 UPDATE **보다 먼저** 들어가면 A 의 전파가 B 의 새 행까지 덮어버려
> 드리프트가 사라지기 때문이고, 스크립트의 신호 타이밍으로는 그 창을 안정적으로 못 맞춘다.
> **H1·H2' 는 스크립트에서도 안정적으로 재현되므로**, 자동 검증은 그 둘로 하고
> H3 는 수동 절차를 스크립트 주석에 남겨 두었다.
> — 재현이 어렵다는 것이 안전하다는 뜻이 아니라는 점이 오히려 이 해저드의 위험성이다.

**H2 와 H2' 의 차이가 이 절의 핵심이다.**
같은 두 트랜잭션인데 **순서만 뒤집었더니 한쪽은 안전하고 한쪽은 깨진다.**

- **H2(안전)**: A의 트리거가 주문 X의 denorm 행을 먼저 갱신하고 **락을 쥔 채** 있으므로,
  B의 트리거가 같은 행에 오다가 **막힌다.** A가 커밋하면 B가 깨어나 최신 상태로 덮어쓴다 →
  **뒤에 쓴 쪽이 옳은 값을 쓴다.**
- **H2'(위험)**: B가 먼저 락을 쥐고, A가 뒤에서 기다렸다가 **나중에** 덮어쓴다.
  그런데 A가 쓰는 값은 "고객 1의 새 등급"이고, 주문 X는 이미 고객 2로 떠났다 → 어긋난다.
- **H1(위험)**: 아예 **경합이 없다.** A의 subquery 는 아직 고객 1 소유가 아닌 주문 X를
  대상에서 제외하므로 A는 X의 denorm 행을 건드리지 않는다. 직렬화해 줄 락이 없으니
  B가 혼자 옛 값을 쓰고 끝난다.

> **여기서 얻는 판별법**: 두 트랜잭션이 **같은 denorm 행에서 경합하면** DB가 직렬화해 주지만,
> **한쪽이 그 행을 "내 대상이 아니다"라고 건너뛰면** 아무도 직렬화해 주지 않는다.
> 파생 데이터 트리거를 검토할 때 **"이 갱신이 놓치는 행은 무엇인가"** 를 물어야 하는 이유다.

**수정** — 세 경로 모두 상위를 **잠그고** 읽게 한다.

```sql
-- sync_ord: 고객이 바뀔 때 그 고객 행을 잠근다 (H1)
SELECT c_mktsegment INTO seg FROM customer WHERE c_custkey=NEW.o_custkey FOR SHARE;

-- sync_cust: 훑을 주문 목록을 잠근다 (H2') — 훑는 중에 주문이 빠져나가는 것을 막는다
UPDATE lineitem_denorm SET c_mktsegment=NEW.c_mktsegment
 WHERE l_orderkey IN (SELECT o_orderkey FROM orders WHERE o_custkey=NEW.c_custkey FOR SHARE);
```

세 시나리오를 다시 돌리면 **전부 드리프트가 사라진다**(H1 `H1FIX`/`H1FIX`,
H2' `MACHINERY`/`MACHINERY`, H3 `2001-09-09`/`2001-09-09`).

**대가** (8 clients / 20초)

| 구현 | tps | 지연 | 데드락 | 드리프트 |
|---|---|---|---|---|
| 트리거 OFF | 5,702 | 2.03 ms | 0 | — |
| 소박한 구현 | 3,562 | 3.02 ms | 0 | 0 (겨냥하면 발생) |
| `sync_li` 만 수정 | 3,593 | 2.87 ms | 0 | 0 (H1·H2' 잔존) |
| **3경로 전부 수정** | **3,297** | **3.65 ms** | **0** | **0** |

정합성을 끝까지 지키면 처리량이 5,702 → 3,297 로 **약 1.8배 비용**이 된다.
`sync_li` 만 고친 상태(3,593)보다 21% 더 느리다 — **나머지 두 경로의 락이 공짜가 아니다.**
데드락은 어느 구성에서도 발생하지 않았다.

### `FOR SHARE` 의 락 범위 — 대형 고객에서 얼마나 비싼가

`sync_cust` 는 **한 고객의 주문 전체**를 `FOR SHARE` 로 잠근다. TPC-H 의 자연 분포는
고객당 평균 10건 / 최대 25건으로 편중이 없지만, 실무에는 주문 수천 건짜리 대형 계정이 있다.
그 상황을 만들어(주문을 한 고객에게 몰아서) 락 범위의 비용을 측정했다.

```bash
./scripts/tpch/t9-lock-range.sh
```

**① 단일 세션에서도 공짜는 아니다 — 잠그는 행 수에 비례해 붙는다**

| 고객1 주문수 | denorm 행 | naive | `FOR SHARE` | 배수 |
|---|---|---|---|---|
| 10 | 30 | 3.4 ms | 3.4 ms | 1.01배 |
| 100 | 412 | 11.6 ms | 7.5 ms | 0.65배 (편차) |
| 1,000 | 3,954 | 32.3 ms | 46.0 ms | 1.42배 |
| 5,000 | 20,075 | 153.6 ms | 222.9 ms | **1.45배** |

3.4ms → 153.6ms 로 늘어난 몸통은 **denorm 행 자체를 갱신하는 비용**이 맞다.
하지만 같은 행 수에서 naive 와 `FOR SHARE` 를 비교하면 1,000건 이상에서 **1.4~1.5배**가 붙는다 —
5,000행 잠금에 약 **+69ms**. 행 공유 락을 5,000개 획득하는 비용은 실재한다.

> 처음에는 이 값을 "0.96~1.17배, 사실상 공짜"로 적었다. 재측정에서 뒤집혔다(정정 목록 12번).
> 다만 **결론의 방향은 그대로**다 — 단일 세션의 +69ms 는 아래 ②의 경합 비용(+2,677ms)에 비하면
> 여전히 작다. 지배적인 것은 락 획득 비용이 아니라 **락을 기다리는 쪽**이다.

**② 비용의 대부분은 경합에서 나온다**

고객1이 주문 5,000건을 가진 상태에서, 그중 **한 주문**을 다른 세션이 건드리면:

| `sync_cust` 구현 | 무관한 `UPDATE orders` 소요 |
|---|---|
| naive | 58 ms |
| `FOR SHARE` | **2,735 ms** (약 47배) |

그 트랜잭션은 고객 등급과 아무 상관이 없는데도 **등급 변경 트랜잭션이 커밋할 때까지 통째로 막힌다.**

**③ 그런데 대기 시간은 고객 크기에 비례하지 않는다**

고객1의 주문을 100 / 1,000 / 5,000 으로 바꿔가며 재도 피해자의 대기는 모두 2.5초 안팎이었다.
당연하다 — 대기 길이는 **앞선 트랜잭션이 얼마나 오래 열려 있는가**로 결정되지
잠긴 행이 몇 개인지와 무관하다. **고객 크기가 키우는 것은 대기 길이가 아니라 "막히는 범위"** 다.

**④ 그래서 처리량 손해는 "워크로드가 잠긴 범위와 겹치는 비율"을 따라간다**

워크로드의 주문 키 범위를 1~5,000 으로 고정하고, 그중 고객1 소유 비율만 바꿔 측정했다
(8 clients / 12초, 5% 확률로 고객1 등급 변경 + 나머지는 그 범위의 주문 갱신).

| 고객1 주문수 | 워크로드 적중률 | naive tps | `FOR SHARE` tps | 손해 |
|---|---|---|---|---|
| 50 | 1% | 7,691 | 8,093 | 0.95배 (편차 범위) |
| 500 | 10% | 391 | 390 | 1.00배 |
| 5,000 | 100% | 67.8 | 27.5 | **2.47배** |

**적중률이 낮으면 `FOR SHARE` 는 사실상 공짜이고, 겹치기 시작하면 급격히 비싸진다.**
앞의 균일 워크로드에서 1.27배였던 손해가, 대형 고객에 편중시키면 **2.47배**로 커진다.

여기서 `FOR SHARE` 손해 배수보다 더 중요한 것이 **naive 열의 절대값**이다 —
7,691 → 391 → 67.8. **락을 아예 안 써도 1%→10% 구간에서 이미 20배가 무너진다.**
즉 편중의 주된 피해는 락이 아니라 **팬아웃 자체**(등급 1건 변경 = denorm 2만 행 갱신)이고,
`FOR SHARE` 는 이미 무너진 것을 2.5배 더 무너뜨릴 뿐이다.
**락을 빼는 것은 이 문제의 해법이 아니다.**

**결론 9 — 정합성 락의 비용은 "무엇을 잠그느냐"가 아니라 "누가 그걸 건드리느냐"다.**
같은 `FOR SHARE` 가 어떤 서비스에서는 공짜이고 어떤 서비스에서는 처리량을 반 토막 낸다.
판단 기준은 락 범위의 절대 크기가 아니라 **그 범위가 실제 쓰기 트래픽과 얼마나 겹치는가**이며,
이것은 스키마가 아니라 **워크로드를 봐야 알 수 있다.**

실무적 함의: 대형 계정이 존재하고 그 계정의 주문에 쓰기가 몰리는 시스템이라면,
행 단위 `FOR SHARE` 대신 **다른 정합성 전략**(변경 큐 + 비동기 전파 + 정합성 배치,
또는 애초에 그 컬럼을 반정규화하지 않기)을 검토해야 한다.
→ 그 대안을 실제로 구현해 잰 것이 다음 절이다.

### 대안 — 변경 큐 + 비동기 전파는 무엇을 사고 무엇을 파는가

```bash
./scripts/tpch/t9-change-queue.sh          # 8 clients / 15초
```

동기 트리거를 **변경 큐 + 백그라운드 워커**로 바꿔, 같은 데이터·같은 워크로드에서 비교했다.

```sql
-- 큐 적재 트리거: 팬아웃만큼 일하지 않고, 키 하나만 남기고 즉시 끝난다
CREATE FUNCTION enq_cust() RETURNS trigger AS $$
BEGIN
  IF NEW.c_mktsegment IS DISTINCT FROM OLD.c_mktsegment THEN
    INSERT INTO denorm_queue(kind,k1) VALUES ('cust', NEW.c_custkey);
  END IF; RETURN NEW;
END $$ LANGUAGE plpgsql;

-- 워커: 배치를 claim 하고 **진실을 다시 읽어** 덮어쓴다
WITH claimed AS (
  DELETE FROM denorm_queue WHERE id IN (
    SELECT id FROM denorm_queue ORDER BY id LIMIT batch FOR UPDATE SKIP LOCKED)
  RETURNING kind,k1,k2,enq_at)
SELECT ... array_agg(DISTINCT k1) FILTER (WHERE kind='cust') ... FROM claimed;

UPDATE lineitem_denorm d SET c_mktsegment = cu.c_mktsegment
  FROM orders o JOIN customer cu ON o.o_custkey = cu.c_custkey
 WHERE d.l_orderkey = o.o_orderkey AND cu.c_custkey = ANY(ck)
   AND d.c_mktsegment IS DISTINCT FROM cu.c_mktsegment;
```

**이 설계에서 정합성을 만드는 것은 두 가지 성질이고, 둘 다 필수다.**

1. **큐에는 값이 아니라 키만 넣는다.** 워커가 적용 시점에 진실을 다시 읽으므로
   멱등하고 순서에 무관하다. 큐가 재정렬되든 중복되든 결과가 같다.
   값을 큐에 실었다면 순서 보장이 필요해지고, 그 순간 큐는 락만큼 비싸진다.
2. **원본 변경과 큐 INSERT 가 같은 트랜잭션에서 커밋된다.**
   워커가 큐 항목을 볼 수 있다는 것은 그 변경도 이미 커밋되어 보인다는 뜻이다.
   그래서 워커는 **낡은 값을 읽는 것이 원리적으로 불가능**하다.
   §T-9 동시성 절에서 본 `READ COMMITTED` 경쟁이 여기서는 단순한 **지연**이 된다.

> 이것이 트랜잭셔널 아웃박스(transactional outbox)가 이중 쓰기(dual write)와
> 결정적으로 다른 지점이다. 큐를 외부 브로커에 직접 쏘면 성질 2가 깨지고,
> 그 순간 "메시지는 갔는데 DB는 롤백" 또는 그 반대가 생긴다.

**① 쓰기 경로 지연** (고객 등급 1건 변경, 5회 최소값)

| 고객1 주문수 | denorm 행 | 동기 naive | 동기 `FOR SHARE` | 큐 | 큐/naive |
|---|---|---|---|---|---|
| 10 | 68 | 4.4 ms | 4.4 ms | 2.4 ms | 0.55배 |
| 100 | 450 | 6.9 ms | 7.8 ms | 2.5 ms | 0.36배 |
| 1,000 | 3,992 | 32.7 ms | 43.7 ms | 2.3 ms | 0.07배 |
| 5,000 | 20,113 | 147.7 ms | 222.3 ms | 2.3 ms | **0.02배** |

동기 트리거는 팬아웃에 비례해 커지고, 큐는 **팬아웃과 무관하게 2.3ms 상수**다.
단 이 시점에 파생 테이블은 아직 안 고쳐졌다 — **일이 사라진 게 아니라 미뤄졌을 뿐이다.**

**② 피해 반경** (5,000주문 고객의 등급 변경 트랜잭션이 열린 동안, 무관한 `UPDATE orders`)

| 동기 naive | 동기 `FOR SHARE` | 큐 |
|---|---|---|
| 2,712 ms | 2,863 ms | **735 ms** |

여기서 앞 절의 이해가 하나 교정된다 — **`FOR SHARE` 를 빼도 대형 고객에서는 어차피 막힌다.**
naive 도 `lineitem_denorm` 2만 행을 갱신하며 행 락을 잡고, 그것이 `sync_ord` 경로와 겹치기 때문이다.
락을 피하는 방법은 `FOR SHARE` 를 빼는 것이 아니라 **경로 자체를 임계 경로 밖으로 옮기는 것**이다.
(큐도 0은 아니다. 큐 테이블과 공용 자원에서 경합이 남는다.)

**③ 처리량 — 자연 분포에서는 큐가 이기지 않는다**

| 구성 | 자연 분포 tps | 대비 | 편중 tps | 대비 |
|---|---|---|---|---|
| A. 트리거 없음(정합성 포기) | 4,932 | 1.00배 | 6,073 | 1.00배 |
| B. 동기 naive | 3,521 | 1.40배 | 48.8 | **124배** |
| C. 동기 `FOR SHARE` | 3,225 | 1.53배 | 24.4 | **249배** |
| D. 큐 (워커 OFF) | 4,660 | 1.06배 | 6,268 | 0.97배 |
| E. 큐 (워커 ON) | 3,308 | 1.49배 | **4,051** | 1.50배 |

이 표가 이 실습의 핵심이고, 읽는 법이 세 가지다.

- **자연 분포에서 E(3,308)와 C(3,225)는 사실상 같다.** 큐는 처리량을 사주지 않는다.
  총 일의 양이 같기 때문이다. 큐가 사주는 것은 **쓰기 지연(①)과 피해 반경(②)** 이다.
- **편중이 생겨야 갈린다.** 동기는 124~249배로 무너지고 큐는 1.50배를 유지한다(E는 C 대비 **166배**).
  무너지는 이유는 락 그 자체가 아니라 **모든 트랜잭션이 20만 행짜리 전파 트랜잭션 뒤에
  줄을 서기** 때문이며, 큐는 그 줄서기를 없앤다.
- **D(워커 OFF)를 시스템 처리량으로 읽으면 안 된다.** D가 보여주는 것은 애플리케이션 체감 지연뿐이고,
  남은 드리프트는 "틀렸다"가 아니라 "아직 안 됐다"이다. 비교 대상은 E다.

> ⚠️ **앞 절의 "편중 시 2.21배"와 여기 "249배"는 모순이 아니라 구성이 다르다.**
> 락 범위 실험은 `sync_cust` **한 경로만** 설치했고, 여기는 3경로를 모두 설치했다.
> `sync_ord` 가 `customer` 행을 `FOR SHARE` 로 읽으므로 **주문 갱신 전부가 등급 변경 뒤에 줄을 선다.**
> 경로를 하나 더 붙였을 뿐인데 손해가 2배에서 249배가 됐다 —
> **반정규화 유지 비용은 경로 수에 선형이 아니라 경로 간 상호작용에 지배된다.**
> 트리거를 하나씩 검증하고 안심하면 안 된다는 뜻이다.

**④ 미뤄진 일은 어디로 갔나** (편중 워크로드, 워커 1개 / 배치 1,000 / 4 CPU)

| 배치 수 | 큐 항목 | 실작업 키 | 합침 절감 | 평균 지연 | 최대 지연 |
|---|---|---|---|---|---|
| 99 | 97,347 | 90,748 | 6.8% | **4,424 ms** | **6,652 ms** |

부하 종료 시점 큐 잔량 37,253건 → 소진까지 5,184ms, 최종 드리프트 0.
**지연창 4~7초**가 큐가 판 대가다. 합침 절감이 6.8%로 낮은 것은 **항목 수 기준**이기 때문이고
(`ord`/`line` 키는 대부분 서로 다르다), 실제 절감은 `cust` 경로에 몰려 있다 —
한 배치의 `cust` 항목 수십 건이 `array_agg(DISTINCT ...)` 로 원소 1개가 되어
2만 행짜리 UPDATE 를 **한 번만** 돌게 만든다. 동기 트리거였다면 수십 번 돌 일이다.
**큐의 진짜 절감은 "미룸"이 아니라 "합침"에서 나온다.**

**⑤ 정합성** — §T-9 동시성 절의 H1 경쟁을 큐에서 그대로 재현했다.
전파 전 드리프트 40,226 → `denorm_drain()` 2회 후 **0**.
성질 2 때문에 워커는 낡은 값을 읽을 수 없고,
동기 naive 의 **정합성 문제가 큐에서는 가시성 문제**로 성질이 바뀐다.

**⑥ 워커가 죽으면 드리프트는 무한정 남는다.**
큐 유실을 시뮬레이션하니 44,070건이 영구히 어긋났다. 전량 대사(reconciliation)로 복구되며
**300만 행 풀스캔 3,262ms**. 즉 **큐는 대사 배치를 대체하지 않고 요구한다.**
"비동기라서 싸다"가 아니라 "비동기라서 운영 대상이 하나 늘었다"가 정확한 서술이다.

**결론 10 — 큐는 비용을 없애지 않는다. 임계 경로 밖으로 옮기고 배치로 합칠 뿐이다.**

| | 산 것 | 판 것 |
|---|---|---|
| 변경 큐 + 비동기 전파 | 쓰기 지연 상수화(2.3ms, 팬아웃 무관)<br>피해 반경 축소(2,863 → 735ms)<br>편중 하 처리량 유지(24 → 4,051 tps) | **4~7초 지연창**<br>큐·워커라는 운영 대상<br>상시 대사 배치(3.3초/300만 행)<br>**"읽는 쪽이 낡은 값을 견디는가"라는 새 요구사항** |

그리고 팬아웃 자체가 감당 불가라면 큐도 못 구한다 — 처리량 대신 **지연이 무한정 늘 뿐**이다.

→ 그래서 실무의 질문은 "정합성이 중요한가"가 아니다. 그건 언제나 중요하다.
실제 질문은 **"읽는 쪽의 지연 예산이 얼마인가"** 이고, 그것이 전략을 고른다.

| 지연 예산 | 선택 |
|---|---|
| 0 (읽는 즉시 최신이어야 함) | 동기 + `FOR SHARE`. 대신 편중을 감당할 수 있어야 한다 |
| 초 단위 허용 | 변경 큐 + 비동기 전파 + 대사 배치 |
| 어느 쪽도 감당 못 함 | **그 컬럼을 반정규화하지 않는다** (§T-8의 인덱스로 돌아간다) |

### 큐 튜닝 — 지연창은 손잡이로 줄이는 값이 아니라 "구간"이다

```bash
./scripts/tpch/t9-queue-tuning.sh          # 8 clients / 12초 / -R 800 / 3(핵심축 5) 라운드
```

앞 절의 4.4초는 **설정 하나(워커 1 / 배치 1,000)의 결과**였다. 두 손잡이를 축으로 훑는다.
이 실습은 산포가 커서 **중앙값과 범위를 함께** 내야 판단이 선다.

**① 배치 크기** (편중, 워커 1개, `-R 800`, 5라운드 교차)

| 배치 | 지연 중앙값 | 지연 범위 | 최대 지연 | 잔량 |
|---|---|---|---|---|
| 100 | 1,581 ms | 166~8,746 | 2,218 ms | 2,991 |
| 500 | 1,278 ms | 239~3,466 | 2,190 ms | 2,942 |
| 2,000 | **121 ms** | **53~249** | 1,112 ms | 261 |

중앙값 차이(13배)보다 **범위**가 중요하다. 작은 배치의 166~8,746ms 는 "느리다"가 아니라
**따라잡기가 불안정하다**는 뜻이다 — 따라잡으면 수백 ms, 한 번 밀리면 적체가 스스로를 키워
수천 ms 로 간다(쌍봉 분포). 배치 2,000 은 중앙값이 낮을 뿐 아니라 **범위가 좁다.**

**② 워커 수** (편중, 배치 2,000, `-R 800`, 5라운드 교차)

| 워커 | 지연 중앙값 | 지연 범위 | 잔량 |
|---|---|---|---|
| 1 | 309 ms | 89~774 | 1,931 |
| 2 | 267 ms | 184~371 | 1,186 |
| 4 | 447 ms | 232~995 | 3,346 |

1개와 2개는 **범위가 겹쳐 구분되지 않고**, 4개는 오히려 나쁘다.
같은 고객1의 denorm 행을 두고 서로 기다리는 데다, 4 CPU 를 8개 클라이언트와 나눠 갖는다.

**③ 자연 분포 대조** (배치 2,000, `-R 800`)

| 워커 | 지연 중앙값 | 지연 범위 | 잔량 | 합침배수 |
|---|---|---|---|---|
| 1 | **81 ms** | 73~176 | 66 | 1.2배 |
| 2 | 182 ms | 148~246 | 0 | 1.3배 |
| 4 | 601 ms | 386~824 | 0 | 1.6배 |

여기서 두 가지가 드러난다.
- **워커를 늘리면 여기서도 지연이 는다**(81 → 182 → 601). 핫키가 없으니 행 경합이 아니라
  순수한 CPU 경합이다. 즉 "워커를 늘리면 빨라진다"는 **어느 분포에서도 성립하지 않았다.**
- **편중 자체가 자릿수를 바꾸지는 않는다.** 워커 1개 기준 자연 81ms vs 편중 121~309ms 로
  같은 자릿수다. 자릿수를 바꾸는 것은 편중이 아니라 **따라잡지 못하게 되는 것**이다.

**④ 배치는 상한인가, 목표인가** (자연 분포, 저부하 `-R 200`, 워커 1개)

| 배치 | 지연 중앙값 | 지연 범위 |
|---|---|---|
| 100 | 59 ms | 58~227 |
| 2,000 | 57 ms | 14~58 |

사실상 같다. 워커가 배치가 차기를 기다리지 않고 `LIMIT batch` 로 **있는 만큼** 가져가기 때문이다.
**즉 batch 는 상한이지 목표가 아니고, 크게 잡아 손해가 없다.**
(배치가 찰 때까지 기다리는 설계였다면 여기서 큰 배치가 훨씬 불리하게 나왔을 것이다.
 큐를 직접 구현한다면 이 성질을 유지하는 것이 중요하다.)

**결론 11 — 지연창은 손잡이로 연속적으로 줄이는 값이 아니라 "구간"이다.**

| 구간 | 지연 | 판별 |
|---|---|---|
| 따라잡는 중 | 수십~수백 ms, 범위 좁음 | 잔량이 0 으로 돌아온다 |

| 포화 | 수렴하지 않음 | 적체가 단조 증가한다 |

배치 크기가 하는 일은 지연을 줄이는 게 아니라 **그 경계를 옮기는 것**이고,
워커 수는 어느 분포에서도 도움이 되지 않았다.
그래서 운영 지표는 "지연 몇 ms 목표"가 아니라 **"지금 따라잡고 있는가"** 여야 한다.
그 지표가 무너지면 손잡이가 아니라 **모델**을 봐야 한다 — 팬아웃을 줄이거나 핫 계정을 쪼개거나.

> ⚠️ **비교는 같은 스윕 안에서만 유효하다.** ①의 (워커1·배치2000)은 121ms, ②의 같은 조건은
> 309ms 로 2.5배 차이가 났다. 라운드 교차는 **스윕 내부의** 시간대 드리프트만 지운다.
> 스윕끼리의 절대값을 비교하면 안 되고, 축 하나를 바꾼 표 안에서만 읽어야 한다.

### 워커를 어떻게 깨울 것인가 — 폴링 / NOTIFY / 고정 창 / 적응형 창

```bash
pip install psycopg2-binary
./scripts/tpch/t9-notify-vs-poll.sh          # 8 clients / 12초 / 3 라운드
```

앞 절 ④에서 저부하 지연이 배치 100/2,000 둘 다 57~59ms 로 **배치와 무관하게 바닥이 잡혔다.**
용의자는 워커의 20ms 고정 sleep 이었고, 여기서 검증한다.

**왜 워커를 클라이언트로 내보냈는가.** plpgsql 로는 알림을 기다릴 수 없다 —
`pg_sleep()` 은 NOTIFY 로 깨지 않으므로 "알림이 올 때까지 블록"을 서버 안에서 표현할 방법이 없다.
그래서 워커를 파이썬으로 옮기되 **네 방식이 완전히 같은 코드·같은 `denorm_drain()`** 을 쓰게 했다.
각각 다른 언어로 짜면 깨우는 방식이 아니라 언어와 왕복 비용을 비교하게 된다.
①② 는 **전부 NOTIFY 를 발행하는 트리거**로 돌려 쓰기 경로를 동일하게 맞췄다.

겨루는 네 방식:
- **폴링** — 큐가 비면 고정 간격으로 잠들었다 다시 본다
- **NOTIFY** — 알림이 올 때까지 블록한다
- **고정 창(디바운스)** — 알림으로 깨우되 창 동안 더 모았다가 한 번에 처리
- **적응형 창** — 창 대신 **drain 사이 최소 간격**을 보장한다. 기다릴 시간을 *계산*하므로
  직전 drain 이후 이미 간격만큼 지났으면 한 톨도 안 기다린다.
  파라미터의 의미가 "얼마나 기다릴까"가 아니라 **"초당 몇 번까지 DB 를 찌를까"** 다.

```python
# 적응형: 기다릴 시간을 계산한다 — 한산하면 0, 바쁘면 자동으로 모인다
if a.mode == 'adaptive' and last_drain:
    wait = a.min_interval_ms / 1000.0 - (time.monotonic() - last_drain)
    if wait > 0:
        time.sleep(wait); conn.poll(); del conn.notifies[:]
```

네 방식을 **같은 스윕 안에서** 쟀다 — 스윕이 다르면 절대값을 비교할 수 없기 때문이다.

```python
# 놓친 알림이 없도록 순서가 중요하다.
#  1) 이미 도착해 버퍼에 있는 알림을 먼저 확인한다(있으면 즉시 재시도)
#  2) 없으면 소켓에서 기다린다. drain 과 select 사이에 도착한 알림은 소켓 버퍼에 남아
#     select 가 곧바로 readable 로 보고하므로 유실되지 않는다
conn.poll()
if conn.notifies:
    del conn.notifies[:]; continue
if select.select([conn], [], [], min(0.5, remaining))[0]:
    conn.poll(); del conn.notifies[:]
```

**② 중부하** (`-R 800`) — 여기서 판이 뒤집힌다.

지연 순서는 그대로다 — 워커가 따라잡는 한 큐는 자주 비고, 비어 있는 동안은

**그런데 왕복 열에서 NOTIFY 가 7,078 로 압도적으로 많다.** 트랜잭션마다 알림이 하나씩
나가므로 알림 기반이 사실상 **트랜잭션 속도의 바쁜 폴링으로 퇴화**했다
(배치당 4.4항목 — 잘게 쪼개 일한다). "알림 기반은 조용하다"는 통념과 반대다.

고정 창이 그 지점을 고치고(5ms: 지연 +1ms 에 왕복 7,078 → 4,213),
**적응형은 한 발 더 간다 — 빈 폴링이 4 와 2 로 사실상 0 이다**(고정 창은 737/365).
페이싱 덕에 깨어날 때는 이미 일이 쌓여 있어 **헛왕복 자체가 사라진다.**
배치당 항목이 4.4 → 16.2 → 51.7 로 커지는 것이 그 기전이다.

곡선으로 보면 **적응형 5ms(6ms/1,380)가 고정창 20ms(9ms/1,988)와 폴링 20ms(9ms/2,066)를
두 축 모두에서 이긴다.** 같은 파라미터끼리는 적응형이 더 공격적으로 모을 뿐이다.

**결론 12 — 배치와 깨우는 간격은 경쟁 관계가 아니라 서로 다른 구간의 손잡이다.**

| 구간 | 지배 요인 | 듣는 손잡이 |
|---|---|---|
| 따라잡는 중(건강) | **깨우는 간격** | NOTIFY / 짧은 폴링 |
| 적체(불건강) | **처리 용량** | 배치·모델 (앞 절 ⑤) |

NOTIFY 는 처리량 대책이 아니라 **응답성 대책**이며, 심지어 처리량을 1.57배 깎는다.
**적체가 문제인 상황에 붙이면 오히려 악화된다.**

**결론 13 — 깨우는 방식의 파라미터는 고정값으로 두면 반드시 한쪽 구간에서 틀린다.**

| | 한산(`-R 50`) | 바쁨(`-R 800`) |
|---|---|---|
| NOTIFY 단독 | 최선(2 ms) | 왕복 폭증(7,078) |
| 고정 창 | 손해(모을 것이 없는데 기다린다) | 이득 |
| **적응형 창** | **고정 창을 두 축 모두 지배** | **빈 폴링 0 수렴** |

고정 창은 부하 구간마다 답이 갈리므로 **한 값으로 두 구간을 다 감당하지 못한다.**
부하가 오르내리는 시스템에서는 어느 값을 골라도 한쪽에서 틀린 값이 된다.
적응형은 대기 시간을 *계산*해 그 딜레마를 없앤다.

다만 적응형도 공짜가 아니다. 부하가 높으면 **페이싱이 곧 지연**이 되므로
(5ms → 6ms, 20ms → 15ms) 값은 **허용 지연**을 보고 정해야 한다.
그리고 부하가 높아지면 "창을 두고 모으는 것"과 "주기적으로 훑는 것"이 같은 동작으로
수렴한다 — 고정창 20ms(9ms/1,988)와 폴링 20ms(9ms/2,066)가 거의 겹치는 것이 그 증거다.

**큐 깊이 신호는 기각됐다.** "적응형은 시간만 보므로 일이 쌓여 있어도 기다린다 —
깊이를 보면 피할 수 있지 않은가"라는 가설로, drain 이 남은 깊이를 함께 돌려주고
(추가 왕복 없음) 깊이 ≥ 임계치면 페이싱을 건너뛰는 `qdepth` 모드를 같은 스윕에서 쟀다.

| 구간 | 적응형 5ms | 큐깊이 5ms | 판정 |
|---|---|---|---|
| 한산 `-R 50` | 4ms / 왕복 883 | 4ms / 왕복 878 | 동일 — 신호 발화 없음 |
| 바쁨 `-R 800` | 5ms / 왕복 1,420 | 6ms / 왕복 1,295 | 동일(편차 범위) |
| 버스트 소진 (2만 건 적체) | 1,508~1,818ms | 1,900~1,927ms | 이득 없음 |

정상 구간에서는 페이싱 간격 동안 쌓이는 항목(~4건)이 임계치에 한참 못 미쳐 발화 자체가
없고, 버스트에서는 이론상 절약(페이싱 × 배치 수 ≈ 180ms)이 배치 작업 시간(1.5~1.9초)에
묻힌다. 임계치를 발화하게 낮추면 NOTIFY 로 돌아갈 뿐이다.

**결론 14 — 합침은 기다림 그 자체다. 기다림을 건너뛰면 합침도 같이 사라진다.**
왕복 절감(모아서 크게)과 지연 절감(즉시 처리)은 같은 손잡이의 양끝이라, 신호를 하나 더
단다고 둘 다 가질 수는 없다. 페이싱 값은 **읽는 쪽의 허용 지연**으로 정한다.

실무 조합은 **NOTIFY + 적응형 페이싱 + 타임아웃 폴링 병행**이다.
NOTIFY 는 저장되지 않으므로 워커가 죽어 있는 동안 발행된 알림은 사라진다 —
알림만 믿으면 재시작 직후 남은 큐를 영영 못 집는다.
**큐 테이블이 진실이고 알림은 힌트일 뿐**이라는 원칙을 지켜야 한다.

> ⚠️ **적체 구간에서의 NOTIFY 비교는 재현하지 못했다.** 편중 워크로드로 적체를 만들려 했으나
> 워커가 배치를 한 번도 적용하지 못한 채 큐가 비는 상태가 나와 해석이 불가능했다(원인 미규명).
> 빈 데이터로 "차이가 사라진다"를 주장하지 않기 위해 그 절을 스크립트에서 삭제했다.

**결론 8 — 파생 데이터의 정합성은 단일 세션 테스트로 보증되지 않는다.**
소박한 트리거는 순차 실행에서 3,000,583행 전부를 정확히 맞췄지만,
동시성에서는 **조용히 어긋난다.** 더 나쁜 것은 무작위 워크로드로는 그 사실이 드러나지도
않았다는 점이다(드리프트 0이 나왔다). **정합성 결함은 부하 테스트가 아니라
"이 두 트랜잭션이 겹치면 어떻게 되는가"를 손으로 따져서 찾아야 한다.**

그리고 이것은 §T-9 반정규화의 비용 항목에 하나를 더한다 —
**설계 난이도.** 조회를 6배 빠르게 만드는 대가로, 동시성 하에서 옳은 트리거를
설계하고 검증할 책임이 생긴다.

**그래서 §T-9의 최종 손익은 이렇게 읽어야 한다.**

| | 얻는 것 | 잃는 것 |
|---|---|---|
| ④ 반정규화 + 동기 트리거 | 조회 324.7 → 53.4 ms (**6배**) | 모든 쓰기 **1.5~3.2배**, 저장 289MB, 스키마 결합도 상승,<br>편중 시 처리량 **최대 249배** 붕괴 |
| ④' 반정규화 + 변경 큐 | 위와 같은 조회 이득 +<br>쓰기 지연 상수화, 편중 내성 | 쓰기 **1.49~1.50배**, **4~7초 지연창**,<br>큐·워커·대사 배치라는 운영 부담 |

읽기:쓰기 비율이 압도적으로 읽기 쪽이고, 그 조회가 자주 실행되며,
다른 방법(§T-8의 인덱스)으로는 목표를 못 맞출 때에만 성립하는 거래다.
셋 중 하나라도 아니라면 하지 않는 편이 낫다.

그리고 셋을 만족해서 하기로 했다면, **네 번째 질문이 남는다 — 읽는 쪽의 지연 예산.**
그 답이 동기와 큐를 가른다. 조회 이득(6배)은 두 경로가 같고, 갈리는 것은 전부 쓰기 쪽이다.

## M-1 | 1·2장 Method R — "중요한 행위의 가장 큰 응답시간 요소부터"

이 랩의 모든 실습에 적용할 **작업 순서 원칙**:

1. 목표를 "시스템을 빠르게"가 아니라 "q05를 3초→1초로"처럼 특정 쿼리+수치로 명세한다
   (책의 '악마의 제니 테스트': 캐시히트율 99% 달성해도 q05가 안 빨라지면 실패다).
2. 그 쿼리의 응답시간 분해(`EXPLAIN ANALYZE`의 노드별 actual time)에서 가장 큰 항목부터 공략한다 — 암달의 법칙.
3. 개선 후 반드시 같은 조건에서 재측정한다 (`run --warmup=1 --iterations=3`이 그 용도).

**잘못된 명세 체험** — "buffer hit ratio를 올리자"는 목표가 왜 실패하는지 직접 확인한다:

```bash
# ① 기준선 측정
./gradlew :tpch:bootRun --args="run --db=postgres --query=q09 --iterations=5"

# ② docker/postgres/postgresql.conf 에서 shared_buffers 를 1GB → 4GB 로 수정
#    (docker-compose.yml 의 shm_size 도 함께 늘려야 할 수 있다)
cd docker && docker compose restart postgres && cd ..

# ③ 워밍업을 충분히 준 뒤 재측정 → hit ratio 는 올라가지만 시간은?
./gradlew :tpch:bootRun --args="run --db=postgres --query=q09 --warmup=3 --iterations=5"
./gradlew :pgbench-lab:bootRun --args="monitor"   # hit_pct 확인
```

q09는 정렬·집계 비용이 지배하므로 버퍼를 늘려도 거의 안 빨라진다.
반면 §T-8의 결합 인덱스 하나가 훨씬 큰 효과를 낸다.
**"전역 지표 개선 ≠ 내 쿼리 개선"** 을 몸으로 확인하는 실습이며,
책 2장의 '악마의 제니 테스트'가 걸러내려던 바로 그 명세 오류다.
실험 후 `shared_buffers` 는 원복한다.

## M-2 | 3·5·6장 확장 SQL 트레이스(10046)의 현대적 대응

책의 트레이스 통계 c(CPU), e(경과), p(물리읽기), cr(논리읽기)는 PostgreSQL에서 이렇게 얻는다:

```sql
-- 세션 수준 "트레이스" 켜기. 이 세션에서만 적용되며 재시작이 필요 없다.
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 0;   -- 모든 쿼리 (ms 단위, 0 = 전부)
SET auto_explain.log_analyze = on;
SET auto_explain.log_buffers = on;
SET auto_explain.log_nested_statements = on;   -- 함수 내부 쿼리까지 (10046의 dep>0 에 대응)

-- 이후 이 세션에서 실행하는 모든 쿼리의 계획이 서버 로그에 남는다
SELECT count(*) FROM lineitem WHERE l_shipdate > date '1998-01-01';
```

```bash
# 로그 확인 (다른 셸에서)
docker logs --tail 50 tuninglab-postgres
```

주의: `LOAD 'auto_explain'` 은 **현재 세션에만** 적용된다.
모든 세션을 자동으로 추적하려면 `docker/postgres/postgresql.conf` 의
`shared_preload_libraries` 에 `auto_explain` 을 추가하고 재시작해야 한다
(기본 설정에는 `pg_stat_statements` 만 들어 있다).
책 6장이 경고한 "타인 세션 트레이스"와 같은 구도다 — 내 세션은 쉽고, 남의 세션은 준비가 필요하다.

| 10046 통계 | EXPLAIN (ANALYZE, BUFFERS) 대응 |
|---|---|
| e (경과시간) | actual time / Execution Time |
| c (CPU) | e - I/O Timings (track_io_timing=on) |
| p (물리읽기) | Buffers: shared read |
| cr (논리읽기) | Buffers: shared hit |
| r (행수) | actual rows |

책 6장의 경고("행위의 시작~끝 전체를 수집하라")는 `pg_stat_statements_reset()` 후
**정확히 대상 작업만** 실행하고 조회하는 습관으로 대응한다: pgbench-lab의 `reset-stats` 명령이 그 용도.

## M-4 | 9장 대기열 이론 — R = S + W, 무릎(knee) 찾기

**핵심 실습.** 동시성을 늘려가며 TPS와 latency 곡선을 그린다:

```bash
for c in 1 2 4 8 16 32 64; do
  ./gradlew :pgbench-lab:bootRun --args="run --clients=$c --seconds=20 --scale=10"
done
# 각 결과의 TPS, p95, p99를 표로 기록
```

관찰 포인트 (책의 M/M/m 곡선 그대로):

- clients ≤ CPU 코어수: TPS 선형 증가, p95 안정 (S만 존재)
- 무릎 근처: TPS 증가 둔화, p95가 서서히 상승 (W 발생 시작)
- 무릎 이후: TPS 정체/하락, **p99가 폭증하고 변동성 급증** (W 지배)

sysbench-lab에서 동일 실험(`--threads` sweep)을 하고, `--hot=true`를 켜면
서비스 채널(m)이 CPU가 아니라 **행 락 1개**로 줄어든 극단적 대기열이 된다 — errors(락 대기) 폭증 관찰.

### 참고: 실제 측정값 (PostgreSQL 16.13, **4 CPU 코어**, scale=10 / accounts 100만, 20초씩)

| clients | TPS | avg | p95 | p99 | max | W = R − S |
|---|---|---|---|---|---|---|
| 1 | 1,327 | 0.75 ms | 1.09 | 1.47 | 25.7 | — (기준 S=0.75) |
| 2 | 2,699 | 0.74 | 1.04 | 1.40 | 39.5 | ~0 |
| **4** | **4,642** | 0.86 | 1.39 | 2.01 | 25.4 | 0.11 ms (13%) |
| 8 | 4,367 | 1.81 | 3.66 | 5.64 | 45.7 | 1.06 ms (59%) |
| 16 | 4,520 | 3.45 | 7.42 | 11.61 | 54.6 | 2.70 ms (78%) |
| 32 | 3,463 | 8.71 | 23.53 | 41.18 | 124.0 | 7.96 ms (91%) |
| 64 | 3,103 | 18.02 | 59.08 | 105.35 | 316.6 | **17.27 ms (96%)** |

**무릎이 정확히 CPU 코어 수(4)에 있다.** 교과서 그대로다.

- **1→4**: TPS 가 1,327 → 4,642 로 **3.50배**(선형에 가깝다). 그동안 avg 는 0.75 → 0.86 으로
  거의 움직이지 않는다. 응답시간이 **전부 S**이고 W 가 없다는 뜻이다.
- **4→8**: TPS 는 오히려 줄었는데(4,642 → 4,367) avg 는 **2배**가 된다(0.86 → 1.81).
  더 내지 못하는 처리량을 대기로 지불하기 시작하는 지점 — 이것이 무릎이다.
- **8→64**: TPS 는 **33% 하락**(4,642 → 3,103)하는데 p99 는 **52배 폭증**(2.01 → 105.35).

**무릎 이후에 동시성을 늘리는 것은 손해가 아니라 순손실이다.** clients=64 는 clients=4 보다
처리량이 적으면서 p99 는 52배 나쁘다. Millsap 의 `R = S + W` 에서 W 가 응답시간의 96% 를
차지하는 구간이며, 이때 튜닝해야 할 것은 쿼리가 아니라 **동시성 그 자체**다.

> 커넥션 풀 크기를 코어 수의 몇 배로 잡는 관행이 왜 위험한지가 이 표에 있다.
> 풀을 키우면 "더 많이 받을 수 있다"가 아니라 "더 오래 기다리게 한다"가 된다.

## M-5 | 10장 자원 프로필 4단계 가이드라인

모든 튜닝 실습에서 지킬 순서 (책 그대로):

1. **응답시간 기여 내림차순으로**: EXPLAIN ANALYZE에서 actual time 최대 노드부터.
2. **호출 횟수 제거가 먼저**: 인덱스로 latency를 줄이기 전에, 그 접근이 애초에 필요한지
   (불필요한 조인/컬럼/반복 호출 제거 — §M-11).
3. **그다음 경합 제거**: 락(§M-4 hot-row), WAL flush(§M-6), checkpoint(§M-7).
4. **하드웨어(메모리 증설 = shared_buffers/buffer_pool 확대)는 마지막**.
   실습: 위 1~3을 안 하고 buffer만 4GB로 올렸을 때 vs 인덱스 하나 추가했을 때의 효과 비교.

## M-6 | 11장 + 12장 사례1·3 — 커밋 비용과 왕복(SQL*Net) 제거

**커밋 비용(log file sync) 측정.** 커밋마다 WAL을 디스크에 내리는 비용을 껐다 켜며 비교한다.

PostgreSQL — `synchronous_commit` 은 **재시작 없이 세션/전역 단위로 바꿀 수 있다**:

```bash
# ① 기준선 (synchronous_commit = on)
./gradlew :pgbench-lab:bootRun --args="init --scale=10"
./gradlew :pgbench-lab:bootRun --args="run --clients=8 --seconds=30 --scale=10"
```

```sql
-- ② psql -d pgbench_lab 에서 전역으로 끄기 (재시작 불필요)
ALTER SYSTEM SET synchronous_commit = off;
SELECT pg_reload_conf();
SHOW synchronous_commit;
```

```bash
# ③ 재측정 → TPS 상승폭이 곧 '커밋당 fsync 대기 시간'의 값어치다
./gradlew :pgbench-lab:bootRun --args="run --clients=8 --seconds=30 --scale=10"
```

```sql
-- ④ 원복 (반드시!)
ALTER SYSTEM RESET synchronous_commit;
SELECT pg_reload_conf();
```

> `ALTER SYSTEM` 은 **트랜잭션 블록 안에서 실행할 수 없다.** 대화형 psql 에서 한 줄씩 치면
> 문제없지만, `psql -c "ALTER SYSTEM ...; SELECT pg_reload_conf();"` 처럼 한 번에 묶으면
> `cannot run inside a transaction block` 으로 실패한다. 스크립트로 돌린다면 `-c` 를 나눠야 한다.

### 참고: 실제 측정값 (8 clients / 30초, 각 설정 2회)

| `synchronous_commit` | TPS | avg | p99 |
|---|---|---|---|
| `on` (기본) | 2,521 / 2,597 | 3.15 / 3.05 ms | 9.52 / 9.44 ms |
| `off` | **5,320 / 6,003** | 1.49 / 1.32 ms | 5.95 / 4.88 ms |

**처리량 2.2배, 지연 절반.** 이 차이가 곧 **커밋마다 WAL 을 디스크에 내리는 값**이다
(오라클의 `log file sync` 에 해당). 두 설정을 각각 2회 재서 구간이 겹치지 않는 것을 확인했다.

주의: `off` 는 성능 옵션이 아니라 **내구성 옵션**이다. 크래시 시 마지막 몇 백 ms 의
커밋된 트랜잭션이 사라질 수 있다(데이터 파일 자체는 깨지지 않는다).
"2.2배" 는 공짜가 아니라 **그 위험의 가격**이다.

MySQL — `innodb_flush_log_at_trx_commit` 도 동적으로 바꿀 수 있다:

```sql
-- docker exec -it tuninglab-mysql mysql -u root -proot sysbench_lab
SET GLOBAL innodb_flush_log_at_trx_commit = 2;   -- 1(기본) → 2
-- sysbench-lab run 재측정 후
SET GLOBAL innodb_flush_log_at_trx_commit = 1;   -- 원복
```

**내구성 트레이드오프를 반드시 함께 기록할 것.**
`synchronous_commit = off` 는 크래시 시 최근 커밋 일부가 사라질 수 있고(단, 데이터 파일은 일관),
`flush_log_at_trx_commit = 2` 는 OS 크래시 시 최대 1초 분량의 트랜잭션을 잃는다.
책 4장의 '사전 동의(Informed Consent)' — 성능 이득과 리스크를 함께 제시하라는 원칙이 여기 적용된다.

## M-7 | 7장 + 실습 — 체크포인트 압력과 미계상 시간

체크포인트는 WAL이 `max_wal_size` 를 넘으면 강제로 발생한다(requested checkpoint).
이걸 일부러 자주 터뜨려 응답시간이 어떻게 요동치는지 본다.

```sql
-- ① psql -d pgbench_lab. 재시작 없이 축소 가능
ALTER SYSTEM SET max_wal_size = '256MB';
SELECT pg_reload_conf();
SELECT checkpoints_timed, checkpoints_req FROM pg_stat_bgwriter;   -- 시작값 기록
```

```bash
# ② 부하 실행
./gradlew :pgbench-lab:bootRun --args="run --clients=16 --seconds=60 --scale=10"
./gradlew :pgbench-lab:bootRun --args="monitor"    # checkpoints_req 증가분 확인

# ③ 로그에서 체크포인트 발생 간격 확인 (log_checkpoints=on 이라 전부 남는다)
docker logs tuninglab-postgres 2>&1 | grep -i checkpoint | tail -20
```

```sql
-- ④ 원복 후 재측정하여 p99 차이를 비교
ALTER SYSTEM RESET max_wal_size;
SELECT pg_reload_conf();
```

> PostgreSQL 17 부터 체크포인트 카운터가 `pg_stat_bgwriter` 에서 **`pg_stat_checkpointer`** 로
> 옮겨졌다. 16 이하는 `pg_stat_bgwriter` 를 본다.

### 참고: 실제 측정값 (16 clients / 60초, scale=10)

| `max_wal_size` | TPS | p99 | **max** | 강제 체크포인트(req) 증가 |
|---|---|---|---|---|
| 1GB (기본) | 3,438 | 15.51 ms | **69.4 ms** | +1 |
| 256MB | 3,023 | 17.07 ms | **3,745.9 ms** | **+6** |

**여기서 봐야 할 것은 TPS 도 p99 도 아니다.** TPS 는 12% 줄었을 뿐이고 p99 는 10% 밖에
안 움직였다. 그런데 **max 가 69ms 에서 3.7초로 54배** 뛰었다.

이것이 Millsap 이 말한 **"미계상 시간(unaccounted-for time)"** 의 실물이다 —
평균도 p99 도 멀쩡한데 어떤 트랜잭션 하나가 3.7초를 멈춰 서 있었다.
쿼리 실행계획 어디에도 그 3.7초는 나타나지 않는다. 체크포인터가 더티 버퍼를 쏟아내는 동안
그 트랜잭션이 I/O 뒤에 줄을 섰을 뿐이다.

**교훈**: 사용자 민원은 평균이 아니라 max 에서 나온다. p99 만 보는 대시보드는
이런 스톨을 통째로 놓친다. `max_wal_size` 를 줄이는 것은 디스크를 아끼는 대신
**응답시간의 꼬리를 사는 것**이며, 그 가격이 이 표다.

관찰 포인트: `checkpoints_req` 가 `checkpoints_timed` 보다 많아지면 WAL 용량이 부족하다는 신호다.
평균 TPS보다 **p99가 먼저 무너지는 것**에 주목한다 — 체크포인트 중에만 느려지기 때문이다.

책 7장의 "비실행 시간(Ready-to-run 큐 대기)"은 clients 를 코어 수의 4배 이상으로 올렸을 때
p99가 실제 작업량으로 설명되지 않게 커지는 현상으로 체험한다.

## M-8 | 12장 사례2 — LIO 7,000 → 7 재현

책의 사례(0건을 반환하는 UPDATE가 실행당 7,000 LIO를 쓰다가, 결합 인덱스 추가 후 7로 줄고
전체 시간이 42분 → 수 초가 된 사례)를 랩에서 그대로 재현한다.

`docker exec -it tuninglab-postgres psql -U tuner -d pgbench_lab` 접속 후:

```sql
-- 인덱스 없는 100만 행 테이블 준비
DROP TABLE IF EXISTS demo_accounts;
CREATE TABLE demo_accounts AS
  SELECT g AS aid, 0 AS abalance, repeat('x', 80) AS filler
  FROM generate_series(1, 1000000) g;

-- ① 인덱스 없음 → Seq Scan
--    EXPLAIN ANALYZE 는 UPDATE 를 실제로 수행하므로 반드시 트랜잭션으로 감싸 되돌린다
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE demo_accounts SET abalance = abalance + 1 WHERE aid = 500000;
ROLLBACK;

-- ② 인덱스 추가 후
CREATE INDEX ON demo_accounts (aid);
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE demo_accounts SET abalance = abalance + 1 WHERE aid = 500000;
ROLLBACK;

DROP TABLE demo_accounts;   -- 정리
```

실측 결과(SF 무관, 100만 행 기준):

| | 스캔 | buffers (LIO) |
|---|---|---|
| 인덱스 없음 | Seq Scan | hit=2,051 read=13,376 → **15,427** |
| 인덱스 있음 | Index Scan | hit=7 read=3 → **10** |

**15,427 → 10.** 책의 "7,000 → 7"이 1,500배 감소였는데 여기서는 1,540배다.
20년이 지나도 같은 크기의 문제가 같은 방법으로 해결된다는 점이 이 실습의 요점이다.

`BEGIN`/`ROLLBACK` 을 빼먹으면 EXPLAIN ANALYZE 가 실제로 행을 갱신해 버려
두 번째 실행부터 결과가 달라진다 — §T-0 ①의 "한 번에 한 변수" 원칙이 여기서도 적용된다.

## M-9 | 12장 사례3 + 11장 황금률 — 1행씩 vs Array Processing

"1행 단위 DML 금지"를 로더로 정량 재현한다:

```bash
# 배치 크기를 바꿔가며 같은 데이터 로드 시간 비교 (tpch supplier 등 작은 테이블 추천)
./gradlew :tpch:bootRun --args="load --db=postgres --batch=1"      # row-by-row (사례3의 안티패턴)
./gradlew :tpch:bootRun --args="load --db=postgres --batch=5000"   # array processing
```

추가 비교: JDBC URL에서 `reWriteBatchedInserts=true`(PG) / `rewriteBatchedStatements=true`(MySQL)를
제거하고 다시 측정 → 드라이버 수준 배치 재작성이 왕복 횟수를 줄이는 효과를 분리 측정할 수 있다.
이것이 책 8장의 "SQL*Net message from client는 아이들 이벤트가 아니다"의 실체다.

## M-10 | 11장 — LIO 상위 커서 찾기 (V$SQL 대응)

```sql
-- pgbench_lab DB에서 부하 실행 후
SELECT calls, rows, shared_blks_hit + shared_blks_read AS lio,
       round((shared_blks_hit + shared_blks_read)::numeric / nullif(calls,0), 1) AS lio_per_call,
       left(query, 70) AS query
FROM pg_stat_statements
ORDER BY lio DESC LIMIT 10;
```

`lio_per_call`이 비정상적으로 큰 문장이 책 11장의 "LIO 높은 커서" — §M-8 방식으로 인덱스를 검토한다.

## M-11 | 황금률 종합 — "필요 없는 일은 하지 않는다"

| 책의 금지 항목 | 랩에서의 확인 방법 |
|---|---|
| 읽지 않는 데이터 조회 | `SELECT *` vs 필요한 컬럼만 — ClickHouse에서 극대화(컬럼 저장이라 차이가 수십 배) |
| 1행 단위 DML | §M-9 배치 실습 |
| 루프 내 반복 파싱 | PreparedStatement 재사용(랩 워커 코드가 재사용 구조) vs 매번 새 Statement |
| 동일 값 UPDATE | `UPDATE ... SET x = x` 도 WAL/redo를 쓴다 — pg_stat_statements로 확인 |
| 불필요한 정렬 | §T-7의 UNION vs UNION ALL |
